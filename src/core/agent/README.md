# core/agent — 循环、工具、预算、闸门

**把 AI 从「执行一条命令」改成「拿着工具达成一个目标」。**

对话页原来是一问一答的单步：作者挑一个命令（讨论 / 挑刺 / 写剧情 / 拆场景…），后端装配一次上下文、调一次模型、把结果摊在气泡里等他点采纳。单步质量很好，缺的是**多步**——「把 12 到 18 章排一遍，注意跟第 9 章埋的伏笔对上」现在要作者点七次，还要自己去翻第 9 章。

这一层管的就是多步。它**与既有的单步命令并存**，不取代：点「写剧情」是确定性动作，多一次调度调用只是加钱加延迟。

| 文件 | 职责 |
|---|---|
| [loop.ts](loop.ts) | ★ 对话循环。一个回合 = 注入状态 → 压缩历史 → 调模型 → 过闸门 → 执行工具 |
| [registry.ts](registry.ts) | `ToolDef[]` → `ToolSpec[]`，外加把「描述与 schema 该怎么写」钉死的校验 |
| [context.ts](context.ts) | ★ 状态注入（每回合把状态机的结论拼进 system）+ 工具结果压缩 |
| [budget.ts](budget.ts) | ★ 步数 / 调用次数 / token 三条上限 + 无进展检测 |
| [policy.ts](policy.ts) | ★ 哪些动作自动、哪些先问一句、问的时候说什么 |
| [tools/](tools/index.ts) | 七个工具，全是 L1/L2 的薄包装（每个不超过 60 行） |

## 七个工具，没有第八个

| 工具 | 干什么 | 底座 |
|---|---|---|
| `list` / `read` / `search` | 查 | `Workspace.list` / `.read` / `.search` |
| `generate` | 调创作模型产出内容（花钱） | `generation.generate` |
| `write` | 落盘（吃 `draftId` 或 `content`） | `Workspace.write` |
| `edit` | 定点替换一段文字 | `Workspace.edit` |
| `run` | 工程动作（拆分 / 批量 / 摘要…） | 既有的 `features/*` |

前三个 + `edit` 是标准四件套，任何支持工具调用的模型都见过。**工具数是硬约束**：每多一个都要在每一轮里发一遍描述，而且模型选错工具的概率随数量上升。

**明确不给**：删除、改名、移动（`workspace` 上都有，就是不暴露）、`bash`、工程根之外的路径、裸 `fs`。理由见 AGENTS 第 25(c) 条。

### 为什么没有 `read_draft`

`generate` 对 text 类能力（`critique` / `check` / `discuss`）也**只回形状不回正文**，于是 agent 拿不到自己 critique 的结论，只能告诉作者「已经显示给你了」。三期留过一个提议：加一个 `read_draft` 工具把这条路接上。

**没有采纳**，两条理由：

1. **它不解决问题，只是把钱挪个地方付。** 「产物不回灌」不是嫌麻烦，是因为回灌的东西每走一步重烧一遍。critique 的结论如果值得进上下文，那它进去之后照样每步重烧；如果不值得，那 agent 本来也不需要它——**它该做的是把结论转述给作者**，而结论已经流进气泡了。
2. **真正要「看自己写了什么」时 `read` 就够了。** 作者采纳之后那份东西在磁盘上，`read` 读得到，而且读的是**作者最终认可的那一版**（他可能在气泡里改过）。没采纳的那一版不该成为下一步的依据。

代价是明确的：agent 不能「先自我批评一轮再据此改」。那条路要成立，得先有「产物在循环内多轮迭代」这套东西，而这一期的立场是**每一层的落盘都要人点**——自我迭代恰好绕开了那个人。

## 五条不能破的约束

### 1. agent 不判断「下一步」

每回合把 `deriveNextStep` 的结论注入 system 消息（`context.ts` 的 `buildStateBrief`）：

```
# 当前工程
《青云志》· 已发布 99 章 · 31.2 万字（规划中 1 章）
当前目标：第 100 章《北行》（.novelforge/plots/100-北行.md）
本章状态：待写剧情
下一步（由状态机算出，不要另做判断）：写剧情
  先把这一章的剧情脉络排出来：发生什么、因果怎么串、收在什么局面上。
提醒：第 12 章、第 13 章的上游产物改过，现有内容可能已经对不上（⟳）
```

label 与 hint **逐字**来自状态机，不在这里改写措辞。两处各判各的，界面上就会出现「徽章说待拆场景，agent 让你写正文」——而那种分叉没有任何测试拦得住，只会让作者不再相信界面（第 20 条）。

这也是**为什么没有 `status` 工具**：状态每回合免费送到，不花一次往返，也不给模型「要不要查一下」的选择。

### 2. 生成产物绝不回灌 agent 上下文

`generate` 返回的是：

```
已生成：剧情·生成 · 剧情 · 4/4 节，620 字
draftId: d3f2a-1
落点：.novelforge/plots/012-入宗.md
内容已经流给作者看了，没有写进磁盘——要落盘得由作者点采纳卡片。你不需要复述它的内容。
```

**一个正文字都没有。** 正文照旧流给前端气泡（作者看得见它在写什么），但不进循环——三千字正文塞回去，agent 每走一步重烧一遍，十步之后这一份正文被算了十次钱。

要落盘就把那个 `draftId` 交给 `write`（等价于作者点采纳卡片），仍然要过覆盖审阅。

### 3. 工具描述里不写领域知识

「剧情不写画面、天气、动作细节或台词」那几句在 [context/prompts.ts](../context/prompts.ts) 的 `STAGE_DUTY.plot` 里，由 `generate` **内部那次调用**自己带着。

在工具描述里再写一遍：一是白烧 token（每一轮都要发一遍），二是两处迟早跑偏——而跑偏之后没有任何测试会红，只有产出会一点点变味。

工具描述只写三样东西：**坐标系**（哪个目录放什么）、**限制**（一次最多返回多少、截断了会怎么说）、**怎么用才对**（连续多章走 `run` 的批量动作，别循环七次 `generate`）。

### 4. 日志不记参数值

只记**工具名与参数的键名**（第 11 条）：

```
[12:03:41] DEBUG Agent｜调用工具 generate
    参数键：target, capability, ask
```

值里可能有正文片段（`generate` 的 `ask`）、可能有整段检索词。无进展检测的指纹算的是值，但它只活在内存里。

### 5. `generate` 的 `history` 传空数组

agent 的工具调用不是作者的讨论。混进装配器，`buildContext` 的 history 层会把 `list .novelforge/plots` 当成作者提的创作要求装进 prompt。

唯一该带历史的能力是 `settle`（它要沉淀的就是一段讨论），而**明确不支持它**——agent 手上没有那段讨论，喂它空历史它会凭空编一份「刚才讨论出的结论」，比不支持更糟。返回的 error 指路到对话页手动执行。

## 闸门：不是保护，是礼貌

真正的保护在下面两层，而且**与策略无关**：`workspace/guard.ts` 的八条守卫、覆盖前审阅（`reviewOverwrite`）、批量动作自带的「预计调用 N 次」确认框——任何模式下都在。

`policy.ts` 管的只是「动手之前要不要先问一句」：

| 模式 | list/read/search | generate | write 新建/追加 | write 覆盖 | edit | run |
|---|---|---|---|---|---|---|
| 谨慎 | 自动 | **每次确认** | 确认 | 审阅 | 确认 | 确认 |
| **默认** | 自动 | 预算内自动 | 确认 | 审阅 | 确认 | 确认 |
| 放手 | 自动 | 预算内自动 | 自动 | 审阅 | 确认 | 自动（批量动作自带的框仍然弹） |

两列**三种模式完全一样，且不可配置**：`write` 覆盖交给网关的覆盖审阅（diff 本身就同时回答了「要不要动」与「改了什么」）；`edit` 一律确认，因为 `ws.edit` 走的是 `review: false` 那条路，框里写出的 old → new 就是它的 diff。

确认框给**三个选项**：执行 / 跳过这一步 / 停止 agent。只给「是/否」的话，作者想拒绝某一步就只能连整轮一起掐掉。**关掉对话框当停止处理**——他被问「要不要动你的磁盘」而没有回答，不该替他答「继续」。

拒绝之后回给模型的话**必须有信息量**：「作者跳过了这一步（…），磁盘上什么都没变。**不要重试同一个动作**。」只回一句「被拒绝」，它多半会把同一个动作再发一遍。

## 无进展检测：最常见的烧钱方式

模型卡在一个读不到的路径上反复重试——`read plots/012.md` 失败、想一想、再 `read plots/012.md`。每一次都是一整轮上下文的钱。

判据是**连续**同工具 + 同参数（键排序后序列化，模型两次填的键序未必一样）：

| 连续第几次 | 行为 |
|---|---|
| 2 | 回一条 tool 结果：「你刚才已经用同样的参数调过 X，结果和上次一模一样」，**不真的执行** |
| 3 | 停下循环，走收尾那一轮 |

判「连续」而不是「出现过」：先看细纲、再看场景、回头核对细纲是正常的工作方式。

## 预算触顶不静默停

`budget.exceeded()` 只报触了哪一条，停不停由循环决定。循环收到之后**给模型最后一次机会**（把 `tools` 摘掉，只让它说话）说明「做到哪了、还差什么」，再结束。作者叫停走同一条路。

直接掐断的话作者只看到一段没头没尾的输出，不知道该从哪接着做。上下文压不下去（`buildAgentMessages` 的 `overBudget`）也走这条路。

缺省上限：20 个回合 / 10 次生成 / 20 万 token。**`run` 的批量动作按 feature 报回来的「计划调用几次」记账**——弹窗写着 7 次、账上记 1 次，正是第 4 条要防的事。

## 取消停在工具边界

`signal.aborted` 时不再发起下一次模型调用，也不再执行下一个工具；**正在跑的 `generate` 靠它自己的 signal 停**（`ToolContext.signal` 就是同一个）。

**已经产出的 draft 保留**——那是花过钱的东西。取消的是「接着往下做」，不是「刚才做的作废」。

流中途被取消时也要认出来：规矩的 provider 会抛 `CancelledError`，但也有直接把流收掉、正常返回的——那时手里是一段半截的回答，不能当成「模型给出了最终回答」。

## 上下文压缩

agent 自己的历史会涨（工具结果一条条累积）。四条策略：

1. **system 与最后 6 轮永不压缩**。刚发生的事必须完整。
2. 更早的 `tool` 消息只留**第一行** + 「（结果已省略，需要可重新调用同一个工具）」。留第一行是因为读工具的第一行恰好是「路径 + 总量」那句——模型据此知道自己看过什么。
3. 压缩时**打一条 warn**（第 2 条：不静默截断）。
4. 压到底仍然超预算 → 停下并如实报告，**绝不丢掉用户最初那句要求**（丢了的话 agent 会开始回答一个谁也没问过的问题）。

保护窗口按 assistant 回复数而不是消息条数切：一轮里可能有一个工具调用也可能有五个，按条数切会留下几条无源的工具结果。

## 用哪个模型

| 谁 | 用哪个 | 为什么 |
|---|---|---|
| **调度**（循环自己那几次调用） | 「Agent 调度」档里第一个勾了「支持工具调用」的；一个都没勾就沿用对话页那个 | 不支持工具调用的模型在这条路上只会莫名其妙地失败 |
| `generate` 打到**正文层 / 大纲层** | 对话页选定的那个，**不走池、不 fallback** | 中途换人会让文风断掉（第 12 条） |
| `generate` 打到**剧情层** | `plotOutline` 档 | 与工程页「批量写剧情」同一个模型 |
| `generate` 打到**细节层** | `sceneBreakdown` 档 | 同上 |

走池时**窗口跟着干活那个模型走**（第 13 条：`generate` 的 `options.budget` 收的就是 `pool.primaryBudget`）——拿 200k 写作模型的窗口给快速档的 32k 模型装配上下文会稳定超窗。

`supportsTools` **由作者手动勾**，不做自动探测：探测要真发一次带 tools 的请求，那是在他没点任何东西的时候花钱（第 4 条）。

## 界面

对话页输入框旁一个 **Agent 开关**（不是新页签——它跟创作是同一件事，只是执行方式不同）。开着时发送走 `sendAgent`，**不带 stage/capability**：前端捎一份过去等于让它也参与判断，两处迟早分叉。

工具调用画成气泡里的一串折叠条，排在正文上方（先查后说），末尾一行是这一轮的账：

```
🔧 search「北境」          2 处命中     320ms
🔧 read chapters/009-北行.md  4 行       40ms
✨ generate 剧情·生成      剧情 · 4/4 节 · 620 字   12.4s
📝 write .novelforge/plots/012-入宗.md   新建 · 620 字   0.2s

已排好第 12 章的剧情，把第 9 章那处「北境旧识」的伏笔接在……
─────────────────────────────────
5 步 · 1 次生成 · 约 1.8 万 token
```

`✨` 是花钱的那一下，一眼看得出这一串里哪几步收费。**只画摘要，不画工具的完整返回值**——一章正文几千字，摊出来会把作者真正要看的那段回答挤到屏幕外。会话里存的也只是这份摘要（`ChatTurn.toolCalls`）与那一行账（`ChatTurn.agentRun`）——**账要留得住**，只在跑的时候闪一下的话，作者第二天回来翻这一轮就看不出它花了多少。

**失败的步骤标红并保留**，不因为后面成功了就把失败那步藏掉；作者跳过的那一步也照样留一行。

「采纳写入」仍然是现有那个按钮（吃 draftId）。一轮里生成多次时只挂最后那一份：更早的是它自己迭代的中间稿，三个采纳按钮摊在一个气泡上，作者分不清该点哪个。

## 依赖关系

`agent/`（L3）→ `generation/`（L2）→ `workspace/`（L1）→ `model/`。严格自下而上：**L1 不认识 L2，L2 不认识 L3**。

`controller/agent.ts` 是它在面板那一侧的入口（占生成位、走 `runTask`、把循环事件翻译成协议消息）。agent 层**不认识 controller**——反过来会成环。
