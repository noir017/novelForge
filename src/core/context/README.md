# core/context — 上下文装配

插件的核心。在有限 token 预算内，把「文风指南 + 全文大纲 + 相关角色卡 + 本层产物 + 近章原文 + 会话历史 + 用户引用」按优先级装配成一次请求的消息序列，并如实记录装了什么、丢了什么。

| 文件 | 职责 |
|---|---|
| [tokenCounter.ts](tokenCounter.ts) | ★ `TokenCounter` 接口 + 注册表 + 默认的字符加权实现（中文 ≈ 1.5 token/字，拉丁 ≈ 1/4）。另含真实用量的校准统计。 |
| [tokenizer.ts](tokenizer.ts) | 门面：`estimateTokens`（= `countTokens`）与按预算截取的 `takeHead` / `takeTail`。全仓库几十处调用点都走这里。 |
| [types.ts](types.ts) | `BuildRequest` / `BuiltContext` / `ContextItem` / `LayerId` / `LayerSpec`。单独成文件是为了打断 recipes 与 layers 的循环引用。 |
| [recipes.ts](recipes.ts) | ★ 四个阶段（架构 / 大纲 / 细纲 / 正文）各带哪些层、优先级多少，外加正文层的几张专用配方（续写、审稿、修稿、修稿续写）。**改装配策略只改这一张表。** |

| [loreSettlePrompt.ts](loreSettlePrompt.ts) | 落定设定（完善设定二期）的那一句做事原则、**任务**（替掉 `CAPABILITY_TASK.settle`：那一句说的是「这一章」，还要模型在产物之外说明没定的——与 JSON 合同打架，这里统一放进 `questions` 字段）与输出合同（只写讨论里定下的、最多 12 条、人不是设定、已有条目给合并后的完整版且讨论没碰的照抄、字数照 `LORE_ENTRY_LIMITS`、暗设没被讨论推翻的照抄、`questions` 0–5 条）。JSON 合同本身单独导出（语法修复用）。 |
| [replay.ts](replay.ts) | 重演检测（纯函数）：上一章结尾约 1000 字与新稿前 1200 字各自归一，按 8 字 n-gram 比对，**连续覆盖 ≥ 80 字**算重演，报出新稿里那一段原文。移植自上游 `hasSubstantialPreviousChapterReuse`；拒不拒收不在这里决定（卡片标红、写入点两下）。 |
| [builder.ts](builder.ts) | ★ `buildContext()`：算预算 → 按配方跑一遍层 → 拼 messages。 |

## Token 计数是可替换的

改造前 `estimateTokens` 是一个写死的函数，想换更准的算法得改遍全仓库。现在分三层：

1. **`TokenCounter` 接口**——`count(text)` 数 token、`charsFor(tokens)` 反推字符数（截断要用），可选 `prepare()` 供需要加载 wasm/词表的实现。
2. **注册表**——`registerTokenCounter()` 注册、`useTokenCounter(id)` 切换。切换失败（未注册、`prepare()` 抛错）时**保持原计数器并返回 false**，绝不让「数不了 token」把写作流程带停。
3. **`HeuristicTokenCounter`**——默认实现，就是原来那套系数，零依赖、同步、永不失败。它是所有降级路径的终点。

要接 tiktoken 或服务商的 count_tokens 接口，写一个实现注册进去即可，`builder.ts` 一行都不用改。

**校准回路**：服务商返回真实用量时（`usage` 事件 → `collect` 的 `onUsage` → `recordUsage`）记下「估算/实测」比值，`usageStats()` 可查。它**只用于日志与展示，不自动修正估算值**——估算必须是纯函数，否则同一份上下文两次装配会得出不同的预算判断，「不静默截断」的明细也就不可复现了。没给 usage 的服务商什么都不记，不拿估算冒充实测。

## 分阶段装配

一次装配由 `BuildRequest.action.stage` 决定带什么。四张配方在 [recipes.ts](recipes.ts) 里，**顺序即填充顺序**：

| 阶段 | 身份 | 带什么 | 明确不带 |
|---|---|---|---|
| **架构** | 网文策划编辑 | **架构三件（配置 / 前提 / 世界观，P0 force）**、角色图谱一览（P0）、已有角色卡（P1）；排设定清单时另带设定（P2：分类表与已有条目一览，与规划阶段同一种带法），排世界观时带命中与近几章出现过的设定，其余几件不带；**展开一条设定**（单条设定目标）另带这一条（P0 force，含暗设）、已排细纲里用到它的地方与定稿过的记录（P1，合计封顶）、相关条目（P2）；**落定设定**（设定目录上的 `settle`）历史 P0、封顶 60%，设定提到历史后面（P1）：讨论里提到的已有条目整条带（含暗设），其余一行 | 正文原文、大纲 |
| **大纲** | 策划编辑 | **架构三件 + 角色图谱一览（只给近期活跃的一段，其余只列名字）+ 故事结构指导 + 大纲（按远近带分三段：最近 10 章整条，P0 force；再往前一章一行、最多 100 章，不强制；更早的交给全文大纲）**、全文大纲与角色卡（P1）、设定（P2） | 正文原文、各章细纲（已经写过的由全文大纲交代） |
| **细纲** | 剧情编剧 | 本章细纲（单章时，P0 force）、**架构三件 + 角色图谱一览（同大纲）+ 大纲里这一次要拆的条目（这一批与前面还没拆的空壳；已经拆过的不带，之后的不带，P0 force）**、前 3 章与后 1 章的细纲、前序细纲一览（最近 30 章）、近几章的连续性事实、叙事线（P1，按区间挑：没收束的线与这几章要收的伏笔，叙事线二期）、全文大纲（P1，接住一览之前的）、结构指导；设定（P2：分类表、已有条目一览，排新章时照抄已有的名字） | 正文原文 |
| **正文** | 作者 | **文风指南、全局要求、本章细纲（含「设定」一节）、上一章结尾（不许重演）、后 5 章细纲（边界）、本章已写末尾（接着写时）、上一版（重写时），都是 P0 force**；出场角色卡、架构三件（除全局要求）、前 3 章细纲（梗概 / 关键事件 / 状态变更，单列「前几章细纲」，没定稿的标「计划」）（P1）；全文大纲、设定（P2）；近 2 章正文（P3） | 情节大纲、更早各章的细纲（2026-10-21） |

**设定（`lore` 层，设定名录）**：几百条设定的书不能命中就整条塞，先排序、再分两种形态装、按详细度封顶。顺位：R0 本章细纲「设定」一节点名的、R1 关键词命中（作者这次说的 → 本章细纲 → 本章已写的末尾）——**整条**（一句话 + 正文 + 尾巴：水位之后、本章之前定稿章里关于它的新事实，条目落后于正文时模型照样拿得到）；R2 前几章定稿出现过的、R3 大纲 / 细纲阶段其余条目按出现章数——**一句话**。整条超了上限降成一句话、一句话超了上限丢，都写原因；R3 超了只并成一条报（`lore:catalog`），不逐条刷明细。条目整合到本章或更晚时明细里提醒可能含之后的事。续写那几轮也带（只 R0、R1）。消息里整条的空行隔开，一句话的并成一张清单。

**展开一条设定（完善设定，2026-10-19，目标 `{ kind: 'lore', relPath }`，阶段是架构）**：设定那张配方多挂两层，目标不是单条设定时它们什么都不带（[layers/loreFocus.ts](layers/loreFocus.ts)）——`loreSelf`（P0 force）是焦点，这一条的一句话、关键词与全部正文，暗设照规划时的样子标明（`loreBodyFor`），还只有一句话的在明细里注一句；`loreMaterial`（P1）是两样原料（`views/loreMaterial.ts` 的 `expansionMaterial`）：**已排细纲里用到它的地方**（没定稿的细纲「设定」一节点名它的那一行、梗概与关键事件里提到它的句子，带章号）与**定稿过的记录**（与建条目、整合同一份 `recordsAbout`），两样合计照整合的 `MATERIAL_TOKENS` 封顶——都放不下各占一半、一边用不完让给另一边，没带上的写明带到第几章（第 2 条）。`lore` 层在这个目标上不提前返回：去掉目标条目本身，关键词命中的来源在作者的话之外再加这一条的标题、关键词、一句话、正文与上面那几句（整条），同一个分类目录里的一行带，给分类表（建议拆出的子条目要归类），不给 R2、R3。消息里的顺序是「定稿过的记录 → 已排细纲里用到它的地方 → 当前这一条设定」，紧挨着指令。焦点不按 `targetNo` 定位（`focus.no` 是 +∞），已写正文的书也不按正文「整理」（`settingFromText` 跳过它）。系统提示的那一句与输出合同在 [loreExpandPrompt.ts](loreExpandPrompt.ts)，不借 `LORE_ENTRY_SYSTEM`（那一份第 1 条是「不补完、不推测」）；放在 context/ 而不是 features/，因为本层不依赖 features/。

**设定条目的「暗设」（完善设定，2026-10-19）**：条目可选的第四节，读者还不知道的真相（`model/loreFile.ts` 的 `splitLoreHidden` 认）。**正文阶段（写、接着写、重写、讨论正文）与续写**：整条只带明面，这一条真有暗设被去掉的在明细 note 里注一句「暗设没带：……」（第 2 条）；作者 @ 引用的设定条目（`attachments` 层，`lore` 种类）同样去掉、同样注一句。**规划时（设定 / 大纲 / 细纲）**：整条带全部，暗设挪到最后、标题统一换成「## 暗设（读者还不知道）」（`LORE_HIDDEN_MARK`）。怎么拆、怎么标在 `layers/render.ts` 的 `loreBodyFor`，lore 层与 @ 引用共用。一句话（`loreBrief`）本来就跳过暗设。

**角色卡的「暗设」（叙事线重做，原「未收伏笔」）**：同一个口径。`characters` 层在正文阶段（写、接着写、重写、讨论正文，连同审稿、修稿——它们也是正文那一层）与续写不带这一节，这张卡真有暗设被去掉才注同一句；规划时（架构 / 大纲 / 细纲）整张带，暗设放在最后、标题同样是「## 暗设（读者还不知道）」（`render.ts` 的 `renderCharacter` / `cardHidden`，空的、写着「无」的当没有）。正文阶段 @ 引用的角色卡同样去掉。只带要点时规划带身份 / 当前状态 / 暗设，写正文只带身份 / 当前状态（`essentialCardKeys`），明细照实写。老卡里的「未收伏笔」是认不出的小节，不读。大纲、细纲合同里「暗设」那条规矩的对象是「相关世界观设定」「相关角色设定」两处。

表里与下文的章数、字数都是**上下文详细度**缺省那一级（「详细」）的值，各级见下面[「上下文详细度」](#上下文详细度)一节。

四张都按 [总计划](../../../docs/design/plans/2026-09-30-blueprint-pipeline-roadmap.md) §2.3 排：前三张二期，正文那一张三期（移植自 AI-Novel-Writer 的 `next_chapter_draft` 材料包），四期在它的 P2 加了 `evidence`。**执行卡与篇幅合同不是层**，由输出契约拼在消息最末（上游 GD:657 的顺序）。

**正文续写那几轮**（`step.kind === 'continuation'`，generation/continuation.ts）换一张精简配方：系统提示、这一轮的话、文风、全局要求、本章细纲、后 5 章边界、本章已写末尾、出场角色，外加近几章定稿的连续性事实（`recentFacts`，≤3000 字）。前几章细纲与前几章全文第一次调用已经用过，每一轮都付一次全价不值；但一条前情都不带也不行——百章实验里首轮常只写到一半，续写写了一章的大半，死了的人在续写里又活过来。细纲配方同样带 `recentFacts`（P1）：全文大纲排在它后面，预算紧时先被挤掉，细纲就会排出与正文矛盾的事。收尾过早被回退的那一轮（`step.rewound`，五期补遗 §1.1）契约开头多两句：「收尾那一段已经拿掉了，写足之后按本章细纲约定的结束状态重新收尾」。

**执行卡后面跟一块【本章边界】**（五期补遗 §1.2、§1.3；禁用词是百章实验复盘加的：生成层 `planWriting` 算好经 `BuildRequest.banned` 交过来，第一次调用点名不许用的词，续写那几轮换成「已写部分用了哪几个、几次」）：后 5 章细纲里才排到、本章与前面各章都没排过的人逐个点名「本章不出场：沈秋（第 4 章才登场）」（生成层 `planWriting` 按磁盘算好经 `BuildRequest.notYet` 交过来：带角色卡上的称呼、本章细纲自己提到的人不算，与写完查的那一份同源；没给时 `promptFactsOf` 从 focus 现算一份）；再重列比喻词上限，续写那几轮换成「已写部分用了 k 次，续写部分最多再用 n 次」（`step.similes`）。三期首跑时边界只有一句原则，第 3 章的结尾照样把第 4 章的人写了出来。

**系统提示加一条「用词贴合年代」**（§1.5）：架构、大纲、细纲的「通用要求」第 4 条与正文的硬性要求第 7 条，古代、民国、架空世界不用 PTSD、抑郁症、多巴胺、CPU 这类现代术语。越早的阶段写进去，后面每一层都照着抄。

三期加的四层：

| 层 | 注入什么 |
|---|---|
| `guidance` | 小说配置的「全局要求」一节，单独成段（`# 全局要求（每一章都要遵守）`） |
| `premiseWorld` | 小说配置（**除全局要求**，不重复带）、故事前提、世界观，一件一条 |
| `plotAhead` | 后 5 章的细纲一章一行（标题 + 关键事件前 300 字），标「绝对不要在本章提前写出」。**按章号窗口取**（N+1..N+5，上游 GD:464-466），只带排过的 |
| `chapterSoFar` | 本章已写正文的最后 1600 字：「接着写」读磁盘，续写那几轮由生成链给（含这一次刚写、还没落盘的） |

「接着写」时不带上一章结尾：这一章的开头早就从那里接过了，两个「从这里接下去」摆在一起，模型会跳回上一章去。

**`revision`（上一版正文 + 修改意见）带整章**（五期修）：从前是 `takeTail(…, 3000)`——3000 token 的尾巴，长一点的章前半截直接没了，「重写」时模型只能凭空重写开头，明细上还看不出少了什么（第 2 条）。

四期加的一层（D18）：

| 层 | 注入什么 |
|---|---|
| `evidence` | 前面各章的**定稿原文片段**：拿定稿过的细纲里连续性事实的证据原句回到那一章的正文里逐字定位，带所在段落与前后各一段（移植 `chapter-materials.ts` 的 `assembleChapterMaterials`）。只认定稿之后正文没再改过的章（细纲的 `sourceHash` 对得上正文）。前 5 章的事实全取，更早的只取提到本章角色（细纲 `characters[]` 与别名）的，最多 12 章、一共 6000 字，由近及远填、按章号正序拼成一节「# 定稿原文片段（前情以这些原文为准……）」。正文层 P2 的第一层，续写配方不带 |

- **定位不到**（作者手改过细纲里的事实或证据句）的那几条换成事实原句，条目标 degraded 并写明几条；放不下的章 dropped 写明是封顶了（第 2 条）。
- **与近章全文去重**：某一章整章正文进来了（`manuscriptFull`），它的片段改成 dropped、预算退回去——与上一章结尾片段同一个做法（`scratch.evidence`）。
- **D23**：上一章有正文却还没定稿，明细里多一条 dropped 的「第 N 章 · 定稿原文」，写明「没有连续性事实，角色状态截至第 K 章」；上一章定稿之后正文又改过，写明「连续性事实不作数」；更早的章遇到这两种静默跳过。`characters` 层每张卡的说明带「状态截至第 K 章」。不挡路，但不静默。
- **近章全文 0 章就是一章全文都不带**（四期顺手修掉：从前 `slice(-0)` 把前面每一章都整章塞了进来；现在各层取「最后 n 个」一律走 `takeLast`）。
- 上下文详细度「精简」整层不带，出一条 `evidence:off` 的 dropped 说明。

七期加的一层：

| 层 | 注入什么 |
|---|---|

几处刻意的抬高（表里加粗的几条）：

- **正文阶段文风指南升到 P0 force**。它是「读者感觉不到换人执笔」的唯一保障，不该跟一段长对话抢预算——改之前它在 P1，一段长对话（封顶 30%）加几张角色卡就能把它挤掉。
- **正文阶段本章细纲也升到 P0 force**。细纲**就是**写正文的依据：少了它，模型手上只有文风与前文尾巴，会自己编一章出来。
- **正文阶段后 5 章细纲也是 P0 force**。那是边界：没有它，模型写到章末时最顺手的就是把下一章的事提前演掉，下一章于是无事可写。
- **架构与大纲两层的架构三件是 P0 force**。四件一件吃一件：前提照着配置写、世界观照着前提与角色写，少了上一件，这一件就是凭空编的。
- **`settle`（落定细纲、落定设定）时历史 cap 从 30% 抬到 60%、优先级提到 P0**（`recipeFor(stage, capability)` 唯一一处按能力改配方的地方，不分阶段）。这条命令要沉淀的就是那段讨论，按常规由远及近截掉等于把结论截没了。**落定设定**（完善设定二期，架构那一层设定目录上的 `settle`）另把 `lore` 层从 P2 的末尾提到历史后面（P1），不让角色卡先拿走预算；`lore` 层在这个目标上照设定清单那样当规划看（分类表 + 已有条目一行一条），关键词命中的来源再加上历史那几轮（近的在前，明细里写「讨论里提到「X」」），命中的整条带（含暗设，标明读者还不知道）——要合并就得看得见原文；整条的名额放宽到一次落定的上限 12 条（`LORE_SETTLE_LIMITS`），字数另加 12 条的上限，不受详细度那一档的整条名额限制，预算放不下照样降级、写进明细。系统提示的原则与任务换成 [loreSettlePrompt.ts](loreSettlePrompt.ts) 那一份（`isLoreSettle`），合同按能力认、排在设定清单（`doc === 'lore'`）之前。

**细纲阶段带前后文而不是只带上一章**：前 3 章的细纲（梗概 + 关键事件 + 状态变更）让这一章接得上——发生了什么、人物落在什么处境；后 1 章（梗概 + 关键事件）让它不至于把下一章要用的东西提前用掉。更早的章由前序细纲一览一章一行带，不再另带一份：细纲与定稿是同一份文件，同一份不带两遍。

**挑角色卡**：`selectCharacters` 第一优先是本章细纲的 `characters[]`（没定稿时是计划出场，D13——只在这里用，不进出场统计），其后是这一轮输入里提到的、前两章定稿过的细纲里出场的与主角。

**前三个阶段都不带正文原文**：定架构、排大纲、拆细纲时读三章正文既没用又昂贵，一章三千字 × 近三章，够装下全文大纲还有富余。

## 预算与降级

| 优先级 | 预算不足时 |
|---|---|
| P0 · force | 永远保留（系统提示、用户这一句、本层产物） |
| 用户 @ 的引用 | 单条封顶预算 35%，超出从头部截断而非丢弃 |
| 会话历史 | 整体封顶按上下文详细度（缺省 30%，`settle` 时固定 60%）、单轮 12%，由近及远保留，更早的整轮丢弃。**已经写入的那一轮（`acceptedTo`）与发起它的命令轮不带**（五期补遗 §1.4）：它们落了盘，有专门的层按磁盘带，落盘后手改过的话历史里还是旧版；明细里记「已写入 xxx，以磁盘上那一份为准」。讨论与没采纳的那一版照旧带。**已经移除的内置 agent 跑的那几轮（`isBuiltinAgentTurn`）与交给它的那句指令也不带**：那是调度过程，不是讨论 |
| 角色卡 | 降级为要点：「身份 + 当前状态 + 暗设」三节（写正文时暗设本来就不带，只剩前两节） |
| 某章正文 | 降级为该章细纲（没定稿的标「计划，没定稿」）→ 丢弃 |
| 规划时一章一行的前情（大纲的中段、前序细纲一览） | 大纲最多 `outlineBriefMax` 章（缺省 100）、一览最多 `plotListMax` 章（缺省 30），由近及远放到预算用完，截过的标 degraded 并写明哪几章没带；更早的交给全文大纲（P1），明细里写它写到第几章 |

预算 = `contextWindow - maxOutputTokens - 512`，并与 provider 的 `maxInputTokens` 取小。

## 关键设计

- **不静默截断**：每条 `ContextItem` 带 `status`（included / degraded / dropped / excluded）与人类可读的 `note`，前端折叠展示。作者随时知道这次没带上什么。
- **发出去的那份原样留着**：对话页那一轮的 `built.messages` 记在回复上（`ChatTurn.contextMessages`，随会话落盘，只记第一次调用——续写、修复那几轮另行装配），装配清单摘要行上「复制完整上下文」一下复制整份。日志照旧只记条目名与 token 数（第 11 条）；工程页批量与 MCP 的 `generate` 不留。
- **层与配方分离**：「带什么」在 recipes、「怎么取」在 layers。让细纲阶段不带正文原文是配方里少写一行，不是装配器里多一个 if。
- **只读用得上的文件**：`resolveFocus` 按配方决定读不读前后章的细纲。正文阶段每次生成都多读三章用不上的细纲，那是落在关键路径上的浪费。
- **引用在 P0**：用户特意 @ 的内容不该被自动装配挤掉。
- **历史是多轮消息**：会话历史按 role 交替作为真正消息发出，不是塞一段「以下是之前的对话」；单轮过长取结尾（越靠后越接近当前进度）。
- **去重**：上一章正文能完整放下时，P0 的结尾片段自动撤掉，同一段文字不在 prompt 里出现两次。没有正文的章（只排了细纲）`manuscriptFull` 跳过，它在前几章之内时细纲由 `plotPrev` 带。
- **正文只读 `chapters/`**：一章一纲之后正文只在一处，从前还要回落到中转站 `manuscripts/`。只有 `chapters/` 的老工程一样带得出前文。
- **讨论型能力禁止改写产物**：`outputKindOf(action) === 'text'` 时系统提示里明写「只回答，不要输出改写后的完整产物」。少了这一条，模型会一边回答一边把整份剧情细纲重写一遍，而界面上那一版是不能采纳的。
- **细纲可以写具体场面，但不是正文**：从前细纲被禁止写画面与动作、只许写抽象的因果链，模型拿它去「扩写」出来的是流水账。现在细纲就是定稿那七节（连续性事实计划时空着，定稿时才生成；叙事线二期删了「新增伏笔」）：「关键事件」一条一件事、按发生顺序（3–6 条、合计 100–300 字，与定稿写出来的列表同一个样子，定稿才能逐条改而不是重写），可以写到具体场面，梗概与关键事件必填、出场人物至少一人；「看点」写爽点，也写章末吊着读者的那一下，过渡章没有爽点就只写钩子，时间地点、看点、状态变更都可以空着；合同里另有 `threads`（这一章在叙事线上的计划：推进 / 关系 / 收束 / 埋〈伏笔〉/ 收〈伏笔〉，一章最多 6 条，不进细纲，写入时写进各条线），以及一条【叙事线】规矩——照着「叙事线」那一节排，标着「本批要收」「已过第 N 章，还没收」的伏笔必须在这几章收，收不了写明推迟到第几章（原来「伏笔强制回收与释放」那一句并进来了）；不写成段的描写与对白。单章与批次用同一份蓝图合同（`{"blueprints":[…]}`，单章就是只有一项），外加上游的章节容量合同（目标字数 ±20%）。
- **`settle` 与 `generate` 的差别只在系统提示**（`CAPABILITY_TASK`），**输出契约必须一字不差**：同一份细纲不该因为入口不同长得不一样。
- **暗设不进正文，揭开靠细纲**（完善设定，2026-10-19）：写正文时看不见暗设，揭开那一章的正文模型只能从细纲知道。细纲合同（写细纲、落定细纲、批量拆细纲同一份）多一块【暗设】：标着「暗设（读者还不知道）」的，这一章不打算揭开就别写进梗概、关键事件、看点与「设定」一节的 note，要铺垫写成 `threads` 里的一条「埋」（叙事线二期；原来写进新增伏笔）、只写读者看得到的那一面；打算揭开就在关键事件里单列「揭开：……」。大纲合同同一个口径（第 10 条要求）——大纲拆成细纲，细纲进写正文的上下文。

## 依赖关系

依赖 `model/`（读架构、大纲、细纲、正文、全文大纲、角色卡、设定；`model/pipeline.ts` 提供 Stage × Capability × Target，`model/structureGuide.ts` 算结构区间，合同的字数上限也在 model 里）与 `llm/`（`ChatMessage` 类型）。**不依赖 `features/`**。被 `generation/`（对话页单次生成与生成链）与 `features/pipelineBatch.ts`（工程页批量）调用——两者走同一个 `buildContext`，因此批量与单次产出的是同一个质量。
