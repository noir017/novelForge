# core/agent — 循环、预算、闸门

**把 AI 从「执行一条命令」改成「拿着工具达成一个目标」。**

对话页原来是一问一答的单步：作者打一句话（讨论）或挑一个命令（写剧情 / 落定剧情…），后端装配一次上下文、调一次模型、把结果摊在气泡里等他点采纳。单步质量很好，缺的是**多步**——「把 12 到 18 章排一遍，注意跟第 9 章埋的伏笔对上」得作者点七次，还要自己去翻第 9 章。

这一层管的就是多步。**而且现在它是对话的唯一一条路**：单步那条（前端挑一层 + 挑个能力）已经删了。两条并存过一阵，代价是「下一步做什么」这个判断在前后端各有一份，迟早分叉——而作者在输入框里能说的话，本来就是它该自己想清楚的事。

| 文件 | 职责 |
|---|---|
| [loop.ts](loop.ts) | ★ 对话循环。一个回合 = 注入状态 → 压缩历史 → 调模型 → 过闸门 → 执行工具 |
| [context.ts](context.ts) | ★ 状态注入（每回合把状态机的结论拼进 system）+ 工具结果压缩 |
| [budget.ts](budget.ts) | ★ 步数 / 调用次数 / token 三条上限 + 无进展检测 |
| [policy.ts](policy.ts) | ★ 三种模式 × 五档意图那张表：哪些动作自动、哪些先问一句 |

## 工具不在这一层

工具在 [`core/tools/`](../tools/README.md)。循环手上只有一个 `ToolInvoker`——四个方法（`specs` / `names` / `intent` / `invoke`），**没有 `Workspace`、没有 `DraftStore`、没有 `ToolDef`**。绑环境是调用方的事：

```ts
runAgent({
  project,                                   // 只为状态注入
  tools: createNovelTools({ project, workspace, drafts, sessionId }),
  provider, ask, signal,
})
```

这么分的理由是两件将来要做的事：**工具要能端出去（MCP）**，而**循环要能换掉**（同一套工具换一个更轻的调度实现）。两层缠在一起时哪件都做不成——细账记在 `tools/README.md` 开头那张表里。

于是这一层还剩三件事，全是调度：**注入状态**、**看着预算**、**过闸门**。加一个工具不必回来改这里的任何一行；`AGENT_SYSTEM` 里也不列工具能干什么（那是每个工具自己的 `description`，模型每一轮都收得到）。

`system` 与每回合的现场描述（`brief`）都可以由调用方替换，缺省是 Novel Forge 那一套。

## 八个工具

清单与理由在 [tools/README.md](../tools/README.md) 与 [tools/novel/index.ts](../tools/novel/index.ts)：`list` / `read` / `search` 查，`skill` 取「这类事该怎么做」，`generate` 产出，`write` / `edit` 落盘，`run` 走既有的工程动作。**明确不给**删除、改名、移动、`bash`、工程根之外的路径、裸 `fs`（AGENTS 第 25(c) 条）。

从前这里写着「七个，没有第八个」。`skill` 破了它，理由在那份文件头：技能的正文取不到就等于没有技能，而现有七个里没有一个能取（`read` 够不着内置那一半——它们不在工程根内，甚至不在磁盘上）。剩下的两条路里，「让 `read` 多认一个工程之外的只读来源」是在网关上开口子，比多发一份几十字的工具描述贵得多。

### 为什么没有 `read_draft`

`generate` **只回形状不回正文**，于是 agent 拿不到自己刚产出的那份东西，只能告诉作者「已经显示给你了」。三期留过一个提议：加一个 `read_draft` 工具把这条路接上。

**没有采纳**，两条理由：

1. **它不解决问题，只是把钱挪个地方付。** 「产物不回灌」不是嫌麻烦，是因为回灌的东西每走一步重烧一遍。讨论出的结论如果值得进上下文，那它进去之后照样每步重烧；如果不值得，那 agent 本来也不需要它——**它该做的是把结论转述给作者**，而结论已经流进气泡了。
2. **真正要「看自己写了什么」时 `read` 就够了。** 作者点头落盘之后那份东西在磁盘上，`read` 读得到，而且读的是**作者最终认可的那一版**（他可能在气泡里改过）。他没要的那一版不该成为下一步的依据。

代价是明确的：agent 不能「先自我批评一轮再据此改」。那条路要成立，得先有「产物在循环内多轮迭代」这套东西，而这一期的立场是**每一层的落盘都要人点**——自我迭代恰好绕开了那个人。

## 五条不能破的约束

### 1. agent 不判断「下一步」

每回合把 `deriveNextStep` 的结论注入 system 消息（`context.ts` 的 `buildStateBrief`）：

```
# 当前工程
《青云志》· 3 卷 · 已发布 99 章 · 31.2 万字（还没交付的剧情段 1 个）
当前目标：剧情 100《北行》（.novelforge/plots/03-北境/100-北行.md）
状态：待写剧情
下一步（由状态机算出，不要另做判断）：写剧情
  先把这一段的剧情脉络排出来：发生什么、因果怎么串、收在什么局面上。
提醒：剧情 101、剧情 102 的上游产物改过，现有内容可能已经对不上（⟳）
```

说法与界面**同一份口径**：还没交付的段说「剧情 N」（位次），已经交付的说「第 N 章」
——把段叫成章会让 agent 和作者都以为它将来就是第 N 章，而一段可以拆成三章。

label 与 hint **逐字**来自状态机，不在这里改写措辞。两处各判各的，界面上就会出现「徽章说待写正文，agent 让你去拆章节」——而那种分叉没有任何测试拦得住，只会让作者不再相信界面（第 20 条）。

这也是**为什么没有 `status` 工具**：状态每回合免费送到，不花一次往返，也不给模型「要不要查一下」的选择。

### 1.5 技能索引拼在稳定前缀里

每回合的 system 是三段：

```
AGENT_SYSTEM        ← 常量
技能索引             ← 开局扫一次，一轮之内逐字不变
brief()             ← 每回合重建（作者可能正在另一个窗口改文件）
```

技能是「这类事该怎么做」的工作流说明（机制见 [core/skills/](../skills/index.ts)）。索引里**只有作者明确开到「仅标题」/「完整」的那几份**——缺省是「仅用户」，那一档 agent 连名字都看不到。

**所以最常见的情况是这一段整个不存在**：什么都不配的工程里技能一个字都不占每轮预算。这正是「方法论可以写得很长」的兑现方式——写多长都不进上下文，直到有人要它。

开到那两档时，索引仍然只有名字（加「完整」那一行描述）：一次 `readdir` 加一次 `Object.keys()`，**正文一个字都不进**，由 `skill` 工具在模型真要用时才取。

**索引不跟着 `brief()` 每回合重建**，两条理由：

1. **它不该变。** 作者中途新建一个技能，本轮不认、下一轮才认——技能是方法论不是状态，中途换掉会让 agent 的判据在一轮之内漂移。
2. **将来接 prompt caching 时断点就在这里。** 目前三条 HTTP 协议实现都没发 `cache_control`，所以现在还没有缓存可省；但把易变的东西排在稳定的东西之后是接缓存的前提，反过来会让这个断点做不出来。

代价说清楚：「仅标题」那一档模型只看到名字，看不到「什么时候该用」。所以**技能名必须自带触发力**；不够的话下一步是把它开到「完整」（多发一行描述），**而不是**回头去做模糊匹配——猜错时它会拿到一份自己没想要的技能，而且不会知道。

`RunAgentOptions.system` 给了就**整段替换**（连索引一起没有）：换掉身份的调用方多半也换了工具集，替它硬塞一份指向 Novel Forge 技能的清单是错的。

### 1.6 作者呼出的技能不走索引，也不走 `skill`

输入框里打 `/` 挑一份，那一份的**整份正文折进作者那句话的前面**（`controller/skills.ts` 的 `foldSkills`），循环这一侧什么都不用改——它看到的就是一句长一点的话。

**不让 agent 自己去 `skill` 一次**：「仅用户」那一档它连名字都没在索引里见过，递个名字过去等于让它去相信一个自己没见过的名字，还多花一次往返（第 4 条）。

**方法在前、要求在后**：模型对最近的内容最敏感，要它做的事该挨着它读到的最后一句。**一个字都不截**——截掉一半的工作流比没有更糟（它会照着半套流程做完，还以为自己做全了）；真塞不下时由 `buildAgentMessages` 报「压不下去」并停下说清楚（第 2 条）。

呼出是**一次性**的：发出去就清空，下一句话不会又带上那几千字。会话里只留名字（`ChatTurn.skills`），正文已经在 `content` 里了。

### 2. 生成产物绝不回灌 agent 上下文

`generate` 返回的是：

```
已生成：剧情·生成 · 剧情 · 4/4 节，620 字
draftId: d3f2a-1
落点：.novelforge/plots/012-入宗.md
内容已经流给作者看了。要不要落盘正在问他，结论就在下面。你不需要复述它的内容。

作者没有采纳这份产物，磁盘上什么都没变。**不要重复生成同一份**——问问作者要改什么。
```

**一个正文字都没有。** 正文照旧流给前端气泡（作者看得见它在写什么），但不进循环——三千字正文塞回去，agent 每走一步重烧一遍，十步之后这一份正文被算了十次钱。

**落盘不用它自己张罗**：产出的当下循环就替它问了一句（`onArtifact` → `controller/chat.ts` 的 `askArtifact`），结论直接接在这段返回的后面——上面那第二段就是作者答「不采纳」时接上去的。写没写盘它读得到，也就不会再生成一遍（那是一整轮上下文的钱）。

**这一问与策略无关**：三种模式都问，包括「放手」。那是产品承诺（第 19 条），不是偏好设置。它当然也还可以把 `draftId` 交给 `write` 去写别的路径，那条路照旧过闸门与覆盖审阅。

### 3. 工具描述里不写领域知识

「剧情不写画面、天气、动作细节或台词」那几句在 [context/prompts.ts](../context/prompts.ts) 的 `STAGE_DUTY.plot` 里，由 `generate` **内部那次调用**自己带着。

在工具描述里再写一遍：一是白烧 token（每一轮都要发一遍），二是两处迟早跑偏——而跑偏之后没有任何测试会红，只有产出会一点点变味。

工具描述只写三样东西：**坐标系**（哪个目录放什么）、**限制**（一次最多返回多少、截断了会怎么说）、**怎么用才对**（连续多章走 `run` 的批量动作，别循环七次 `generate`）。

### 4. 日志不记参数值

只记**工具名与参数的键名**（第 11 条）：

```
[12:03:41] DEBUG Tools｜调用工具 generate
    参数键：job, target, ask
```

值里可能有正文片段（`generate` 的 `ask`）、可能有整段检索词。无进展检测的指纹算的是值，但它只活在内存里。

### 5. `generate` 的 `history` 传空数组

agent 的工具调用不是作者的讨论。混进装配器，`buildContext` 的 history 层会把 `list .novelforge/plots` 当成作者提的创作要求装进 prompt。

从前这里还有一档 `settle`（把一段讨论沉淀成细纲），它是唯一该带历史的能力，而 agent 手上没有那段讨论——喂它空历史它会凭空编一份「刚才讨论出的结论」。那一档已经删了：现在作者要按讨论的结论排剧情，直接跟它说就是了，那段讨论本来就在 agent 自己这一轮的历史里。

## 闸门：不是保护，是礼貌

真正的保护在下面两层，而且**与策略无关**：`workspace/guard.ts` 的八条守卫、覆盖前审阅（`reviewOverwrite`）、批量动作自带的「预计调用 N 次」确认框——任何模式下都在。

`policy.ts` 管的只是「动手之前要不要先问一句」。它**不认识任何一个工具的名字**——性质与说辞由工具自报（`ToolIntent`），这里只按五档查表：

| gate | 谨慎 | 默认 | 放手 | 谁是这一档 |
|---|---|---|---|---|
| `auto` | 自动 | 自动 | 自动 | list / read / search / skill |
| `costly` | **每次确认** | 预算内自动 | 预算内自动 | generate |
| `mutating` | 确认 | 确认 | 自动 | write 新建/追加、run（批量动作自带的框仍然弹） |
| `reviewed` | 审阅 | 审阅 | 审阅 | write 覆盖 |
| `always` | 确认 | 确认 | **确认** | edit |

后两档**三种模式完全一样，且不可配置**：`write` 覆盖交给网关的覆盖审阅（diff 本身就同时回答了「要不要动」与「改了什么」）；`edit` 一律确认，因为 `ws.edit` 走的是 `review: false` 那条路，框里写出的 old → new 就是它的 diff。

**认不出的工具名不弹框**：`invoke` 会回一句「没有叫 X 的工具」，为一个根本不存在的动作问作者，他只会莫名其妙——而且答「继续」也没有用。

**两个选项**：确认 / 跳过。「跳过」只否掉这一步，agent 接着跑别的。**叫停整轮不在这一问里**——那是输入框旁边那颗「停止」，与「这一个文件要不要动」是两件事；摆进闸门的第三颗按钮常被误当成「跳过」，而两者的后果差着一整轮。**没有回答仍然不算「继续」**——他被问「要不要动你的磁盘」而没答（Esc、关掉框、这一轮被取消），那一步就不该发生，按停止结算。

同意那颗按钮上**不写动词**：「Agent 要写入「第 12 章的细纲」」这句话就在按钮上方，按钮再说一遍「写入」是重复；而让每个工具各报一个动词（写入 / 替换 / 执行 / 生成）的话，同一颗主按钮每次换一个字，作者反倒要先读按钮才敢点。

**问在哪儿不是这一层的事**：循环手上只有一个 `onGate` 回调（`AgentHandlers`），面板那条路把它画成**贴在输入框上方的一张卡片**（[controller/gate.ts](../controller/gate.ts)），答完在这一轮的流水里留一行记录；没实现 `onGate` 的调用方（命令行式宿主、测试）才退回 `Host.confirm` 那个全局模态框。

从前这里直接调 `Host.confirm({ modal: true })`，于是一个盖住整个窗口的框把作者从他正要判断的东西上拽走——它动的是哪个文件、前几步读了什么，全在被盖住的那条气泡里，而窗口还是锁死的，想先翻一眼那个文件再决定都做不到。

拒绝之后回给模型的话**必须有信息量**：「作者跳过了这一步（…），磁盘上什么都没变。**不要重试同一个动作**。」只回一句「被拒绝」，它多半会把同一个动作再发一遍。

## 无进展检测：最常见的烧钱方式

模型卡在一个读不到的路径上反复重试——`read plots/012.md` 失败、想一想、再 `read plots/012.md`。每一次都是一整轮上下文的钱。

判据是**连续**同工具 + 同参数（键排序后序列化，模型两次填的键序未必一样）：

| 连续第几次 | 行为 |
|---|---|
| 2 | 回一条 tool 结果：「你刚才已经用同样的参数调过 X，结果和上次一模一样」，**不真的执行** |
| 3 | 停下循环，走收尾那一轮 |

判「连续」而不是「出现过」：先看细纲、再看正文、回头核对细纲是正常的工作方式。

## 预算触顶不静默停

`budget.exceeded()` 只报触了哪一条，停不停由循环决定。循环收到之后**给模型最后一次机会**（把 `tools` 摘掉，只让它说话）说明「做到哪了、还差什么」，再结束。作者叫停走同一条路。

直接掐断的话作者只看到一段没头没尾的输出，不知道该从哪接着做。上下文压不下去（`buildAgentMessages` 的 `overBudget`）也走这条路。

缺省上限：20 个回合 / 10 次生成 / 20 万 token。

**账在这一层，报数在工具那一层**：工具只 `usage.record(n)` 说「我调了 n 次模型」，连上限是多少都不知道；「已用 3/10 次生成，约 1.2 万 token」那句话由循环在工具跑完后补一条（`budget.describe()`）。`run` 的批量动作报的是 feature 算出来的「计划调用几次」——弹窗写着 7 次、账上记 1 次，正是第 4 条要防的事。

## 取消停在工具边界

`signal.aborted` 时不再发起下一次模型调用，也不再执行下一个工具；**正在跑的 `generate` 靠它自己的 signal 停**（`ToolRun.signal` 就是同一个）。

**已经产出的 draft 保留**——那是花过钱的东西。取消的是「接着往下做」，不是「刚才做的作废」。

流中途被取消时也要认出来：规矩的 provider 会抛 `CancelledError`，但也有直接把流收掉、正常返回的——那时手里是一段半截的回答，不能当成「模型给出了最终回答」。

## 「没调工具」不一定等于「说完了」

循环判「模型给出了最终回答」的依据只有一条：**这一回合没有工具调用**。这个等号有一个前提——上游没在别处说过它想调工具。

而兼容网关会破坏这个前提。抓到过的现场：一个 OpenAI 协议转 Anthropic 协议的中转，上游模型明明返回了 tool_calls，它把 `stop_reason: "tool_use"` 照抄过来了，却把 `tool_use` 内容块整个漏掉。同一份请求连发八次，五次这样，三次正常——纯抖动。

那种响应落到循环里，长得和「模型说完了」一模一样：agent 说一句「我先看看工程状态」就停，一个工具都没调，也没有任何报错。作者看到的是「agent 执行一轮就中断」，而日志里什么都没有。

所以 provider 现在把上游报的收尾原因归一成 `StopSignal` 交上来（`llm/provider.ts`），循环拿它跟手里的工具调用**对账**：

| 手里的调用 | 上游说的 | 循环怎么办 |
|---|---|---|
| 有 | — | 照常执行 |
| 没有 | 没说 / `end` | 模型给出了最终回答，收工 |
| 没有 | `toolUse` | **响应缺了一半**：原样重发这一回合（`PROTOCOL_RETRIES` 次） |
| 没有 | `toolUse`，重发几次都一样 | 停下，`stopReason: 'protocol'`，说清是接口丢了这一段 |

重发的是**同一份上下文**：那一回合什么都不往 `turns` 里推，否则模型会看到一条自己没调过工具的助手消息，下一轮跟着跑偏。重试额度**按回合归零**——第 3 步抖一次不该受第 1 步抖过一次的影响。

次数定在 3：实测那条链路的丢失率约六成（十八次里丢了十一次），四次机会把「一个回合彻底失败」压到 0.6⁴ ≈ 14%（只重发一次是 36%，一轮走五步就几乎跑不完）。再往上加收益开始平，而每一次重发都是一整轮上下文的钱（第 4 条）。

值得说清的是：**被丢掉的那一回合本来就已经花过钱了**，而且什么都没换回来。重发不是「多花一次」，是把已经花掉的那次救回来；真正不该做的是无声地把它当成「模型说完了」。连着四次都缺就不是抖动，而是这条链路压根不支持工具调用，那时该做的是把话说清楚。

重发有一个看得见的代价：那一轮模型已经说出口的话早流到界面上了，重发之后它会再说一遍类似的话。所以每次重发都在气泡里留一句 `onNote`——重复得有个解释，否则看起来像 agent 在自言自语。

现场排查用 `node scripts/diag-tools.js`：它走真实 provider、真实 `AGENT_SYSTEM`、真实的八个工具规格，一边打印请求体里到底带没带 `tools`，一边把 SSE 原样计数，把「我们没发」「上游吞了」「我们没解析出来」三种成因分开。

## 上下文压缩

agent 自己的历史会涨（工具结果一条条累积）。四条策略：

1. **system 与最后 6 轮永不压缩**。刚发生的事必须完整。
2. 更早的 `tool` 消息只留**第一行** + 「（结果已省略，需要可重新调用同一个工具）」。留第一行是因为读工具的第一行恰好是「路径 + 总量」那句——模型据此知道自己看过什么。
3. 压缩时**打一条 warn**（第 2 条：不静默截断）。
4. 压到底仍然超预算 → 停下并如实报告，**绝不丢掉用户最初那句要求**（丢了的话 agent 会开始回答一个谁也没问过的问题）。

保护窗口按 assistant 回复数而不是消息条数切：一轮里可能有一个工具调用也可能有五个，按条数切会留下几条无源的工具结果。

## 用哪个模型

| 谁 | 用哪个 | 为什么 |
|---|---|---|
| **调度**（循环自己那几次调用） | 「Agent 调度」档里第一个解析得出的；那一档没配就沿用对话页那个 | 不支持工具调用的模型在这条路上只会莫名其妙地失败——换一个 |
| `generate` 打到**正文层 / 大纲层** | 对话页选定的那个，**不走池、不 fallback** | 中途换人会让文风断掉（第 12 条） |
| `generate` 打到**剧情层** | `plotOutline` 档 | 与工程页「批量写剧情」同一个模型 |

走池时**窗口跟着干活那个模型走**（第 13 条：`generate` 的 `options.budget` 收的就是 `pool.primaryBudget`）——拿 200k 写作模型的窗口给快速档的 32k 模型装配上下文会稳定超窗。


## 界面

对话页**只有一个输入框，说话就是 agent**（不是新页签、也不是开关——它跟创作是同一件事）。发送走 `sendAgent`，**只带作者那句话**：不带层、不带要干什么，前端捎一份过去等于让它也参与判断，两处迟早分叉。

界面上因此**没有「下一步」主按钮**：那个入口是往单步那条路上发请求的。「下一步做什么」这个判断还在（`deriveNextStep`），只是唯一的消费者变成了 agent 每回合的状态注入。

`/` 这个键回来了，但**不是从前那个命令面板**：那一版是「挑一层 + 挑个能力」，等于让前端参与「该做什么」的判断；现在它呼出的是**一份技能**（「这类事该怎么做」），选中之后仍然只发一条 `sendAgent`——干什么还是 agent 自己按状态注入决定。两者形似而事不同：一个替它决定做什么，一个告诉它怎么做。

`@ 引用` 折进作者那句话里：整文件只给路径（它手里有 `read`，自己读比把几万字塞进第一条消息便宜），选区内联那份快照——快照只存在会话里，磁盘上的文件可能早改了。`/` 呼出的技能同样折进那句话，排在**最前面**（方法在前、要求在后），且一个字都不截。

**它想的、它说的话与它做的事按发生顺序交替**（`ChatTurn.segments`，一段思考、一段文字或一次调用），末尾一行是这一轮的账：

```
▸ 思考过程 · 82 字                                   ← 折叠着，点开才看
🔧 list .novelforge            2 项          2ms
🔧 read chapters/009-北行.md    4 行         40ms
▸ 思考过程 · 140 字                                  ← 读完之后又想了一次

我先看看第 9 章那处伏笔，再排第 12 章。
┌ ✨ generate 剧情·生成                     23.6s  ▾ ┐
│ ✓ 剧情 · 4/4 节 · 620 字 · 已写入 …012-入宗.md      │
├─────────────────────────────────────────────────┤
│ ## 第一节 入宗                                    │ ← 产出的正文，卡内滚动
│ 他在藏书阁门口站了很久……                          │
└─────────────────────────────────────────────────┘

已排好第 12 章的剧情，把第 9 章那处「北境旧识」的伏笔接在……
─────────────────────────────────
5 步 · 1 次生成 · 约 1.8 万 token
```

**顺序是这一轮唯一存不回来的东西**。改造之前存的是 `content` 一整块 + `toolCalls` 一整串，界面只能画成「所有工具 / 一整段话」——真实过程是「读了三份 → 说一句 → 生成 → 再说一句」，作者看不出哪句话是在哪一步之后说的；而 `content` 拿的还是 `outcome.text`（**最后一回合**那段文字），中间几回合说的话跑完就没了。`toolCalls` 那个形状已经没有了（`serializeTurn` 也不认它），界面只认段一条路；旧会话里没有段的那些轮次照旧画成一块正文。

**相邻的调用并进同一串**：连着五次 `list` / `read` 仍然读成一串流水账，散成五块比从前更乱。思考、文字与 generate 卡打断它。

**攒段那几个纯函数在 [`model/session.ts`](../model/session.ts)**（`pushTextSegment` / `pushReasoningSegment` / `pruneSegments` / `textOfSegments`），不在 controller 里：它们是 `TurnSegment` 上的纯运算，跟那个类型放在一起才测得动。其中一条不显眼但要紧——**纯空白开不了新段**：模型几乎总在调工具前后吐一两个换行（有时一整回合只有一个 `\n` 就转头调工具），为它开一段，界面上就是工具条之间一块一行多高、什么都没有的盒子（`.msg-body` 是 `pre-wrap` 还带内边距），刷新之后那块空白还随会话回来。段**内**的换行照旧留着，只有段首那几个抹掉；段尾那几个流到最后才有，由收尾时的 `pruneSegments` 剪掉。

**思考是段，不是气泡顶上那一块**（`kind: 'reasoning'`）。`ChatTurn.reasoning` 那个字段是**单步创作**留下的形状——一轮只调一次模型，思考自然只有一份，画在正文上方就对了。agent 一轮要调好几次，**每个回合各想一次**：攒成一整块的话，「它读完这三章之后在想什么」就和第一回合的胡思乱想拌在一起了，而前者才是作者要看的（第 3 步为什么突然去改别的章）。**思考不是正文**——`textOfSegments` 只取文字段，所以它不进 `content`、不算字数、不被采纳写入章节；也**不作为 assistant 消息的 content 发回给模型**（那等于让它把想的话当成说过的话，下一轮还要再烧一遍），跨回合接得上靠的是 `traces`（provider 原样交回的思考凭据，见 [../llm/README.md](../llm/README.md)）。

这条通道从前是断的：`runAgent` 收流时只挂了 `onDelta` 与 `onUsage`，provider 一路发上来的 `reasoning` 事件到循环这里被丢掉。对话只留 agent 一条路之后，这意味着**界面上永远看不到思考**——开着深思考，等三十秒，气泡里什么都没有。

**那一行上只画摘要**——一章正文几千字，摊出来会把作者真正要看的那段回答挤到屏幕外。**每一条都点得开**：展开后是这一步的参数与回给模型的那段文本（`TurnToolCall` 的 `argsText` / `resultText`，都由 `controller/agent.ts` 截过，参数 800 字、返回 2000 字，截了就在文末说明——第 2 条）。参数在 `toolCall` 那一刻就有，所以「它现在卡在哪个路径上」当场查得到。

**`generate` 那一次自成一张卡**（`TurnToolCall.output`，上限 2 万字）。`read` 回来的东西是它查资料的过程，而这几千字是**产物本身**——作者接下来要判断「这份要不要落盘」，读的就是它。所以它走的是**另一条通道**——工具照旧往 `ToolRun.onDelta` 里推，循环按「当下跑的是哪一次调用」贴上 `callId` 再经 `AgentHandlers.onToolDelta` 送出去（`onDelta` 从此只有模型自己说的话）——默认展开、卡内滚动：铺开会把整轮对话顶出屏幕，藏起来又等于让作者隔着一行摘要去决定要不要写进书里。改造之前它顺着 `onDelta` 和模型说的话拌进同一个文本节点，刷新之后还整份消失（那几千字没进会话）。

会话里存的就是这些段加那一行账（`ChatTurn.agentRun`）——**账要留得住**，只在跑的时候闪一下的话，作者第二天回来翻这一轮就看不出它花了多少。

**失败的步骤标红并保留**，不因为后面成功了就把失败那步藏掉；作者跳过的那一步也照样留一行。

**落盘的结论记在各自那一次调用上**（「已生成 剧情 · 4/4 节 · 已写入 …012-入宗.md」/「· 未采纳」）。一轮里它可能生成三份、写了两份、拒了一份——挂在气泡上的单个「产物」字段说不清这件事，而每一次调用本来就各占一段、随会话留得住。

**有段的那一轮不可就地编辑**：`editTurn` 换的是整轮内容，而那时正文分成好几块，改哪一块都映射不回去；产物改不改走落盘卡片那条路。

气泡上**没有任何能写文件的按钮**：那一问在产出的当下就问过了（输入框上方那张权限卡片，与动手前那一问同一副样子）。

## 依赖关系

`tools/`（L3）→ `generation/`（L2）→ `workspace/`（L1）→ `model/`。严格自下而上：**L1 不认识 L2，L2 不认识 L3**。

`agent/` 与 `tools/` **并列**，不是上下级：agent 只 `import type` 那一份契约（`tools/types.ts`），tools 一行都不 import agent。由 [tests/contract/layerBoundary.test.js](../../../tests/contract/layerBoundary.test.js) 守着。

`controller/agent.ts` 是它在面板那一侧的入口（绑工具环境、占生成位、走 `runTask`、把循环事件翻译成协议消息）。agent 层**不认识 controller**——反过来会成环。
