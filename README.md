# Novel Forge

**把一个脑洞养成一本完整的书。**

从一句「如果……」开始，先想清楚这本书到底讲什么，再摊成每一章发生什么、每一幕长什么样，最后落成一章一章能读的正文。每一层的产物都摊在屏幕上，可编辑、可重写，**确认后才落盘**——AI 负责把上一层展开成下一层，拍板的始终是你。

写长篇卡住的地方通常不是写不出字，而是**越写越记不住自己写过什么**：小说越写越长，模型窗口装不下全文，续写时人物走形、伏笔丢失、文风漂移。所以这里同时做两件事：**往下展开**（把一个念头逐层填成成品）与**往回记住**（把已经写下的东西压成模型每次都带得动的记忆）。

具体是三件事：

1. **逐层展开** —— 大纲拆成一章章的细纲、细纲拆成场景、场景写成正文，正文再拆成发布章节。每一层都可以停下来讨论、挑刺、重做，写到一半发现前面不成立，回上一层改了再往下走。
2. **按创作阶段装配上下文** —— 写大纲、排剧情、拆场景、写正文是四件不同的活，需要的东西完全不同。工具按你当前在哪一层，只装那一层用得上的东西，并把装了什么、没装什么明明白白列给你看。
3. **整合总结** —— 手动命令把已发布的正文压缩成单章摘要、滚动全书摘要、角色卡和世界观设定，让「记忆」始终有限且可人工校正。

所有数据都是工作区里的普通 Markdown，可以 Git 版本管理，可以直接用编辑器改，程序挂了数据也还在。

三种用法共用同一套核心：浏览器里的[独立 Web 版](#独立-web-版不装-vs-code-也能用)、双击就开的[桌面 App](#桌面-app-windows--linux)、以及 [VS Code 插件](#快速开始)。

### 从脑洞到成书

```
你的脑洞   →  全书大纲  →  本章细纲  →  场景细节  →  正文  →  拆成章节
一句「如果…」   故事讲什么    这章发生什么   这幕长什么样   怎么写出来   你标断点，一键拆
```

第一格目前还只是你在输入框里说的那句话：选「大纲」层描述你的念头，让它先长成一份全书大纲，后面几层都从那里展开。把这句话本身也变成工程里一份可讨论、可挑刺、可重做的产物（**灵感层**），设计见 [docs/design/specs/2026-08-14-idea-stage-design.md](docs/design/specs/2026-08-14-idea-stage-design.md)，尚未实现。

**管理的单位是「章」，但生成时不按章硬切。** 每一章都有自己的细纲、场景与正文，编号从头到尾连着；已经写了 99 章的老工程直接打开就是 99 章，新建的就是第 100 章，不需要迁移。

不同的是**生成那一步不被「一章要有头有尾」框住**：模型按剧情的自然长度写，写出来的正文先落在中转站 `.novelforge/manuscripts/`。你读一遍，在想断开的地方插一行 `---`，点「拆成章节」——正文按标记切成发布章进 `chapters/`，中转站那份随即删掉。不标就是整章原样发布。此后一切按章管理：摘要从 `chapters/` 生成，上下文里的前文也从那里取。

**拆分不花一分钱。** 它只是按标记切文件：断点是你标的，第一章沿用原标题，其余留纯序号名等你重命名。让模型给章起名，是拿 token 换一批你八成要重写的名字。

每一层都可以**讨论、挑刺、检查**（AI 只回答，不动你的文件），也可以**生成、改写、拆分**（产出可采纳的产物）。切到哪一层，AI 的身份就跟着变——同一句「这里冲突太弱」，策划编辑会去动故事结构，剧情编剧会去调这一章的节奏，编剧会去想这一幕的画面，作者会去改措辞。

**约束在剧情，素材在场景。** 该发生什么、埋什么收什么由细纲定，它写的是**剧情脉络**——谁做了什么、导致什么、收在什么局面上，**不写画面、天气、动作细节或台词**，也不规定这一章从哪句话开头、到哪句话结尾（起讫是拆分那一步才定的事）。场景层不再往下压约束，它产的是写正文时能直接取用的东西——子时下着雨、青石墙泡胀了、巡逻的灯每隔一丈一盏、墙那边两个弟子在说什么。写正文时这些素材是**可以取舍的材料**，不是必须逐条落实的清单：写小说不需要那么在乎逻辑严丝合缝，一张勾选表换来的是一段读着像施工验收的正文。

各层产物串成一条**指纹链**：改了大纲，用到它的细纲标一个 ⟳；改了某一章的细纲，该章场景标 ⟳；改了场景，还没拆分的正文标 ⟳。已经发布的章不会被拉回「待写正文」——那是你已经发出去的文字，工具只挂一个 ⟳ 提醒，不催你重写。这件事**零模型调用、零 token**——它只是比对 hash。把「变更影响」做成 AI 功能，等于每改一行剧情就烧一次钱，还会给出看起来很像但没有依据的影响清单。

流水线不是必经之路：想直接写正文就直接写。四层里任何一层空着都不挡着下一层，只是上下文会少一些东西。

## 快速开始

```bash
git clone <this-repo> && cd novel-forge
npm install
npm run compile
```

在 VS Code 里打开本仓库，按 `F5` 启动 Extension Development Host（会自动打开 `sample-novel/` 示例工程）。

用在自己的小说上：

1. 打开一个空文件夹作为工作区
2. 命令面板 → `Novel: 初始化小说工程`
3. 点活动栏的 Novel Forge 图标 → 「设置」页点一个预设添加服务商 → 填 API Key → 点该模型的「测试」
4. 回到「对话」页，在下拉框里选模型，描述接下来要写什么

## 独立 Web 版（不装 VS Code 也能用）

同一套核心逻辑另有一个独立壳：在本机起一个 Web 服务，浏览器里操作，写作仍在你自己的编辑器里完成。

```bash
# 方式一：源码直接跑（需要 Bun）
npm run standalone                                   # 空窗口；上次没关文件夹则恢复
npm run standalone -- sample-novel                   # 打开该目录
npm run standalone -- sample-novel --no-open --port 4000
npm run standalone -- sample-novel --verbose         # 终端也打调试级日志
npm run standalone -- init [目录]                    # 终端交互式初始化（缺省才是当前目录）

# 方式二：编译成单文件可执行
npm run dist                                   # 产出 dist/novelforge（当前平台）
./dist/novelforge                              # 空窗口
./dist/novelforge sample-novel

# 方式三：npm 包
npm i -g novel-forge && novelforge             # 空窗口
novelforge sample-novel                        # 打开该目录
```

服务只绑定 `127.0.0.1`，无鉴权——设计上只服务本机作者。WebSocket 额外校验 `Origin`（只认本机同端口），挡住恶意网页跨源写入。配置与 API Key 存在 `~/.novelforge/config.json` / `secrets.json`（不再用 VS Code 的 settings.json / SecretStorage；插件壳首次激活时会把旧配置一次性迁移过去）。

独立版是一个 VS Code 式的工作台：左边活动栏切「对话 / 工程 / 文件 / 历史 / 日志 / 设置」，右边是**内置文件编辑器**，中间的分隔条可拖拽（双击复位）。深浅主题用标题栏右上角的按钮切换，选择记在浏览器里。不带目录启动时是空窗口（Get Started + 文件 / 编辑 / 帮助）；文件 → 打开文件夹在同一进程里换工程，不必重启服务。上次关窗口时工程还开着，下次会恢复；先「关闭文件夹」再退出则仍进空窗口。记忆在 `~/.novelforge/window.json`。

### 文件（资源管理器）

活动栏第三个页签，独立版专属——插件形态里这件事由 VS Code 自己的资源管理器承担。

它列的是**工程目录的原样结构**，与「工程」页那个整理过的视图不同：这里一个文件都不藏，**包括 `.novelforge/` 这类点开头的文件夹**。摘要（`summaries/`）、会话记录（`sessions/`）、`project.json`、`style.md` 都在里面——想手改它们，这里是唯一入口。

- 点文件夹展开/折叠，按需加载（几百章的工程不会一进来就扫全盘）；展开状态记在浏览器里，刷新后还在
- 点文本文件在右侧编辑器打开；图片、压缩包这类打不开的文件名字置灰，点了交系统默认程序
- 编辑器里当前编辑的那个文件在树上高亮，工具栏的 ◎ 可以定位到它
- 右键：展开/折叠、在系统中打开、复制相对路径

这一页**只看不改**：新建、改名、删除仍然在「工程」页做（那里的操作锁在章节/角色/设定三个区内，删除也是搬进回收站而非真删）。

### 内置编辑器

在「工程」页点任意章节、角色卡、设定条目，或在「文件」页点任意文本文件，即可在右侧打开；产物落盘后也会自动打开写入的那一章。

- 多标签页，未保存的标签带圆点标记
- `Ctrl`/`Cmd` + `S` 保存，「还原」丢弃修改重新读盘
- 底部状态栏显示字数、字符数、行列位置与保存状态
- Markdown 可切「预览」；frontmatter 单独框出，不混进正文
- 刷新页面不丢未保存的草稿（存在浏览器本地，磁盘内容变过则丢弃并提示）
- 关闭有未保存修改的标签、或带未保存内容离开页面，都会先问一句
- 打开的是章节正文时，工具栏多一个「草稿」按钮——点它在右边再开一块编辑区，草稿与正文并排（见 [章节草稿](#章节草稿)）

**两块编辑区**：主区放正文，草稿区在它右边，各有自己的标签条、工具栏与状态栏，中间的分隔条同样可拖拽、双击复位。`Ctrl`+`S` 保存的是**有焦点的那一块**。草稿区里关掉最后一个标签就整块收起。同一个文件不会同时出现在两块里——从另一块打开时会连同未保存内容一起搬过去。窄屏（≤900px）放不下并列，草稿区自动隐藏。

**不静默覆盖**：保存带内容 hash 乐观锁。如果文件在你编辑期间被别处改过（你在真编辑器里改了、或插件写入了内容），保存会被拒绝并给出取舍——「用磁盘版本覆盖编辑器」或「用编辑器内容强制保存」，绝不悄悄盖掉任何一边。

进内置编辑器的条件：在工程目录内、不超过 2 MB，且是纯文本——扩展名在 `.md` / `.markdown` / `.txt` / `.json` / `.yml` / `.yaml` 里，**或者**它本身就是一份章节（数字前缀 + 非二进制扩展名，所以 `001-楔子` 这种无扩展名的章节也打得开）。其余仍交系统默认程序；工具栏上的「外部打开」可随时切到你自己的编辑器。

与插件版的差异：

| 能力 | 插件 | 独立版 |
|---|---|---|
| 加入选区 | 读编辑器选区 | 弹粘贴框 |
| 角色卡更新 | diff 编辑器对比 | 确认框（无 diff） |
| 打开文件 | VS Code 文档 | 内置编辑器（非文本回落系统默认程序） |
| 打开草稿 | 开在正文旁边一栏（`ViewColumn.Beside`） | 右边第二块编辑区 |
| 浏览工程目录 | VS Code 的资源管理器 | 侧栏「文件」页（含点开头的文件夹） |
| vscode-lm（Copilot） | 支持 | 隐藏（无 Copilot 授权） |
| 弹窗（输入/确认/选择） | 原生对话框 | 网页 modal（WebSocket 往返） |
| 主题 | 跟随 VS Code | 页内切换深/浅 |

断线时页面顶部出现红色重连条，恢复后自动重放全量状态。

## 桌面 App（Windows / Linux）

不想开终端、不想面对浏览器地址栏的话，还有一个桌面壳：双击图标就是一个普通桌面应用。
不带工程也能启动（空窗口 Get Started）；上次关窗口时工程还开着则恢复。打开/关闭文件夹
走页面里的 File 菜单，不重启窗口、不杀 sidecar。

```bash
npm run app:dev      # 开发运行（需要 Rust 工具链）
npm run app:build    # 出安装包（Linux: AppImage / deb，Windows: NSIS）
```

它是**一层纯壳**：里面装的就是上面那个独立 Web 版的单文件可执行，壳负责把它悄悄起起来、
把窗口导航过去、退出时收掉。所以界面、功能、数据落点与独立 Web 版**完全一致**——
文件仍是工作区里的普通 Markdown，仍然可以用你自己的编辑器改、用 Git 管。

换工程用标题栏「文件 → 打开文件夹…」。服务起不来时闪屏给出原因和「查看日志」
（壳看到的进程输出在 `<应用日志目录>/sidecar.log`，与网页里那个「日志」页不是一回事）。

Windows 安装包必须在 Windows 上构建（sidecar 能交叉编译，Tauri 的 Rust 壳不能），
见 [.github/workflows/app.yml](.github/workflows/app.yml)。细节与已知坑见
[src/shells/desktop/README.md](src/shells/desktop/README.md)。

## 界面

活动栏里只有一个侧边栏视图，全部内容都在这个 webview 里，顶部 tabbar 切五页：

| 页签 | 内容 |
|---|---|
| **对话** | 四层创作。选层 → 选动作 → 描述要什么 → 流式生成 → 就地编辑 → 当场点头才落盘 |
| **工程** | 章节 / 角色 / 设定 / 文风与摘要，以及各自的操作入口 |
| **历史** | 本工程的所有会话，可打开、重命名、删除 |

侧边栏太窄时，点右上角 ⧉ 可以把同一个面板作为标签页在编辑器区打开——两边是同一个会话，内容实时同步。

（[独立 Web 版](#独立-web-版不装-vs-code-也能用)在「工程」后面多一个「文件」页，即工程目录的资源管理器；插件形态里这件事由 VS Code 自己的资源管理器承担。）

### 工程页

六个可折叠分组（「出场人物 · 未建卡」只在确有其人时出现）。行上只有内容——图标、名字、字数/副标题——**所有操作都在右键菜单里**，和文件管理器一样：

- **章节** —— 创作流水线在工程页上的落点，扁平一列，序号即章号。**一行同时代表一章的两面**：规划（`plots/` 里的细纲）与成品（`chapters/` 里的发布正文），两边都可能缺席——只有细纲是「还没写完的章」，只有成品是「老工程里早就写好的章」，右键菜单据此增减。行首圆点表示摘要新鲜度：`●` 最新、`○` 缺失或过期（还没拆分发布的章不算过期，那不是「旧了」是还没到那一步）；后面跟一个**流水线徽章**说明这一章该做哪一步（待写剧情 / 待拆场景 / 待写正文 / **待拆分** / 待审阅 / 已完成），鼠标移上去看四段完成度；上游改过的章挂一个 ⟳。**鼠标悬停在章节行上会浮出这一章的摘要**：悬停约半秒后出现，按小节分块；摘要过期会标「已过期」，没有摘要时说明原因。**鼠标可以移到浮窗上去**——那样它会一直留着，长摘要可以滚动，也能选中复制；移开才收。浮窗始终夹在窗口内，屏幕矮时自动翻到行的上方或压低高度改用滚动。点名字**在编辑器里打开这一章**（成品正文 → 待拆分的正文 → 细纲，取第一个有的那份）；要接着写就用右键的「进入这一章」——它落在这一章当前该做的那一步上。右键有「打开正文 / 打开细纲 / 进入这一章 / 剧情 · 场景 · 正文（各带完成度，点了直接切到创作页那一层）/ 总结这一章 / 看摘要 / 草稿」，以及重命名与删除。正文写完还没拆分时，菜单最上面多一条 **「拆成章节」**。**没有「移动到…」**：顺序由序号决定，把一章挪进子目录只会让它从流水线上消失。
  在**分组标题**上右键有「新建章节」与三条批量动作：**批量写剧情**、**批量拆分场景**、**批量写正文**。三者都是一章一次调用、可并发、可停止，动手前的确认框会写清要调几次模型、走哪一档。**它们只补空白**——已经写过的一律跳过，不问也不覆盖（一次弹几十个对比框没人看得完，跳过是那条路上唯一安全的做法）。要重做某一章，去创作页单独重做。
- **章节** —— 你的**发布区**：写完正文之后自己切出来的一篇篇成品。这里是**纯文件列表**，没有徽章、没有进度、没有 ⟳——工具不分析它的内容，也就没有任何「该做什么」可说。每层内正序排列（第 1 章在上，与文件名顺序一致），支持分卷等目录收纳。字数后面的「· 草稿」表示这一章已经有草稿。点标题打开文件；右键只有「打开 / 打开草稿（没有就新建）/ 重命名 / 移动到… / 删除」。
- **角色** —— 副标题除标签别名外，还给出这个人在摘要里的出场章数（「出场 12 章」）。上次更新角色卡之后又出场了几章，会以 `＋N` 标在行尾。右键除「打开」与三个类文件操作外，多两项：**更新角色卡**（只读新增的那几章）与**重新通读全部 N 章**，详见下一节。
  在**分组标题**上右键另有两条不调模型的整理动作：**清理别名**——删掉 aliases 里不是专属称呼的词（`她`、`姐姐`、`少女`、`这位小姐` 这类泛称，以及被误填成别名的其他角色的名字）；**查找并合并重复角色卡**——同一个人被建成两张卡时（摘要里一会儿写「方源」一会儿写「古月方源」就会这样），逐组问你保留哪一张，其余的搬进 `.novelforge/.trash/`。两者都只改文件头部的 frontmatter，**你手写的正文一个字都不会动**。
  如果有两张卡抢同一个称呼，这一组顶部会出现一条黄色提示——出场统计只会算给其中一张，另一张必然是错的，而这件事光看界面看不出来。
- **出场人物 · 未建卡** —— 摘要里出现、但还没有角色卡的人物，按出场段数从多到少排。点名字（或右键「创建角色卡」）会建一张卡，并立刻通读他的出场段落把档案填出来。在分组标题上右键还有「给全部 N 人建卡」，一次把这一组清空（动手前会报清人数、段数与预计调用次数）。这一组只在确实有这种人时出现。
- **设定** —— 点开对应的 Markdown 文件；副标题显示 keywords。右键可「从已写正文生成/更新设定」：首次会逐章通读，随后为每条设定做一次跨章整合；新条目按分类目录创建，已有条目逐条审阅后才覆盖。
- **文风与摘要** —— 全书摘要（含覆盖到第几章）、文风指南、全书大纲，以及「重建」「从正文提取」「同步过期摘要」「提取/更新角色卡」。这几行是工程的固定文件，**不能**重命名或删除。分组副标题给出摘要覆盖情况（如「已总结 62/76 章 · 14 章待总结」）。

  在**全书大纲**那一行（或这一组底部的工具行）右键，同样有那三条批量流水线动作——大纲是整条流水线的源头，从它出发做批量最顺手。

**出错的行会挂一个感叹号。** 角色卡、章、设定条目一旦生成失败，那一行的名字前面会出现 ❗，鼠标移上去说清楚发生了什么：**红色**表示这次整体失败、磁盘上的东西一个字都没改（比如模型没按要求返回 JSON，角色卡原样不动）；**黄色**表示部分完成——成果已经写回，但有一块没成，下次更新会从那里重来。浮窗里能看到时间、原因与建议，鼠标可以移进去选中复制。这个标记会**一直挂着直到那一项成功为止**，成功之后自动消失——你不必守着日志页，也不会因为错过一条 toast 就拿着一张没更新的角色卡继续写下去。（完整记录仍然在日志页，那里能翻到每一批的细节。）

有过期摘要时这一页顶部会出现黄条，写清「有几章缺失或过期」「已总结多少 / 共多少章」，并画一条进度条；点「立即同步」批量补齐。同步跑起来后这个按钮会撤掉（重复点只会撞上「已有任务在进行」），改由页面顶部的任务进度块接手。**这条提示只长在工程页**——过期摘要要处理也只能在这里处理，对话页那点宽度留给正文；人在别的页时，活动栏「工程」上的小圆点负责留个记号。工作区还不是小说工程时，这一页显示初始化入口。

#### 长任务进度

同步摘要、重建全书摘要、提取角色卡/文风这类要连着调几十次模型的动作，会在工程页顶部出现一块进度：**任务名 · 第几项/共几项 · 百分比 · 已用时 · 停止按钮**，下面一行是当前正在处理的对象（如「第 12 章《夜访》」）。

- 计时每秒自己走，不等后端推——一次模型调用可能安静一分钟，秒数停住会让人以为卡死了。
- 不知道总量的阶段（比如提取文风的「分析中」）画一条来回扫的条，不给假的百分比。
- 「停止」立刻中断，已完成的部分**保留**（摘要是一章一写盘的，停在第 30 章就有 30 份摘要）。
- 刷新页面或重连后进度条自动接上，任务不会因为你关了标签页而消失。

同一时刻可以有多个任务并存，各占一行。

### 日志页

第四个页签。上面说的每一步都在这里留痕，用来回答「刚才那 76 章卡在哪了」：

| 能做什么 | 说明 |
|---|---|
| 按级别过滤 | 调试 / 信息 / 警告 / 错误，默认「信息及以上」。逐章请求这类细节在「全部（含调试）」里 |
| 关键字过滤 | 对来源、消息、详情一起匹配 |
| 展开详情 | 带 ⏵「详情」的行可以点开，里面是耗时、文件路径、失败原因、堆栈等 |
| 加载更早 | 往前翻**重启之前**的日志。日志页平时只显示本次会话的几百条（存在内存里，关掉就没了），更早的存在 `.novelforge/novelforge.db` 里，保留 30 天。点一次往前翻一页，翻到头按钮会变成「没有更早的了」 |
| 复制 | 把**当前筛选出的**日志按纯文本复制，方便贴进 issue |
| 清空 | 清掉**内存缓冲**（库里的历史不动，仍然翻得到）。会留一条「日志已清空」——「日志是空的」和「日志被清过」是两回事 |
| 自动滚动 | 默认开。翻上去看东西时不会被新日志拽回底部 |

两条安全约定：

- **日志里绝不出现 API Key**。所有文本都过一遍脱敏，`sk-…`、`Bearer …`、`api_key=…` 一律抹成「…〔已隐去〕」。可以放心整段复制出来求助。
- **不记 prompt 与正文全文**，只记条数、字数与 token 估算。一次续写的 prompt 有十万字，记下来会把此前所有日志挤没。

日志只存在内存里（最近 800 条），不落盘、不上传，关掉进程就没了。插件版另外把同一份日志写到 VS Code 的**输出面板**（「Novel Forge」通道，命令 `Novel: 显示输出面板日志`），可以和其他扩展的日志并排看；独立版则打在启动服务的终端里（`--verbose` 连调试级一起打）。

其它页面（对话、历史、设置）以及独立版的编辑区，右键给一个「刷新」。

#### 文件夹与文件操作

章节、角色、设定三个区都能像文件管理器一样用：**建文件夹、往里塞东西、随便嵌几层**。文件夹默认折叠，点一下展开，折叠状态记在界面上，刷新数据不会把你收好的树又摊开。（细纲不在其中：`plots/` 是扁平的，序号即章号，它的改名与删除走章节行自己的右键——见下。）

新建有三个入口：页面顶部工具栏的「＋ 新建章节 / 角色卡 / 设定 / 文件夹」建在区根目录；在分组标题或分组空白处右键「在此新建…」同样落在区根目录；**在某个文件夹上右键，落点就是那个文件夹**。

新建章节**不问标题**：文件按纯序号命名（`007.md`），建完直接把你送到这一章当前该做的那一步——刚建出来是空的，所以那一步是「写剧情」。标题要等剧情排完、知道这一章到底发生什么之后再起，走「重命名」。想好之前它在界面上显示为「第 7 章」。章号取 `plots/` 与 `chapters/` 两边的最大号 +1，所以老工程的 99 章之后建出来的就是第 100 章。

任意文件或文件夹上右键，还有这三个操作：

| 操作 | 说明 |
|---|---|
| 重命名 | 章节的 `NNN-` 序号前缀自动保留，只让你改标题部分。正文首行的 `# 标题` 只在它原本与文件名一致时跟着改——你要是单独改过它，那是你手写的东西，改名不动。草稿跟着搬 |
| 移动到… | 弹出同一个区里的目录列表（含根目录）选落点 |
| 删除（移到回收站） | 搬进 `.novelforge/.trash/`，保留原来的相对路径，随时能手动捞回来。文件夹连里面的东西一起搬，删之前会告诉你里面有多少个文件 |

**章的改名与删除是另一回事**：一章不只是一个文件——场景目录与中转站正文的名字都跟着细纲走，摘要与草稿跟着发布章节走。所以改名时**一起搬**（对话页顶部那支 ✎ 改的也是当前这一章），删除时**一起进回收站**，确认框里会把要删的东西列出来。章节没有「移动到…」：顺序由序号决定，把一章挪进子目录只会让它从流水线上消失。

几条不会被打破的规矩：**不跨区**（章节挪不进角色目录，任何操作也出不了工程目录）、**不覆盖**（目标位置已有同名文件就直接报错退出，绝不悄悄盖掉）、**不真删**（一切删除都是搬进回收站）。

改名与移动都**不会让这一章的产物变旧**：跟着改的只有 frontmatter 与标题行，参与新鲜度判断的指纹一个字节都不碰——给一章起个名字不该让它写好的正文显示「上游已变更」。

分卷不影响任何逻辑：章节序号仍然全书连续。

### 章节草稿

每一篇发布章节都可以有一块**和正文并排的涂改区**：放废弃的段落、备选的写法、给自己的批注。草稿是普通文本文件，跟着工程走、可 Git、可手改，和别的东西一样。

在章节上右键点「新建草稿」（已有草稿时显示「打开草稿」），或者在内置编辑器里打开正文后点工具栏的「草稿」按钮。**首次点的时候才创建**——不会给一个已经二百章的工程凭空撒二百个空文件。

草稿存在工程根的 `drafts/` 下，路径镜像章节在 `chapters/` 之下的那一段，文件名（含扩展名）原样沿用：

```
chapters/001-楔子.md        →  drafts/001-楔子.md
chapters/第二卷/003-夜访.md  →  drafts/第二卷/003-夜访.md
chapters/005-手记.txt       →  drafts/005-手记.txt
```

几条要记住的：

- **草稿不进 LLM 上下文。** 装配器任何阶段都不读它——想让模型看见，就在 `@ 引用` 里手动挑（草稿单列一组，只列已经建过的）。
- **绝不覆盖。** 第二次点「打开草稿」只是打开，不会把你写的东西换成模板。
- **草稿跟着章节走。** 章节改名或移动，草稿一并搬过去；如果新位置已经有草稿了，两份都留着并提示你自己去合。
- **删章节不删草稿。** 确认框里会说明草稿留在哪儿。
- 草稿**不是**可管理区：它不出现在工程页的树上，也不能在界面上重命名/移动/删除——它的位置由章节路径推导，直接改它只会让下次点「打开草稿」建出一个新的空文件。要清理就在文件管理器里删。
- 草稿字数不计入章节字数，也不影响摘要新鲜度。

### 对话怎么用

对话页从上到下分四块：**流水线条**（我在哪一层）、**工作区卡**（我正在改的那份东西）、消息区、**下一步**（我接下来该干什么）。

打开一章的正确方式是**在工程页点它的名字**，或者在输入框旁的下拉框里选它。选中之后界面会自动落到**那一章当前该做的那一层**：还没排剧情就落剧情层，剧情写好了就落到「拆场景」，场景填齐了就落到正文，正文写完了就落到「拆成章节」。你不需要自己判断该从哪儿接着做。

#### 流水线条

顶上一行只报你在哪：`第 12 章《夜入青云》 › 场景 2`（**信息条不是按钮**，切层靠下面那三格）；行尾一格徽章说这一章整体走到哪了（`待拆场景`、`待拆分`、`待审阅`…）。右侧两个小按钮：**✎ 给当前这一章起名/改名**（新建出来的章只有序号，起名就在这儿），**＋ 开始一段新对话**。下面是这一章的三层状态与摘要：

```
剧情 ●  细节 ◐ ⟳  正文 ○                    摘要待更新
```

- 状态点是**实打实算出来的**：4 场里有 2 场备好了素材就是「进行中」，不是一个存在文件里的状态字段（那种字段在你手删半段正文之后就开始撒谎）。
- **⟳ 表示上游改过**。改了剧情，那一章的场景就挂上它——不是错误，是提醒你回头看一眼。手写的产物永远不会挂 ⟳（拿一个凭空的过期标记催你重做，你会学会无视所有标记）。
- 切到细节或正文层时，下面还会列出这一章的场景，点哪一场就写哪一场。虚线框的是还没备素材的，写正文之前先把环境、动作、对话想出来。

三层都可以点——**流水线不是单行道**。写正文时发现剧情不成立，点回剧情层改了再回来，比自己去 `plots/` 里翻文件快得多。

#### 工作区卡

流水线条上挂着一个入口，鼠标移上去（或点一下钉住）浮出**当前这一层的产物本身**：剧情层是这一章的目标与剧情脉络，场景层是这一幕的时间地点与备好的素材（环境、动作、对话），正文层只给字数与写了几场（三千字摊在浮窗里没人读，要读点「打开」）。聊到第十轮它还在——回头确认「这一场的雨到底下了多久」不用往上翻。

#### 下一步

输入框上方只有**一个主按钮**，写着这一章现在该做的那件事：

| 这一章的状态 | 主按钮 |
|---|---|
| 还没有剧情 | 写剧情 |
| 有剧情、没拆场景 | 拆成场景 |
| 有场景、还没备素材 | 设计场景 N |
| 场景齐了、正文没写 | 写场景 N 的正文 |
| 场景改过、正文没跟上 | 重写正文 |
| 正文写完、还没拆分 | 拆成章节 |
| 拆分发布了、摘要过期 | 总结这一章 |
| 都齐了 | 不给按钮 |

（整本书还没大纲时主按钮是「生成大纲」；有大纲还没拆过章时是「拆成章节大纲」。）

**点了就跑，不必先输入什么**——该说的都在剧情细纲和场景卡里了。输入框里有字就当补充要求一起带上（「多写点雨里的细节」）。

其余动作（讨论、落定剧情、扩展、挑刺、检查、拆分、改写）收在 **`/` 命令**里：**在输入框里直接打 <kbd>/</kbd>**（和 Cursor、Claude Code 一样），候选列表就浮在输入框上方；也可以点输入框下面那颗「/ 命令」。接着往下打字就是过滤，中文和拼音首字母都认（`/cf` → 拆成场景）。<kbd>↑</kbd><kbd>↓</kbd> 选，<kbd>Enter</kbd> 确认——命令变成输入框里的一枚标签，那几个字符自动收走，剩下的空间留给补充要求。按 Enter 执行，用完即清：命令是一次性的选择，不是模式。

**`/落定剧情` 只有剧情层有**，它是「先跟人聊、聊出结论再落文件」的那条路：跟 AI 来回讨论几轮这一章该怎么走，谈拢了打 `/落定剧情`，它把讨论中**已经达成的结论**整理成细纲——不会塞进被你否掉的方案，也不会临时发明新走向；还没定下来的地方留空并在细纲之外说一句。为此这条命令装配上下文时**会把整段讨论都带上**（历史预算从三成抬到六成，优先级提到最高）：要沉淀的就是那段对话，按常规由远及近截掉等于把结论截没了。

另一条入口是 **`/写剧情`**：你在输入框里描述这一章的剧情走向，它按你说的填成细纲，不另起炉灶改走向，你没说到的地方顺着已有设定与前后章补上。

`/` 在中文正文里是普通字符（日期、比值、网址），所以只有「整个输入框就是一个 `/词`」才当成在下命令——`子时 3/4 刻` 和 `/ 这是一句话` 都不会弹面板。

会写文件的命令（生成/落定/改写/拆分）名字后面挂一枚「写文件」标签：点它们要花钱，而且会在磁盘上留下东西。**只有「讨论」必须先输入**，其余都可以留空——留空发出去时，消息气泡里显示的是 `/写剧情` 这样的命令名，不是一片空白。

输入框下面还有：**模型**（切换即时生效，预算按新模型的窗口重算）、**当前章**、**目标字数**（0 表示不限）。

#### 落盘：当场问你一句

产出结构化产物时，**生成一结束就在对话里问你要不要写进工程**——一张卡片，写清落点与分量：

```
🔒 把这份产物写入到「第 12 章《夜入青云》 · 剧情」
   剧情 · 4/4 节
   [ 写入 ]   不采纳
```

回复本身可以直接点进去改，**改完再点「写入」，落盘的就是你改过的那一版**。目标已经有内容时按钮是 **[覆盖并写入]**，点了还会再让你对比一遍新旧两版。点「不采纳」就一个字都不写，气泡末尾留一行「未采纳」，翻回来看得出这一轮产出过什么、你没要。

**只是讨论的回复不会问**——一段闲聊没有该落的地方。每条回复下面折叠着这次的上下文明细，点开就知道带了什么、丢了什么。

> 这一问和 AI 助手（agent）动手前那一问长得一模一样、在同一个位置：**要动你的磁盘，一律先在对话里问**。从前它是气泡末尾一颗「采纳写入」按钮，可以一直不点——于是常常攒下几份没落地的产物，谁也说不清哪份写过。

### 引用上下文（Cursor 式）

两种方式往当前这轮对话里塞内容：

- 点 **@ 引用**（或在输入框直接敲 `@`）——列出所有章节、角色卡、设定条目，也能浏览工作区任意文件。
- 在编辑器里选中一段文字，按 <kbd>Ctrl+Shift+L</kbd>（macOS 为 <kbd>Cmd+Shift+L</kbd>），或右键「将选中文本加入对话上下文」。

引用会以标签形式挂在输入框上方，发送前可以逐个移除。**选区存的是快照**——你选的时候是什么样，历史记录里就一直是什么样，之后改了原文也不会让过去的对话跟着变；整文件引用则每次都读最新的。

### 对话历史

发出第一条消息后自动保存到 `.novelforge/sessions/<id>.json`，跟着工程走，可以提交到 Git。空会话不落盘，历史列表里不会堆一排没说过话的占位。

## 目录结构

初始化后的工作区：

```
chapters/                    发布章节。**唯一真相**：摘要从这里生成，上下文里的正文也从这里取
├── 001-楔子.md               工具不分析这里，只提供文件操作
├── 002-客栈里的女人.md
└── 第二卷/                   可以按卷分子目录，随便分几层
    └── 003-夜访.md
drafts/                      章节草稿，路径镜像 chapters/，按需创建
├── 001-楔子.md
└── 第二卷/
    └── 003-夜访.md
.novelforge/
├── project.json             章节索引 + 摘要新鲜度指纹
├── style.md                 文风指南 —— 写正文时必注入
├── outline.md               全书大纲（流水线的源头）
├── characters/<名字>.md      角色卡（同样可分子目录，如 characters/主角/林昭.md）
├── lore/<条目>.md            世界观设定（同上）
├── plots/                   剧情细纲，NNN-标题.md，扁平，序号即写作顺序
│   ├── 001-楔子.md
│   └── 002-客栈里的女人.md
├── scenes/                  场景卡（按细纲名镜像成目录，一场一个文件）
│   └── 001-楔子/
│       ├── 01-踩点.md
│       └── 02-翻越侧峰.md
├── manuscripts/             **中转站**：模型写出来的正文暂存在这里，拆成章节后就删掉
│   └── 001-楔子.md
├── sessions/                对话历史，一次会话一个 .json
├── novelforge.db            失败记录与日志历史（SQLite，可随时删，见下）
├── .trash/                  工程页删掉的东西搬到这里，可手动找回
└── summaries/
    ├── 001-楔子.md          单章摘要（按**章节**名镜像）
    └── global.md            全书滚动摘要
```

**拆分前按细纲镜像，拆分后按章节镜像。** 拆分之前的两样（场景、中转站正文）跟着细纲的文件名词干走：`plots/003-夜访.md` 的场景在 `scenes/003-夜访/`、正文在 `manuscripts/003-夜访.md`。拆分之后的两样（摘要、草稿）跟着发布章节走：`chapters/003-夜访.md` 的摘要在 `summaries/003-夜访.md`、草稿在 `drafts/003-夜访.md`。改名时各自跟着搬——所以起个名字不会让写好的场景凭空消失。

**`chapters/` 是这条链的终点。** 正文拆分之后落在这里，此后它就是这本书的唯一真相：摘要从它生成，上下文里的前文从它取，工程页那一行的字数也报它。中转站里那份拆完就删了——同一批文字不该有两个真相。

老工程直接把已有的章放进来就行：没有细纲不影响，`chapters/` 里有文件就算写完了那一章，可以直接总结、直接进上下文。

剧情细纲与场景是普通 Markdown，可以直接改。它们的 frontmatter 里有个 `upstreamHash`，记着生成时上游长什么样，界面上那个 ⟳ 标记就是靠它比对出来的。手写的（没有这个字段）永远不会被标 ⟳。

**中转站正文带 frontmatter，发布章节不带。** `manuscripts/*.md` 是插件自己的产物，「这份正文依据的是哪一版场景」那个指纹就记在它的 frontmatter 里；而 `chapters/` 下的文件可以是 `.txt`、可以没有扩展名，是你的东西——拆分时只把切好的文字写进去，之后插件一个字节都不往里改。

**分子目录只是收纳。** 章节的顺序永远由文件名前面的数字决定，跟它在第几层没关系——`第二卷/003-夜访.md` 就是第 3 章。分卷不重置编号，全书连续编号。细纲则是扁平的：`plots/` 下不分子目录，序号即章号。

**摘要按发布章节的文件名对应。** `summaries/001-楔子.md` 对着 `chapters/001-楔子.md`。因此同序号但不同标题的两章（手改文件名撞车时会出现）各有独立摘要，互不覆盖；给一章改名时摘要跟着搬到新名字下。**还没拆分发布的章没有摘要是正常的**——没有成品就无从总结，工具不会为此催你。

**章节不挑扩展名。** `chapters/` 下凡是「数字前缀 + 不是二进制文件」的都算章节：`001-楔子.md`、`001-楔子.txt`、`001-楔子`（没有扩展名）、`004.json` 都会出现在章节树上，从别处导入的稿子不用先改名。图片、Office 文档、压缩包、音视频这类打开必然是乱码的会被挡在外面——往 `chapters/` 里丢一张 `001-封面.png` 不会凭空多出「第 1 章」。

只有 `.md` / `.markdown` 的章节会把正文首行的 `# 标题` 当成章节标题（并在注入上下文时剥掉）。其余格式的章节标题一律取自文件名，正文一个字节都不动——`.txt` 里写一行 `# 什么什么` 就只是正文里的一行字。

角色卡与设定条目不跟着放宽，仍然只认 `.md`：那是插件自己的数据格式（frontmatter + 固定小节）。

**`novelforge.db` 是可以删的。** 它只存两样东西：**失败记录**（哪张角色卡/哪一章/哪条设定生成失败了，工程页上那个红色感叹号就是读它）与**日志历史**（让日志页能看到重启之前的记录，超过 30 天自动清理）。你的作品内容一个字都不在里面——正文、摘要、角色卡、设定永远是纯 Markdown。删掉它不会丢任何内容，只是丢掉这些历史痕迹，下次需要时会自动重建。它已经在 `.gitignore` 里（连同 WAL 模式产生的 `-wal` / `-shm` 两个附属文件），不会进版本库。

> 从 0.1.x 升级：元数据目录由 `.novel/` 改名为 `.novelforge/`。插件启动时检测到旧目录会问一次是否重命名，不会静默改动。

### 角色卡格式

```markdown
---
name: 林昭
aliases: [阿昭]        # 纲要里出现别名也能命中
tags: [主角]           # 标 "主角" 的角色始终注入
firstAppear: 1
lastSeen: 3
appearsIn: [1, 2, 3]   # 出场段落（由摘要自动聚合，可手改）
updatedThrough: 3      # 上次更新角色卡时读到第几章
---

# 林昭

## 身份
## 外貌
## 性格          ← 最重要，决定模型能不能把这个人写像
## 语言习惯      ← 对保持角色声音最关键
## 人物关系
## 当前状态      ← 预算不足时优先保留
## 未收伏笔      ← 预算不足时优先保留
```

小节名固定。预算紧张时角色卡会降级为只保留「身份 / 当前状态 / 未收伏笔」三节。

`appearsIn` 与 `updatedThrough` 是插件自己维护的两个字段：前者是这个人出场过的章，后者是上次更新角色卡时读到了哪一章（增量更新的起点）。**它们只是缓存**——真正的出场记录始终在各章摘要里，插件每次刷新工程页都从摘要重新聚合。手删掉这两行不会丢数据，只会让下一次「更新角色卡」变成全量重读。

### 更新角色卡

角色行右键有两个更新入口：

| | 读哪些章 | 什么时候用 |
|---|---|---|
| **更新角色卡（新增 N 章）** | 只读 `updatedThrough` 之后这个人出场的章 | 日常。写了几章之后把新进展补进档案，最省 token |
| **重新通读全部 N 章** | 这个人出场的所有章 | 角色卡被改乱了、或者想彻底重来 |

出场章由摘要自动关联，你不用再手输章号——所以**这个功能依赖摘要**：某个角色没有任何摘要提到过他，菜单里会直接说「未在摘要中出现，无法自动更新」，先去同步摘要即可。

主角可能在几十章里出现，一次装不进上下文窗口。插件会按输入预算把这些章切成若干批，**并在动手前告诉你要调几次模型**：

> 全量重建「林昭」的角色卡：需要通读 34 章，分 4 批，预计调用模型 4 次。现在开始？

后一批看得到前一批已经归纳出的内容，是逐批精炼同一张卡，不是各写各的然后拼起来。分批过程中工程页顶部有进度条，可以随时停止（已归纳的部分不会写坏原卡——最后一步才落盘，且照旧走 diff 确认）。

角色卡会在**每次续写时注入上下文**，所以它必须精炼。更新用的提示词给每一节都定了字数上限，并明确要求优先写好「性格」和「语言习惯」，外貌和人物关系写个梗概就行；「未收伏笔」里已经在正文中解决的会被删掉。反复更新十几次也不会让角色卡膨胀成一篇论文。

## 上下文是怎么装配的

这是插件的核心。**每一层带的东西不一样**——讨论故事结构时读三章正文既没用又昂贵，而写正文时那三章是必需的：

| 阶段 | AI 是谁 | 带什么 | 明确不带 |
|---|---|---|---|
| **大纲** | 资深策划编辑 | 大纲全文、全书摘要、各章摘要 | 正文原文 |
| **剧情** | 剧情编剧 | 本章细纲、大纲、**前 3 章与后 1 章的细纲原文**、更早章的正文摘要 | 正文原文 |
| **细节** | 编剧 | 本场场景卡、本章细纲、前后两场、**在场人物的角色卡** | 正文原文 |
| **正文** | 资深小说作者 | **文风指南**、场景卡、上一章结尾、近 N 章正文…全套 | —— |

前三层不带正文原文，token 因此降一个数量级。三处刻意的抬高：

- **写正文时文风指南永远保证注入**。它是「读者感觉不到换人执笔」的唯一保障，不该跟一段长对话抢预算。
- **写场景时按场景卡里写明的在场人物精确取角色卡**。你说「把这一场写扎实点」时一个人名都没有，靠在这句话里搜名字的老办法会把在场的人全漏掉。
- **`/落定剧情` 时历史对话的预算从三成抬到六成，且提到最高优先级**。这条命令要沉淀的就是那段讨论，按常规由远及近截掉等于把结论截没了。

**写剧情时会带上前后文。** 前 3 章的细纲原文让你接得上，后 1 章（如果有）让你不至于把下一章要用的东西提前用掉，更早的章以正文摘要形式带上。还没写正文的早期章带不出摘要，那时它**退化成只带「目标」一行**，并在上下文明细里注明「这一章还没写正文」——不是悄悄少带。

每一层内部按优先级填预算：

| 层级 | 内容 | 预算不足时 |
|---|---|---|
| **P0** | 系统提示、你这一轮的话、**@ 的引用**、本层产物、上一章结尾、重写反馈 | 永远保留；引用超限时截断 |
| **P1** | **本会话历史对话**、前后段剧情、（正文阶段）角色卡、全书滚动摘要 | 整块丢弃并标注 |
| **P2** | 相关角色卡、命中关键词的设定 | 降级为「身份+当前状态+未收伏笔」 |
| **P3** | 最近 N 章完整正文（默认 2 章） | 降级为该章摘要 → 丢弃 |
| **P4** | 更早段落的摘要 | 由近及远填充，填满即止 |

预算 = `contextWindow - maxOutputTokens - 512`。

**引用为什么在 P0**：你特意点了它，就不该被自动装配挤掉。但单条封顶预算的 35%，超出从头部截断——@ 一个大文件不能把前文全挤没。

**历史对话怎么带**：作为真正的多轮消息发出（role 交替），不是塞进一段「以下是我们之前的对话」。整体封顶预算的 30%、单轮 12%，由近及远填充；单轮过长时取结尾，因为越靠后越接近当前进度。

**角色卡怎么选**：本场在场人物（场景卡里明写的）→ 你这句话里出现姓名/别名的 → 最近两章出场的（读摘要的「出场人物」）→ 标签含「主角」的。取并集去重。

**讨论型的动作不会顺手改写产物**：点「挑刺」时系统提示里明写「只说问题和改法，不要顺手替他改写」。少了这一条，模型会一边回答一边把整份剧情细纲重写一遍，而界面上那一版是不能采纳的，你只会困惑。

**不静默截断**：任何被降级或丢弃的条目都会留在明细里，标明原因（「预算不足，需 800 token，剩 200」「这一章还没写正文，只带目标」「历史对话预算已满」）。每条回复下方折叠展示，你随时知道这次没带上什么。

**去重**：如果上一章整章原文能完整放下，P0 那份结尾片段会自动撤掉，同一段文字不会在 prompt 里出现两次。

### 摘要格式

单段摘要是让模型输出 JSON、再由插件渲染成 Markdown 落盘的——你读到、改到的仍然是普通 Markdown：

```markdown
---
plot: .novelforge/plots/002-客栈里的女人.md
no: 2
title: 客栈里的女人
sourceHash: a26b6dc8fb924aa7
cast: [林昭, 沈氏(那个女人), 客栈掌柜]   # 机器可读的出场人物
generatedBy: novel-forge
---

# 第2段 客栈里的女人 · 摘要

## 梗概
## 出场人物
## 时间地点
## 关键事件
## 新增伏笔
## 状态变更
```

`cast` 是给程序用的那一份出场人物：角色页的「出场 N 段」、未建卡人物清单、更新角色卡时自动关联段落，都读它。括号里是这一段对该角色的其它称呼。`## 出场人物` 小节是同一份信息给人看的形态，两者写盘时保持一致。

手写的摘要、以及 0.2.x 之前生成的摘要没有 `cast` 字段，插件会从 `## 出场人物` 小节的文字里反解出名字，不会因此在角色页上少人。重新生成一次摘要就会补上这个字段。

模型没按 JSON 格式回答时（会发生）插件逐层降级：JSON → 认 `## 小节` → 实在不行把全文塞进「梗概」。无论哪一层，这一段的剧情都不会凭空丢掉。

### 摘要过期机制

正文写盘 → 重算内容 hash → 与摘要里记录的 `sourceHash` 比对 → 不一致就在工程页把那一段标成 `○`。

摘要**不会自动重新生成**（避免后台偷偷烧 token），但工程页顶部会提示「有 N 段摘要已过期」，一键同步；切到别的页时，活动栏「工程」上会留一个小圆点提醒还有这件事没做。各段之间没有先后依赖，所以同步按 [`novel.concurrency`](#默认模型列表并发与-fallback) 并发跑（默认 3 路）。同步过程中工程页顶部有进度条（已完成几段/共几段、正在跑哪几段、已用时、可停止），每一段的成败、耗时与用的哪个模型都记在[日志页](#日志页)里；个别段落失败不会中断整批，结束时会点名是哪几段，去日志里能看到具体原因。

### 角色卡不会被静默覆盖

`提取/更新角色卡` 与角色行右键的「更新角色卡」对已存在的角色一律打开 diff 编辑器让你对比确认，而且你可以在右侧直接改完再点采纳。模型留空的小节保留原文，别名和标签取并集。

批量更新时几张卡是并发分析的，但 **diff 一次只弹一张**，按完成顺序排队——同时弹三个 diff，谁也说不清自己在看哪一张。

唯一不走 diff 的情况是**给未建卡的人物新建角色卡**——那张卡是插件刚刚创建的空卡，没有你写过的内容可覆盖。

## 配置

设置页（侧边栏 → 设置）分为「模型配置」与「上下文管理」两个二级页签。模型页管理服务商、模型预算、分档与请求参数；上下文页单独管理近期原文注入和全书摘要分批。API Key 只存 SecretStorage，不写进配置文件。「模型配置」页里「模型分档 / 任务档位 / 请求与调度」这几块日常不常动的配置收在「高级设置」折叠开关下，展开才能看到。

### 服务商与模型

可以同时配置多个服务商，每个服务商下挂多个模型。模型用 **`前缀/模型名`** 引用，前缀就是服务商的 id：

```jsonc
"novel.providers": [
  {
    "id": "glm",                                              // 引用前缀
    "label": "智谱 GLM",
    "kind": "openai",                                         // openai / anthropic / vscode-lm
    "baseUrl": "https://open.bigmodel.cn/api/paas/v4",
    "models": [
      { "name": "glm-4-plus", "contextWindow": 128000 },
      { "name": "glm-4-air" }
    ]
  },
  {
    "id": "openrouter",
    "kind": "openai",
    "baseUrl": "https://openrouter.ai/api/v1",
    "models": [
      { "name": "z-ai/glm-4.6", "contextWindow": 200000 }     // 模型名自带斜杠
    ]
  }
],
"novel.model": "glm/glm-4-plus"
```

于是：

| 引用 | 含义 |
|---|---|
| `glm/glm-4-plus` | 智谱官方的 glm-4-plus |
| `openrouter/z-ai/glm-4.6` | OpenRouter 上的 GLM |
| `ollama/qwen2.5:14b` | 本地 Ollama |

**引用只在第一个斜杠处切分**，后面的都属于模型名——OpenRouter 的模型名本就是 `厂商/型号`，不这样切就没法引用。所以服务商前缀不能含斜杠，设置页会挡住。

同一个模型走不同渠道就是两条独立的引用，各有各的 baseUrl、各有各的 API Key，切换只要在输入框旁的下拉框里选一下（或用命令 `Novel: 选择模型`）。

**窗口与输出上限按模型单独设置**。同一家的 32k 和 200k 模型常常并存，装配器按真正执行任务的模型计算预算，所以切模型或切档位时预算会跟着变。设置页不再提供全局默认预算；模型留空时使用内置兼容值（窗口 128000、输出 4096）。旧配置里已有的 `novel.contextWindow` / `novel.maxOutputTokens` 仍作为兼容兜底读取，但不再作为新配置项展示。

设置页备了 9 个常用预设（OpenAI / DeepSeek / 智谱 / Kimi / 通义 / OpenRouter / Anthropic / 本地 Ollama / Copilot），点一下**添加一整个服务商**（含常用模型和窗口大小），不会覆盖已有的。每个模型行右边有「测试」，当场发一个最小请求验证——比写半段才发现 Key 填错强。

API Key 按服务商 id 分开存。本地 Ollama 随便填一个非空值即可；`vscode-lm`（Copilot）不需要 Key，但模型有硬性输入配额，装配器会自动按其 `maxInputTokens` 收紧预算，明细里会标注「已按模型配额压缩」。

### 默认模型列表、并发与 fallback

设置页的「默认模型」是一份**排好序的清单**，不是单选。它管两件事：对话页当前用哪个模型（= 第一项），以及工程页后台任务里**没有配置档位的那些**用哪些模型——同步摘要、重建全书摘要、更新/批量更新角色卡、批量建卡、生成设定、提取文风、提取角色。配了[模型分档](#模型分档简单的活省钱难的活花钱)之后，下面这些规则在**每一档内部**同样成立：

- **串行时**（`novel.concurrency = 1`，或本来就只有一件事要做）恒用第一个模型；报错就在**其余模型里随机挑一个**重试，最多 `novel.fallbackAttempts` 次。同一个模型不会被试两遍，只有一个模型时不重试。
- **并发时**在整份清单里**轮转**取模型，把请求摊到几个服务商上——这往往是并发跑得起来的前提，单个服务商的限流额度撑不住几路并发。
- 用户点「停止」时立刻停，不会换模型重试。
- 备选模型缺 API Key 或当前环境不支持（如独立版里的 Copilot 模型）会被**排除在池外并写进日志**，不会为此连弹几个输入框。只有第一个模型缺 Key 时才会引导录入。

**对话页的单次生成不走这套**：你在输入框旁的下拉框里选了哪个模型，就必须是哪个模型写的正文——中途偷偷换人会让文风断掉。那个下拉框切换模型等于把它**提到列表首位**，所以设置页与对话页看到的「当前模型」始终是同一个。

并发只作用于**彼此无先后依赖**的条目：段落摘要之间、角色卡之间、全书摘要的各个阶段批次之间。同一张角色卡内部的分批仍然严格按顺序来（后一批要看到前一批的产出）；批量更新角色卡选「逐张确认」时，分析照样并发，但 diff 会按完成顺序**一张一张弹出**。

并发不改变总调用次数，确认框里报的「预计调用模型 N 次」在并发下依然准确；但它更容易撞上服务商的限流（429），配了多个模型时 fallback 正好接住这种情况。

> 从 0.1.x 升级：旧的 `novel.provider` / `novel.openai.*` / `novel.anthropic.*` / `novel.vscodeLm.family` 仍然生效——`novel.providers` 为空时会自动按它们生成一份服务商列表（前缀分别是 `openai` / `anthropic` / `copilot`），旧的 API Key 也会迁到新键上，不用重新输。在设置页保存一次即转为新结构。

### 模型分档：简单的活省钱，难的活花钱

工程页那几件事的难度差得很远。「把 76 段正文各总结一遍」是 76 次调用，每次只看一段、输出固定结构；「把几十份阶段摘要合并成一份全书摘要」全书只调一次，却要跨几十万字取舍主线。用同一个模型干这两件事，你只能在「贵而好」和「省而糙」之间二选一。

所以设置页把模型分成**三档**，每档各是一份有序清单（用法和「默认模型」完全一样，可排序、可多填几个做 fallback）：

| 档位 | 放什么模型 | 内置默认包含的任务 |
|---|---|---|
| **快速档** | 便宜、快的模型 | 单段摘要、全书摘要 · 分批汇总、设定 · 逐段识别、拆分场景 |
| **均衡档** | 折中的模型 | 设定 · 条目整合、角色卡 · 更新 / 建卡、剧情细纲、批量写正文 |
| **精标档** | 最聪明的模型 | 全书摘要 · 最终合并、提取角色、提取文风 |

归档的判据是「调用次数 × 单次难度」：次数多而单次简单的归快速档；一次定调、错了代价大的归精标档（提取角色决定「谁是谁」，判错会污染整个角色体系；文风指南和角色卡每次写正文都要注入上下文，写砸了会一路影响下去）。

剧情细纲与拆场景这一对值得单说：两者调用量相同（都是一段一次），但**剧情决定这一段讲什么、怎么转，写歪了后面每一场、每一段正文都跟着歪**，所以归均衡档；拆场景是在已经定好的剧情上切几刀，判据明确得多，归快速档。

**批量写正文**也在均衡档：它是量最大也最贵的一项，但正文的文风与语气直接决定成品质量，压到快速档等于用便宜模型写整本书。归均衡是折中——真要省钱或真要质量，改一格就行，默认值不该替你做这个取舍。

设置页的「任务档位」表里每项都是一个下拉框，不认同哪条默认改掉即可，标「默认」的就是内置推荐值。

几条要点：

- **不配就是不分档。** 某一档留空，归在该档的任务就沿用「默认模型」；三档都不配，行为和没有这个功能时**完全一样**。不会有任务被偷偷降级到便宜模型。
- **换模型只在档内。** 快速档的模型失败了，只在快速档里换人，绝不会自动升级到精标档——否则你以为在省钱，账单却按贵的算。
- **每档按自己的窗口切批。** 分批读正文时用的是**这一档首选模型**的上下文窗口，不是对话页那个模型的。所以快速档放 32k 的小模型也安全，不会因为你在对话页选了 200k 的模型就把一大堆正文硬塞进去。
- **确认框会说清这次用谁。** 动手前的弹窗里写的是「单段摘要 → 快速档：glm/glm-4-air」，档位没配时会明说「未配置，沿用默认模型」。
- **对话页的单次生成不受影响**，永远用你在输入框旁选的那个模型。

一个典型配法：快速档放 `glm/glm-4-air` 或 `deepseek/deepseek-chat`，精标档放你写正文用的那个好模型，均衡档留空（自动沿用默认模型）。一部几十万字的书跑一轮全量摘要，光这一项就能省下大头。

界面不使用 VS Code 自带的 TreeView 等控件，全部由 webview 渲染：一套 UI 同时供侧边栏和编辑器标签页使用，工程页与对话页共享同一个 tabbar，不再上下分栏。`projectView.ts` 只产出一份可序列化快照（任意深度的 `ProjectNode` 目录树），展开/折叠状态留在前端。

关于 token 计数：默认实现是按字符类别加权的粗估（中文 ×1.5、拉丁 ÷4），没有引入 tiktoken——体积大、要 wasm，且各家分词器本就不同，粗估只要保证不低估，加上 512 的安全余量就够用。

但计数本身是**可替换**的：`context/tokenCounter.ts` 定义了 `TokenCounter` 接口与一张注册表，想接 tiktoken 或某家服务商的 count_tokens 接口，写一个实现注册进去、切过去即可，装配器一行都不用改。切换失败（加载不了词表之类）会退回默认实现并返回 false——数不了 token 不该把写作流程带停。

服务商返回真实用量时（OpenAI 的 `stream_options.include_usage`、Anthropic 的 `message_start` / `message_delta`）插件会记下「估算 / 实测」的比值，写进日志里供你判断这个数字靠不靠谱。这份统计**不会反过来自动修正估算值**：估算必须是纯函数，否则同一份上下文两次装配会得出不同的预算判断，上下文明细也就不可复现了。
