# 技能（Skills）接入设计

**一句话**：给 agent 一份「怎么做某类事」的工作流说明，**按需读**，不占每一轮的 token。

## 为什么需要它

现在 agent 手上有两样东西：七个工具（能做什么）与每回合注入的状态（现在到哪了）。缺的是**方法论**——「审一章正文该看哪几件事、按什么顺序、判据是什么」。

这类知识不能塞进 `AGENT_SYSTEM`：它一轮里每回合都要重发一遍，而十次里有九次用不上。也不能塞进 `context/prompts.ts`——那是**被调用的模型**每次生成都要读的，占的是作者的 token 预算，且那一层要的是「你是谁、产出什么形状」的结论，不是方法。

所以：**方法论放技能，结论放提示词。** 技能只在 agent 判断「这一轮要做这件事」时才读进来。

| | 提示词（`core/context/prompts.ts`） | 技能 |
|---|---|---|
| 谁读 | 被调用的模型，每次生成都注入 | agent，需要时才读 |
| 内容 | 「你是谁、这一次产出什么、什么形状」 | 「怎么判断好坏、怎么修、改哪个文件」 |
| 长度 | 必须短，占作者的 token 预算 | 可以长，不进生成上下文 |

## 读者是产品内的 agent

**不是 Claude Code、不是写代码的人。** 这一条决定了技能能写什么：

产品内的 agent 手上只有七个工具，够得着的只有 `.novelforge/` 那棵树。所以技能里**不能出现源码路径**——「改 `prompts.ts` 的 `manuscript` 分支」对它是一句无法执行的话，它只会把这句话原样转述给作者。技能开出的药方必须落在**作者的工程文件**上（`style.md`、`outline.md`、某一份细纲），那些它有 `write` / `edit` 够得着。

现有的 `src/skills/chapter-review/` 写的正是「改 `prompts.ts`、粘条款到 `style.md`」，读者是开发代理。**它搬到 `.claude/skills/` 去**（本机私有，不入库），不属于本设计。

## 两个来源

| 来源 | 位置 | 谁维护 | 怎么发布 |
|---|---|---|---|
| 内置 | `src/skills/<名>/SKILL.md` | 我们，随应用发布 | 构建时**烘成 TS 常量** |
| 工程 | `.novelforge/skills/<名>/SKILL.md` | 作者自己写 | 就是工程数据，跟 `style.md` 一样 |

### 内置那一半为什么必须烘成常量

三个壳的资源路径各不相同，而其中一个根本没有「路径」这回事：

- **VS Code 壳**：`.vscodeignore` 排除了 `src/**`，`.vsix` 里没有这些文件；
- **独立版**：`bun build --compile` 出的是**单文件可执行**，运行时没有 `src/skills/` 可读；
- **桌面壳**：sidecar 就是上面那个单文件。

拷进 `dist/` 再运行时读盘只解决前两个壳的一半，还要让 `core/` 知道自己装在哪——而「我装在哪」是平台知识，按分层约定属于壳，不属于 `core/`。

烘成常量三个壳全部白拿：`core/` 直接 `import`，esbuild 与 bun 各自把它打进产物，`.vscodeignore` 一行不改。这与 `scripts/embed-media.js` 把前端产物烘成 `mediaAssets.ts` 是同一件事、同一个理由。

**代价**：改一份 `SKILL.md` 要重新生成才生效。可以接受——内置技能是我们改的，改完本来就要重新构建。

**内置技能不允许有 `references/`。** 附件靠 `read` 取，而 `read` 走 `guardRead`，只认工程根之内的路径——内置技能不在工程里，链接会断。所以内置技能的 `SKILL.md` **必须自足**，长内容压进正文或者拆成两个技能。工程内技能不受这条限制（它们在工程里，`read` 够得着）。

### 工程那一半不需要任何新东西

`.novelforge/skills/**` 在工程根之内，`guardRead` 直接放行，现有的 `read` 就能取 `references/`。`kindOfPath` 会把它判成 `other`（工程页不显示、装配器不读），这是对的——技能不是创作产物。

## 名字就是目录名，没有 frontmatter

一个技能 = 一个子目录 + 里面的 `SKILL.md`。**目录名就是技能名**，与「路径即产物身份」同一套口径。

**不解析 frontmatter**，因为索引只列名字（见下）——`description:` 那一行没有消费者，留着解析代码就是留着一个没人读的字段慢慢跑偏。

技能名总是带来源前缀：`builtin:chapter-review` / `project:我的审章流程`。**两个来源同名时两份都列**，各带各的前缀。前缀恒在（不是只在撞名时才加），这样同一份技能在任何工程里的叫法都一样，模型不必猜这一次要不要带前缀。

## 索引：稳定前缀，一轮只扫一次盘

`system` 现在是每回合重拼的 `${AGENT_SYSTEM}\n\n${await brief()}`（`agent/loop.ts`）——`brief()` 每回合重读磁盘是有意的（作者可能正在另一个窗口改文件）。

技能索引**不跟着重建**：一轮 agent 开始时扫一次盘，得到的字符串在这一轮之内逐字不变，拼在 `AGENT_SYSTEM` 之后、`brief()` 之前：

```
AGENT_SYSTEM        ← 常量
技能索引             ← 开局扫一次，一轮之内不变
brief()             ← 每回合重建
```

两条理由：

1. **它不该变**。作者中途新建一个技能，本轮不认，下一轮才认——技能是方法论，不是状态，中途换掉会让 agent 的判据在一轮之内漂移。
2. **将来接 prompt caching 时断点就在这里**。目前三条 HTTP 协议实现都没发 `cache_control`（`llm/` 里搜不到），所以现在还没有缓存可省；但把易变的东西排在稳定的东西之后，是接缓存的前提。反过来（索引每回合重扫重拼）会让这个断点做不出来。

**只列目录名，不读文件内容**——一次 `readdir`（工程那一半）加一次 `Object.keys()`（内置那一半），零文件读取。

代价说清楚：模型只看到名字，看不到「什么时候该用」。所以**技能名必须自带触发力**——`chapter-review` 好过 `reviewer`，`审章找AI味` 好过 `流程1`。这一条要写进「怎么写一个技能」。

## 取正文：第八个工具

`tools/novel/index.ts` 现在写着「七个，没有第八个」。**这一期破它，理由要写进那份 README**：

技能的正文取不到就等于没有技能，而现有七个工具里没有一个能取——`read` 够不着内置那一半（不在工程根内）。让 `read` 多认一个只读来源，就是在网关上开一个「工程之外也能读」的口子，而第 7 条（文件访问不越界）是产品承诺里最不该松的一条。加一个只读、不写盘、不花钱的工具，比在网关上开口子便宜得多。

```
skill(name)  →  那份 SKILL.md 的正文
```

- **`gate: 'auto'`**：不花钱、不写盘、不改任何东西，跟 `list` / `read` / `search` 同一档。三种策略下都自动执行，不弹框。
- **只回 `SKILL.md` 正文**，不回 `references/`。工程内技能的附件由模型自己用 `read` 去取（技能正文里写着相对路径）；内置技能没有附件（见上）。
- **名字不存在时回 `error`，并列出实际有哪些**——逐字照搬 `registry.ts` 那句「没有叫 X 的工具。可用的是：…」的做法：名单从**实际扫到的那一份**来，写死一串名字，加了技能之后这句话就在撒谎。绝不抛。
- **不做模糊匹配**：猜错时它会拿到一份自己没想要的技能，而且不会知道。

## 明确不做

- **不做模糊匹配**（见上）。
- **技能不能写盘、不能触发生成**。它是一份说明，读进来之后做什么仍然走那七个工具、过原来的闸门。技能里写「然后写入 style.md」，执行的是 `write`，该弹的框照弹。
- **不给技能加 `enabled` 之类的开关**。作者不想要某个技能，把那个目录删掉/改名就是了——工程里的一切都是普通文件（第 1 条的同一套思路）。
- **索引不带描述**（本期）。名字自带触发力是这一版的赌注；若实测发现模型选不准，下一步是往索引里加一行描述，而不是回头去做模糊匹配。
