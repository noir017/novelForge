# 分卷层与「剧情段」的正名

**状态**：已实现。

在 `outline.md` 与 `plots/` 之间插一层**卷**，并把「一份细纲 = 一章」这条隐含的
等式拆开：规划的单位是**剧情段**，管理的单位是**章**，两者是两条独立的轴。

---

## 为什么

### 1. 大纲直接拆章，跨度太大

从前 `outline` 阶段的 `split` 一次吐出一批章骨架。实际跑起来是这样的：

```
用户：大纲：赤星临近，全球变异…女主觉醒「掌握」能力…
模型：（写好 outline.md，随即）拆出 5 章的细纲，每章一句目标
```

全书大纲那一两千字里**没有足够的信息**去决定第 7 章该发生什么。模型只能一次
给出五章骨架，而那五章彼此的因果薄得像一份目录——它们不是「剧情」，是标题。
紧接着的「批量写剧情」会照着这份目录往下拆，错误就这样一层层放大。

中间缺的是一个**中等尺度**：一条完整的弧线，有自己的开局、升级与收束，十几到
几十万字。有了它，「接下来该发生什么」才答得准。

### 2. 「章」这个词在两处骗人

设计上早就承认了「生成时不按章硬切」：模型按剧情的自然长度写，正文落在中转站，
作者标断点，一份正文可以拆成两章、三章。但界面上那个单位仍然叫「第 N 章」，
于是：

- 作者以为「第 4 章」将来就是书里的第 4 章——**它可能变成第 4、5、6 章**。
- 一段拆成三章之后，为了维持「细纲与章同号」，后面**每一份**还没拆的细纲都要
  整体改名让路，连带搬走各自的场景目录与中转站正文。一次几十份文件的重命名
  风暴，只为维持一个作者根本不需要的等式。

---

## 改成什么

```
outline.md ──拆卷──▶ volumes/NN-卷名.md ──拆段──▶ plots/NN-卷名/NNN-段名.md
           ──拆场景──▶ scenes/… ──▶ manuscripts/… ──拆章──▶ chapters/…
```

### 卷不是一个创作阶段

`CreationStage` 仍然是四个（大纲 / 剧情 / 细节 / 正文）。卷只做两件事：

- **收纳**：剧情段按卷落进 `plots/<卷词干>/`。
- **拆分**：从卷纲拆出下一个剧情段。

所以 `CreationTarget` 多一个 `volume`，而 `stageOfTarget` 把它归到 `outline`
——分卷与拆段都是「策划编辑」这个身份的活，用的也正是大纲那一套上下文
（全书大纲 + 全书摘要）。少一个阶段就少一套配方、一套提示词、一组能力按钮。

代价是**同一个 `stage × capability` 在两种 target 上做的事不同**，所以这三处都要
收 target：

| 位置 | 全书大纲 | 某一卷 |
|---|---|---|
| `labelOf` / `commandsFor` | 「拆成卷」 | 「拆出剧情段」 |
| `buildOutputContract` | 分卷清单 JSON | **一个**剧情段 JSON |
| `parseArtifact` | `volumeList` | `plotSegment` |
| `acceptArtifact`（`outlineDoc`） | 写 `outline.md` | 写那一卷的卷纲 |

### 一次只拆一段

`plotSegment` 刻意不是列表。理由与「大纲直接拆章」是同一条：一次吐五段只会得到
一串彼此没有因果的骨架。一次一段时，模型手上有卷纲（`volumeSelf`）也有这一卷
已经排到哪了（`volumeSegments`），两层都是 P0 force——少了后者它会把已经排过的
那几段重新发明一遍。

模型不听话给了三段时**只取第一段**：契约是一次一段，收下三段会让这条设计在数据
这一侧悄悄失效，而作者以为自己点的是「拆一段」。

### 段号与章号是两条轴

- **段号**（`plots/` 里的文件名前缀）只是**排序键**。`nextPlotNo()` 仍跨
  `plots/` 与 `chapters/` 取最大号 +1，好让新建的段在文件名上排在最后。
- **章号**自己连续排（`nextChapterNo()` = 最大章号 + 1）。读者按章追，章号必须连续。
- 界面上剧情段称「**剧情 N**」，那个 N 是 `segmentDisplayNo(最新章号, 位次)`
  ——最新章号 + 在未交付的段里排第几。

举例。拆出 5 段、一章都还没有：显示剧情 1~5。把第 1 段写完、拆成了 3 章
（第 1~3 章）：那一段从待做列表里消失，剩下 4 段接着往下数——剧情 4~7。
老工程写了 99 章、现在开始规划：第一段就是剧情 100。

于是**拆分不再改任何别的文件**。那次重命名风暴整个消失了。

### 「段 → 章」的链是显式的

`chapters/` 下的文件是作者的东西，拆分之后插件一个字节都不往里改，所以这条链
只能记在段这一侧：`splitManuscript` 把建好的章节路径写进细纲的 frontmatter
（`chapters:`）。

老工程没有这个字段。那时**只对 `plots/` 根下的段**退回同号判定
（`views/pipeline.ts` 的 `chaptersOfSegment`）：本层出现之前一段就是一章、两者
同号，那些工程一个字节都没改就得能继续用。

**兜底只对根下的段生效**是有意的：新口径下段号会与章号撞车（一段拆成三章，
后面的段号不再让路），拿同号去认会把一个刚拆出来的空段误判成「已经交付」——
那一段会从待做列表里凭空消失。根下不会有这种误判，因为分卷之后新建的段都落进
卷目录，`newPlotFlow` 也把手工新建的段放进最后一卷。

### 镜像规则：从「文件名词干」推广到「plots/ 之下的整段路径」

```
plots/01-觉醒之日/007-入宗.md
  → scenes/01-觉醒之日/007-入宗/
  → manuscripts/01-觉醒之日/007-入宗.md
```

未分卷的段（根下那些）镜像出来自然就是扁的，与本层出现之前**完全一致**——所以
老工程一个文件都不用搬。这与「摘要镜像 `chapters/` 下的相对路径、分卷子目录照样
带上」是同一条规则，只是轴换成了 `plots/`。

`kind.ts` 的反推因此按**最后一个** `/` 切（前面全是镜像键，后面是文件名），仍然
零 I/O。

代价：**卷改名要搬三棵目录树**（`plots/` `scenes/` `manuscripts/` 各一棵，卷词干
是三处的第一级目录名）。只搬 `plots/` 那一棵的话，一卷改名之后每一段都会显示
「还没拆场景」，而那些场景就躺在旁边一个孤儿目录里。见
`workspace/handlers/volume.ts` 的 `carryVolumeCompanions`。

### 指纹链多一环，粒度反而变细

```
outline.md ───hash──▶ volumes/*.md      (upstreamHash)
volumes/V.md ─hash──▶ plots/V/*.md      (upstreamHash)
plots/X.md ───hash──▶ scenes/X/*.md     (upstreamHash)
```

从前细纲的上游是全书大纲，于是**改一句立意换来一屏 ⟳**。现在剧情段的上游是
它所属那一卷，改一卷的走向只让那一卷的段标脏。未分卷的段退回全书大纲——它们
本来就是那样记的。

### 界面

工程页多一组「**卷**」，排在章节之前（它是章节的上游，也是拆剧情段唯一的入口）。
**前端复用章节行的组件**，所以 `ProjectVolumeNode` 与 `ProjectPlotNode` 刻意同形
——同一套骨架读两种数据时，字段对不上就得在前端写分支。

「章节」那一组变成一条**时间线**：已发布的章在前，还没交付的剧情段在后，中间
一条虚线分界，那就是「我写到哪了」。两种行的说法完全不同（「第 12 章《夜访》」/
「剧情 4《楼道》」），所以 `label` 由后端给——前端按 `no` 自己拼会把每个剧情段
都叫成「第 N 章」。`PlotSummaryView` 同理多一个 `label` 与 `emptyHint`。

分成两组会让作者在两边之间来回找同一件事（「我写到哪了」），所以合成一列。

## 不改的东西

- **四层装配与提示词的质量来源一个字没动**：`recipes.ts` 里卷借大纲那一张配方，
  三个与卷相关的层在 target 不是某一卷时自然是空的。复制一份出来，下次改大纲层
  的装配策略就会漏掉一边（与 `settle` 只微调既有配方同一条理由）。
- **落盘前必须过一遍人**（第 19 条）：新增的两条路径（拆卷、拆段）走的是同一张
  落盘卡片。
- **老工程不需要迁移**：`volumes/` 是空的、`plots/` 是扁的、段与章同号——三条
  一起构成「纯老口径」，而每一条都单独有兜底。
