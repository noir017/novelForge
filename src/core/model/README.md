# core/model — 数据层

小说工程的数据模型与全部文件读写。所有上层功能（上下文装配、生成、定稿）都通过这一层访问数据，不直接碰磁盘。

核心约定：**数据是工作区里的普通 Markdown / JSON**，作者随时可以在编辑器里手改。因此本层的一切解析都以「容错优先」——手改文件不该让插件崩掉。

## 文件

| 文件 | 职责 |
|---|---|
| [types.ts](types.ts) | 全部数据结构：`Chapter` / `SummaryCast`（定稿过的细纲里的一位出场人物）/ `CharacterCard` / `LoreEntry` / `ProjectManifest` / `NovelConfig`，以及角色卡的**固定小节**定义（`CHARACTER_SECTION_KEYS`）。细纲的八节定义在 plotFile.ts。 |
| [chapterFile.ts](chapterFile.ts) | ★ 「什么文件算章节」的唯一定义：数字前缀 + 扩展名不在二进制黑名单里。纯函数无 I/O，扫描器、编辑器可编辑判定、独立版文件监听三处共用。 |
| [naming.ts](naming.ts) | ★ 称呼学（纯函数、零 I/O）：`isGenericAppellation` 判断一个词是不是泛称（代词、亲属称谓、`少女`/`丫头` 这类谁都能用的词、带修饰语的描述短语），`sanitizeAliases` 据此过滤别名。**只过滤 aliases，绝不过滤 name**——`店小二`、`家老`、`房东` 这类以泛称当正式名的角色确实存在。 |
| [identity.ts](identity.ts) | ★ 同一人聚类（纯函数）：把定稿过的细纲里散落的称呼归并成人。判据是**同章共现作硬约束的贪心聚类**——同一章 cast 里各自出场的两个称呼永不合并，候选链接按「多少章这么写过」计票贪心处理。朴素并查集在这里是错的：一条幻觉别名会顺着传递闭包把主角和她孪生弟弟并成一个人。 |
| [gender.ts](gender.ts) | 角色卡 frontmatter 的 `gender`：`normalizeGender` 把 `male`、`女性` 这类写法收成「男」「女」，「未知」「不详」与空当没写，认不出的照原样留（截 8 字）；`keepGender` 是几条建卡 / 更新路共用的合并口径——**卡上写了的不动**，没写才用模型给的。名字看不出性别时写正文只能猜，这一行跟着名字进上下文（`context/layers/render.ts`）。纯函数、零 import。 |
| [pipeline.ts](pipeline.ts) | ★ **创作流水线的领域模型**：`Stage × Capability × Target` 三元组。四个阶段：架构 / 大纲 / 细纲 / 正文（`setting` 叫「架构」而不叫「设定」，免得与设定条目撞名）；四个能力：讨论 / 生成 / 落定（`settle` 只有细纲层有）/ 审稿（`review`，五期，只有正文层有、不进主按钮；输出形态是第三种 `report`——有结构、要校验，但不是可以落盘的产物）；`CreationTarget` 四种（`setting` 带 `doc`：配置 / 前提 / 角色图谱 / 世界观）与它的稳定字符串键。单章状态机（`deriveStage` / `deriveProgress` / `deriveNextStep`：待写细纲 → 待写正文 → 待定稿 → 已完成；定稿之后正文又改过的回到待定稿）与全书状态机（`deriveBookStage` / `deriveBookNextStep`：架构四件 → 大纲覆盖 → 拆细纲 → 写下一章 → 写完，带章号区间 `range`；拆细纲的区间在第一份已有细纲之前收住），以及 `commandsFor`（`/` 命令面板的命令表）。每一步带 `calls`（`CallEstimate`：通常几次、最多几次，第 4 条），`planPlotBatches` / `planWriteBatch` 给工程页弹窗与后端确认框算同一份批次切分（批量写章：已写跳过、最多 10 章；没细纲但在大纲覆盖之内的章「边写边拆」——排进 `plotBatches`、每批算一份 `blueprintCalls`，超出大纲覆盖才收住；每章多算一份写前冲突检查 `PLOT_CHECK_CALLS`（0–1 次、最多 2 次）；每拆一批细纲、批量拆细纲拆完，各多算一次排叙事线；写完即定稿时全书滚动摘要落后 `GLOBAL_SUMMARY_EVERY` 章就在那一章之后更新一次（`globalSummaryAt`，各 1 次）；两种模式「只写正文 / 写完即定稿」，另可「写完即审稿」——每章多算一份 `REVIEW_CALLS`，五期补遗 §4）；定稿那一步是「定稿第 N 章」，带 `FINALIZE_CALLS`（预计 1–3 次：照正文更新细纲 + 出场角色的当前状态 + 本章推进了哪几条叙事线）；生成小说配置那一步带 `form: 'idea'`（先填一句话与规模）。写正文的三种下一步带 `writeMode`（`WriteMode`：新写 / 接着写（追加）/ 重写（覆盖审阅）；第四种 `revise` 按审稿修稿，只由报告卡发起、永远不是下一步）与 `WRITE_CALLS`（1 次，没写够时自动续写最多再 7 轮，`describeCalls` 把原因接在后面）；`describeWriteLength` 是卡片与气泡共用的「2980 / 3000 字 · 已达标」。审稿与修稿的调用次数是 `REVIEW_CALLS`（1 次，截断或不合格时重来，最多 3 次）与 `REVISE_CALLS`（1 次，被截断时接着写，最多 4 次）。老会话里的 `volume` / `scene` / `split` 由 `normalizeAction` / `normalizeTarget` 容错回落。**纯类型 + 纯函数，零 import**，所以前端可以直接 import 同一份表。读磁盘的聚合器是 [`../views/pipeline.ts`](../views/pipeline.ts)，不要混为一处。 |
| [settingFile.ts](settingFile.ts) | ★ 架构层三份文档的格式：小说配置 `config.md`（frontmatter 是类型 / 受众 / 结构 / 视角 / `totalChapters` / `wordsPerChapter` / `paragraphStyle`，正文八节；**会重写 `config.md` 的路径——生成链的 `mergeWithAuthor`、配置草稿读回来的 `ConfigFields`、`workspace/handlers/setting.ts`——都把 `paragraphStyle` 带过去**，作者在编辑器里切的分段格式不许被一次重写静默丢掉；切换分段格式走 `setConfigParagraphStyle`，只改 frontmatter 的这一行、别的字节一个不动）、故事前提 `premise.md`（四节）、世界观 `world.md`（三节）。`isSettingFilled` 各看主体小节（配置只看「核心梗概」——只写了一句话等于还没展开）；**占位文字读回来就是空串**，免得「（待补充）」被送进 prompt。角色图谱没有自己的文件，就是 `characters/` 那一组卡。文风不在这里，唯一出处是 `style.md`。纯函数无 I/O。 |
| [plotFile.ts](plotFile.ts) | ★ 一章的细纲（`.novelforge/summaries/` 下，**镜像正文在章节根下的相对路径**、扩展名 `.md`：`chapters/第一卷/003-深处.txt` ↔ `summaries/第一卷/003-深处.md`；文件名前缀仍是章号，`parsePlotFileName` 与章节一样认 1–5 位；`global.md` 没有数字前缀，不是细纲）的格式。**写之前是计划，定稿之后是档案，同一份文件**。八节：梗概 / 出场人物 / 时间地点 / 关键事件 / 看点 / 新增伏笔 / 状态变更 / 连续性事实（**关键事件可以写具体场面**；看点写爽点与章末吊着读者的那一下；连续性事实计划时空着、定稿时生成）。frontmatter：`targetWords` / `upstreamHash`（大纲里覆盖本章那一节的指纹）/ `writtenFrom`（正文据以写成的细纲指纹，正文落盘那一步记、定稿时刷新）/ `sourceHash`（定稿时正文的 contentHash，有它就是定稿过）/ `cast`（定稿时记的实际出场，`林昭(阿昭)`）/ `status` / `preflightOk`（一致性预检的永久放行，一行「名字：理由」，五期补遗 §2：按章记；改名、定稿留着，重新生成这一章的细纲就丢掉）/ `factCheckOk: true`（写前冲突检查的放行，作者手写）。`Plot.characters`：定稿过取 `cast` 的名字，没定稿取「出场人物」一节的计划名单（`plannedNames`，**不进出场统计**）。`isPlotFilled` **只认「关键事件」**；`plotContentHash` 只哈希八节，frontmatter 与标题都不进。老工程 `summaries/` 下的单章摘要（含按卷分子目录的）本来就是这八节、本来就镜像正文的路径，直接当定稿过的细纲读（`chapter:` 不认，章号取文件名）。纯函数无 I/O，**只认 `.md` / `.markdown`**。 |
| [outlineFile.ts](outlineFile.ts) | ★ 情节大纲按章号区间切片：认 `## 第a–b章：标题` 等写法（只认阿拉伯数字），一节最多覆盖 `OUTLINE_SECTION_MAX`（5）章——提示词里要求、写完由 `oversizedSections` 查一遍、只记说明不拦（百章实验：一节十章，细纲把同一个高潮反复演）；给出覆盖到第几章（`outlineCoverage`，散文式大纲为 `Infinity`——不拦老工程）、覆盖某一章的那一节（`outlineSliceFor`）与那一节的指纹（`outlineUpstreamHash`，细纲落盘记它、流水线判脏比它，两处同一个函数）。`isOutlineFilled` 不把模板里的 `>` 说明、括号提示、空列表项当内容。`mergeOutline` 把续写的那一段并进旧大纲：只替换与本批区间重叠的节，前言、别的节、附注原样保留。纯函数无 I/O。 |
| [structureGuide.ts](structureGuide.ts) | 故事结构指导：六种结构（三幕 / 英雄之旅 / 节拍表 / 起承转合 / 多线 / 自由）一律按累计百分比切成章号区间——上游 AI-Novel-Writer 的英雄之旅与节拍表只有一行占位，这里补上；章数少于段数时相邻段共用一章，保证连续覆盖全书。纯函数。 |
| [markdown.ts](markdown.ts) | 轻量 Markdown 结构工具：YAML frontmatter 与「## 小节」的解析/序列化，四个 frontmatter 取值兜底（`asString` / `asArray` / `asNumber` / `asNumberArray`），以及 `hasContent`（空白与占位文字不算内容）。刻意不引入 yaml 依赖，解析失败退化为忽略该行而非抛错。 |
| [fs.ts](fs.ts) | 磁盘与字符串小工具：文本读写、稳定哈希、字数统计、文件名清理、slug 生成与扫描目录忽略规则。 |
| [castParse.ts](castParse.ts) | 出场人物字段的序列化、frontmatter 解析，以及没有 `cast` 时从「出场人物」小节文本反解（老工程的摘要、手写的细纲）。 |
| [continuity.ts](continuity.ts) | ★ 细纲最后一节「连续性事实」（四期，D18；定稿时才有）：`- 陈述 〔证据：「原文」〕` 的渲染与读回（手改的写法都认）；定稿时用 bigram 给每条事实在正文里找一句证据（`attachEvidence`，移植 `finalize-chapter.command.ts`，找不到依据的丢掉）；写正文时拿证据原句逐字定位、取所在段落与前后各一段（`locateEvidence`，移植 `adjacentEvidencePassages`）。纯函数、零调用。 |
| [writingSkill.ts](writingSkill.ts) | 写作技能的纯函数（移植自 AI-Novel-Writer 的 `writing-skills.ts`）：读 `SKILL.md`（上游那份手写的 frontmatter 解析，一行一个键）、六条不兼容规则（相对引用 / 脚本 / hook / 子代理 / 工具调用 / 超过 64 KiB）、建议阶段、技能名与 id（`来源:目录名`，名字可以是中文）、绑定文件 `.novelforge/skills.json` 的读写（读不懂不抛，问题记在出事的那个阶段上）、`skillStageOf`（讨论不带；规划 / 写正文 / 审稿 / 修稿）、注入那一块的说法、GitHub 地址。**零运行时 import**，前端直接用阶段名与来源名。 |
| [importText.ts](importText.ts) | 拆书的纯函数（导入原稿、从参考书学写法共用）：字节解码（BOM → UTF-8 严格解 → GB18030）、认章标题（`第X章/回/节`、`Chapter N`、序章楔子番外；`第X卷` 是卷标题，丢掉；超长或以句末标点收尾的是正文）、切章（简介、卷标题、目录里的空标题不算章，段落规整成一段一行）、没有标题时按字数切段、均匀抽样与看结构的那几章、头尾节选、篇幅统计、规模缺省（平均字数、总章数）、参考书写法技能的名字与 `SKILL.md`。**零 I/O、绝不抛** |
| [threadsFile.ts](threadsFile.ts) | ★ 叙事线 `threads.md`（七期，移植 AI-Novel-Writer 的 `narrative-thread.ts`）：一个 `## 名字` 一条线，类型 / 计划（第 a 章埋、第 b 章前收）/ 意图 / 事件行（`第 N 章 · 埋下|推进|回收|放弃：「原文」——理由`），手改的几种写法都认、认不出的行跳过。**状态不落盘**，取章号最大的事件；`asOf` 只留第 N 章之前的事件（重写前面的章时不透后面的事）。写入只有两个外科式的追加（`appendThreads` 在末尾加线、`appendEvents` 在一条线的事件末尾加行），作者写的字、BOM、CRLF 原样保留。`pickActiveThreads` 定写正文时带哪几条（细纲提到 → 区间内 → 已过回收章 → 已埋下 → 人物对上；6 条、1200 字——缺省那一级，条数与字数随上下文详细度，放不下的跳过接着试）；`verifyThreadPlans` / `verifyThreadEvents` 校验模型的输出（先校验后截；证据按 `review.ts` 的归一化逐字找、至少 4 个字）。纯函数无 I/O。 |

## 关键设计

- **每次读盘，不缓存正文**：`read*` 方法每次调用都重新读文件（作者可能刚手改完），只有章节列表做一层缓存，由 FileSystemWatcher 主动失效。
- **目录是任意深度的**：`chapters/`、`characters/`、`lore/` 都递归扫描，作者可以按卷、按阵营分子目录整理（`summaries/` 也递归扫：细纲跟着正文的子目录走）。隐藏目录（含 `.trash/`）与 `node_modules` 一律跳过，深度上限 8 层。
- **章节认任意扩展名，角色/设定只认 `.md`**：章节的判定在 `chapterFile.ts`——数字前缀 + 非二进制扩展名，所以 `001-楔子.txt`、`001-楔子`（无扩展名）、`004.json` 都是章节，`001-封面.png` 不是。角色卡与设定条目是插件自己的数据格式（frontmatter + 固定小节），不跟着放宽；`listFilesDeep` 收 accept 回调，两类各传各的。
- **顺序只看序号，一条轴**：章节顺序由文件名数字前缀决定，与所在层级无关；`卷一/003-x.md` 与 `003-x.md` 都是「第 3 章」。细纲号就是章号，但配对按路径：有正文的章只认正文镜像的那份细纲（`NovelProject.plotFor`），还没有正文的章按号认计划。序号撞车时两条都留在树上，让作者看见冲突，流水线认路径排序第一份正文。
- **只有 markdown 家族解析 H1**：`.md`/`.markdown` 的章节标题取自正文首行的 `# 标题`（`readChapterText` 会剥掉），其余格式一律取文件名、正文一个字节不动。`extractH1` 与 `stripH1` **都只看首行、互为逆运算**——早先 `extractH1` 带 `m` 标志扫全文，会把 `.txt` 正文中段的一行 `# xxx` 认成标题却不剥掉它。改这两个函数时务必保持互逆。（副作用：角色卡/设定条目里 `# 名字` 不在首行时，标题现在回落 `frontmatter.name` → 文件名。）
- **草稿与细纲都按章节路径镜像**：`chapters/第一卷/012-夜入.txt` → `drafts/第一卷/012-夜入.txt`（文件名原样）、`.novelforge/summaries/第一卷/012-夜入.md`（扩展名换成 `.md`），不落索引——没有索引就没有会漂移的第二份真相。章节（文件或整个卷目录）经网关改名/移动时草稿与细纲跟着搬（`workspace/handlers/chapter.ts` 的 `carryDraft` / `carryPlot`；移出 `chapters/` 就留在原处），删章节两样都不删（第 10 条；细纲退回这一章的计划）；在外面直接给正文改名，旧细纲不被新路径冒认（那是一章新的）。细纲改名改的是标题：没有正文时文件名跟着标题，有正文时文件名跟着正文不动；正文从不跟着细纲改名（作者的文件）。照细纲新写正文时正文落在细纲所在的子目录，纯序号的细纲（`030.md`）配上有标题的正文会跟着改名（`Workspace.createChapterAt`）。目标已存在时**不动**（不静默覆盖）。
- **`deletePlot` 不碰 `chapters/`**：删细纲只是放弃这一章的规划稿（定稿过的连同档案一起进回收站），正文是作者的东西，不该被顺手带走。
- **新建只出序号名**：`writePlot` / `createChapter` 的 `title` 允许为空，那时落成 `007.md` 且不写 H1——手工新建一章时还没有标题可言，凭空塞一个「第7章」进文件名只是个假标题，而它会进上下文。为此有个 `safeStem`：**空标题给空串，不给 `sanitizeFileName` 的兜底名「未命名」**，否则会得到 `007-未命名.md`。标题回落链（`extractH1` → 文件名词干 → `第 N 章`）本来就认这种名；界面上的说法统一走 `pipeline.ts` 的 `chapterLabel`，未命名时只报序号。写 H1 时用的是**清洗后的词干**而不是原样 `title`，两者一致，改名时 `renamedBody` 才认得出「这个 H1 是跟着文件名走的」。
- **正文依据的细纲指纹记在细纲上**：章节可以是 `.txt` / 无扩展名 / `.json`，是作者的东西、没有 frontmatter，所以「这份正文依据的是哪一版细纲」记在细纲自己的 frontmatter（`writtenFrom`），由正文落盘那一步写（`workspace.recordWrittenFrom`），定稿时刷成反向更新之后的指纹——之后再改细纲，正文才挂 ⟳。定稿时正文的 `contentHash` 记在同一份 frontmatter 的 `sourceHash` 上。从没记过（作者手写的正文）就永不标脏。老工程 `manuscripts/` 里的中转站正文、`plots/` 里的老细纲一个字节都不动，代码不再读。
- **草稿是纯推导出来的**：`draftRelPathFor` 把章节在**章节根之下**的那段相对路径镜像到 `draftsDir` 下，文件名含扩展名原样沿用。`ensureDraft` 按需创建、已存在原样返回（不静默覆盖）；`listDraftPaths` 一次遍历给出全部已存在的草稿，供工程页与 `@` 引用共用（每章一次 stat 会把工程页刷新的 syscall 翻一倍）。`draftsDir` 是 `chaptersDir` 的兄弟目录、不从它派生，因此改 `chaptersDir` 不影响草稿落点；`chapterSkipDirs()` 兜住 `chaptersDir` 被配成 `.` 的极端情况。
- **出场人物只认定稿过的细纲**：有 `sourceHash` 的细纲，它的 `cast` 是**实际出场**，也是唯一的真相（AGENTS.md 第 14 条）。没定稿的细纲里「出场人物」一节是**计划**出场：只给装配器挑角色卡（`context/layers/render.ts` 的 `selectCharacters`）、算「后几章才出场的人」与一致性预检用，不进 `castIndex`——混进去会污染出场章统计与角色卡语料（D13）。
- **角色/设定的 slug 是路径**：根目录下的文件 slug 就是文件名（与改造前一致），子目录里的形如 `主角/林昭`——上下文明细里的 `character:<slug>` 因此仍然唯一。
- **定稿对不对得上按章算**：`chapters/` 里的成品写盘后重算 `contentHash`，与正文镜像那份细纲 frontmatter 里的 `sourceHash` 比对（`finalizedPlotOf`），不一致就回到待定稿。**空章不算没定稿**——没有正文就无从定稿，混进来会让同步细纲的确认框报一个虚高的调用次数。不自动重新定稿，只提示。manifest 只是章节索引，不记任何定稿的账。
- **出场人物有两种形态，一份信息**：定稿过的细纲 frontmatter 的 `cast: [林昭, 年轻守卫(那个年轻人)]` 给程序用（角色页聚合、角色卡关联），`## 出场人物` 小节给人看。定稿时从结构化 cast 渲染出小节，保证两者一致；**读的时候以 frontmatter 为准，字段缺席才从小节文本反解**（见 [castParse.ts](castParse.ts) 的 `castFromText`）——老工程的摘要与作者手写的细纲没有这个字段，不该因此在角色页上凭空少一批人。用括号而不是嵌套 YAML 是因为本层的 frontmatter 解析器刻意只支持字符串与字符串数组，为一个字段引入真正的 yaml 依赖不值得，而括号形式作者也能直接手改。
  `castFromText` 的两条判据（名字 ≤ 8 字、不含「的了是在不没」这类虚词）是为了挡住模型把这一节写成句子的情况——按标点切开会得到一串句子碎片，全都会跑进角色页的「未建卡」组里。宁可漏掉一两个长称呼，也不能让那一组塞满垃圾；漏掉的重新定稿就有了（定稿走结构化 cast，根本不经过这个函数）。计划名单（`plannedNames`）不套这两条：那是作者与排细纲的模型写的名单，「沈从文」不该因为带个「从」就漏掉。
- **角色卡的 `stateThrough` / `stateHash` 是「当前状态」的归属账**（四期，D15）：前者是这一节写到第几章（0 = 开篇，角色图谱建卡时写的），后者是机器最后一次写它时的指纹。`renderCharacterCard` 原样带着它们走——清理别名、合并重复卡这些维护动作不重新盖章，作者改过的那一节不会因为换了个别名就变成「机器写的」。
- **角色卡的 `appearsIn` / `updatedThrough` 是缓存**：前者是该角色出场的章号，后者是上次「更新角色卡」读到了第几章（增量更新的依据）。真相永远是各章定稿过的细纲，落在卡里只为两件事——不读全部细纲就能在角色页显示「出场 12 章」，以及日后按人物检索章节。
- **会话用 JSON 而不是 Markdown**：会话是机器记录（含 token 明细、附件快照），不期待人工编写，但仍是纯文本、可 Git。
- **选区引用存快照**：`Attachment.text` 对 selection 存当时的快照，历史对话不因原文修改而变；整文件引用每次读盘取最新。

## 依赖关系

本层只依赖 Node API 与 core 内更底层模块；`context/`、`features/`、`llm/` 依赖本层，反向不允许。
