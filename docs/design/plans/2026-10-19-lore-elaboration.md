一句话方案：**单条设定可以当生成目标（展开），讨论结论可以落定成一批条目（落定设定），名录指出接下来几章要用、却还是空的设定（待完善）；条目多一节「暗设」，规划时看得见、写正文时看不见。**

## 数据格式

### 条目多一节「暗设」

```markdown
## 概要
## 规则与边界
## 现状
## 暗设
```

- 可选的第四节：读者还不知道的真相——真实身份、来历、规则背后的真正原因。**≤200 字，不算进明面的 600**（`LORE_ENTRY_LIMITS` 加 `暗设: 200`，`body: 600` 仍指前三节）。
- **认法**：以「暗设」开头的二级标题（`## 暗设`、`## 暗设（未揭示）` 都认），到下一个二级标题或文末为止。纯函数 `splitLoreHidden(body) → { visible, hidden }` 放 `model/loreFile.ts`。作者写成别的标题就当明面（第 1 条：认不出就照常读）。
- **谁看得见**：

  | 场合 | 带不带暗设 |
  |---|---|
  | 设定 / 大纲 / 细纲阶段（讨论、生成、落定） | 带，标明「暗设（读者还不知道）」 |
  | 正文阶段（写、接着写、重写、讨论正文）与续写 | **不带**，明细里注一句（第 2 条） |
  | 正文阶段 @ 引用一条设定 | **不带**，明细里注一句；要让正文知道，就写进这一章细纲 |
  | 审稿、修稿 | 这两张配方本来就不带设定（`recipes.ts:217-267`） |
  | 展开、整合、落定设定 | 带（要改的就是它） |
  | 一行（`brief`） | 提示词不许把暗设写进一句话；缺 `brief` 时取正文第一句（`loreBrief`，`loreFile.ts:161-175`）跳过暗设那一节 |
  | 定稿 / 记设定的 `loreHint` | 只给标题、分类、关键词（`loreRecord.ts:59-67`），不碰正文；提示词不许把暗设里的东西写进关键词 |
  | MCP `read` | 原文——外部 agent 是调度者，不是写正文的那个模型（第 24 条） |

- **揭开靠细纲**：细纲阶段的提示词加一条——暗设是读者还不知道的事，这一章不打算揭开，就别写进梗概、关键事件、看点；要铺垫就写进「新增伏笔」，只写读者看得到的那一面；打算揭开，就在关键事件里写明「揭开：……」。细纲进正文的上下文，揭开那一章的正文模型从细纲知道这件事。
- **整合**：`LORE_ENTRY_SYSTEM` 加一条——记录表明正文已经揭开了暗设里的某件事，就把它挪进前三节、从暗设里删掉；没揭开的原样保留（那是作者的计划，正文没推翻）。
- 全书查找替换保护的标题（`model/bookFind.ts:66`）加「暗设」。
- **为什么不学叙事线「带上，注明别揭开」**：叙事线一条一句、有明确的揭开章号；条目的暗设没有章号，和明面混在同一条里整条带，正文模型看见就容易说漏。写正文本来也不需要知道真相——需要的铺垫，细纲里已经写了。

### 薄条目怎么认

`loreThin(entry)`（`model/loreFile.ts`，纯函数），下列任一就算「还只有一句话」：

- 明面正文（去掉暗设）是空的；
- 是「新建设定」留下的占位（以「（在这里写这条设定」开头，`features/characters.ts:345`）；
- 三节都只写着「（未交代）」。

不按字数猜——作者写了两行就是作者认为够了。`hasContent`（`model/markdown.ts:304-307`）只认「（待补充）」，不动它。

## 1. 展开一条设定（一期，1 次）

### 生成目标

- 新增目标 **`{ kind: 'lore'; relPath }`**，阶段是 `setting`。照细纲 `plotRelPath` 的路子：目标自己带着文件身份。
- **不复用** `{ kind: 'setting', doc: 'lore' }` 加一个路径：凡是 `doc === 'lore'` 的分支都会走设定清单那条链（`structured.ts:599-614`、`prompts.ts:690-692`、`artifact.ts:137`），`targetKey` 会把单条和整批当成同一个目标，`normalizeTarget` 会丢掉多出的字段——随会话存下的草稿重开后会被当成整批清单采纳（`model/session.ts:620`）。
- `kindOfPath` 的设定分支给出 `stage: 'setting'`、`target: { kind: 'lore', relPath }`（`kind.ts:216-219`），MCP 的 `generate` 不用特判就认条目路径。
- 要改的地方：穷举 switch 编译器会抓（`targetKey`、`describeTarget`、`pathOfTarget`、`targetHasContent`、`normalizeTarget`）；**要人工逐处查的是「不是 setting 就当 config」的那些**（`artifact.ts:133`、`prompts.ts:176` / `:683`、`background.ts:131-134`、`focus.ts:98`、`builder.ts:309`、`views/workbench.ts:59`、`views/stateBrief.ts:84`、`media/src/view/pipeline.ts:131`、`media/src/view/project/nextSteps.ts:106`；动手前 grep `kind === 'setting'` 全部过一遍）。
- 这个目标上的能力：讨论（聊这一条）与生成（展开，界面叫「展开这条设定」）。

### 喂什么

| 优先 | 内容 |
|---|---|
| P0 | 配置、前提、世界观；这一条现有的全部内容（含暗设）；作者这次的话（可以空） |
| P1 | **已排细纲里用到它的地方**：没定稿的细纲第九节点名它的那一行，以及梗概、关键事件里提到它（标题或关键词）的句子，带章号——展开是为这些情节服务的 |
| P1 | **定稿过的记录**：与建条目、整合同一份（`recordsAbout`，`features/lore.ts:95-123`）——已经写进正文的，不能推翻 |
| P2 | 相关条目：同目录的、关键词在本条或上面那些句子里命中的，整条 / 一行照 lore 层的规矩封顶；角色一行一人 |

细纲与定稿记录合计照整合的 `MATERIAL_TOKENS` 封顶，放不下的进明细（第 2 条）。

### 合同（新写一份，不借 `LORE_ENTRY_SYSTEM`）

```json
{
  "brief": "…",
  "keywords": ["…"],
  "body": { "概要": "…", "规则与边界": "…", "现状": "…", "暗设": "…" },
  "children": [{ "name": "…", "category": "…", "brief": "…" }],
  "questions": ["…"]
}
```

1. **为已排的情节服务**：细纲里打算让它做什么，它就得撑得住；和剧情无关的百科不写。
2. **定稿记录里已经确立的不许改**；作者现有的内容是作者认过的，没理由不删，只补、只细化。
3. 字数上限同第 27 条；暗设 ≤200 字，没有就给空。
4. 关键词 3–8 个，只放读者会看到的叫法；人名不算；暗设里的东西不进关键词、不进一句话。
5. `children`：写不下、值得单独一条的部分，≤3 条，只给名字、分类、一句话。
6. `questions`：2–5 条还没定、要作者拍板的问题（「阁规是成文的还是口传的？」），不问已经定了的。

程序校验（不加调用）：一句话截 40 字；四节按上限截（同 `normalizeLoreBody` 的做法）；新关键词过 `cleanLoreKeywords`；`children` 里名字已有条目的、是人名的、重名的丢掉；`questions` 最多 5 条、每条 ≤60 字。**解析不了就报失败、不给写入**，不做全文兜底——条目被一段没解析开的原文盖掉，比没写更糟（同定稿）。

### 落盘

- 新增产物 **`loreEntries`**（展开与落定设定共用）：`{ entries: LoreDraft[], questions: string[] }`。展开时 `entries[0]` 是目标条目，**按 `relPath` 认、不按标题**（展开不改名），其余是 `children`（正文空）。
- 目标条目：
  - 明面正文是空的、是占位 → 直接写；其余走覆盖审阅 diff（第 3 条）。
  - 关键词只增不减；一句话新的优先；正文整份换成展开后的。
  - `bodyHash` = 新正文的指纹，记作机器写的（定案 4）。
  - 水位与整合同一个算法（`integrationWatermark`，`lore.ts:67-81`）：展开喂的定稿记录就是整合会喂的那一份，写完 `＋N` 也就收了。
- `children`：随卡片一起建空条目（与细纲带出新设定同一个第 19 条例外），卡片上列「会新建设定条目：……」（`plannedLore` 扩到 `loreEntries`）。
- `questions`：**只上卡片**。`SerializedArtifact` 加一个字段，`artifactDetail`（`controller/chat.ts:634-656`）加一行「还没定的：……」；落盘时拿气泡文本重新解析（`chat.ts:601-602`），这个字段不写进任何文件。没采纳的那一轮留在历史里（`dialog.ts:138-142`），作者接着回答就行。
