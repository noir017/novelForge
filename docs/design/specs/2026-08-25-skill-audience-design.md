# 技能的两种受众：给 agent，还是给创作模型

**一句话**：把技能按**写给谁读的**分成两类——`agent` 类由 agent 自己读，`generate` 类由 agent 点名、正文直接进**创作模型**的上下文，一个字都不进 agent 的每一轮。

## 为什么要分这一刀

[2026-08-22 那份设计](2026-08-22-agent-skills-design.md)把技能定成「给 agent 的工作流说明」，并明确写着方法论不进 `context/prompts.ts`——那是被调用的模型每次生成都要读的，占的是作者的 token 预算。

那一刀切得对，但**它假设了所有方法论都是给 agent 的**。实际写下来，方法论有两种：

| | 例 | 它要在什么时候生效 |
|---|---|---|
| **动作** | 跨章核对伏笔：搜哪几个词、按章号排、结论落到哪个文件 | agent 调工具的时候 |
| **写法** | 章尾钩子怎么选、AI 味的句式怎么改、这一类题材的套路是什么 | **落笔那一刻** |

第二种塞给 agent 是错位的。它手上有八个工具，但「别写『眼中闪过一丝』」不是一个工具能执行的东西——agent 拿到这几千字，能做的**只是转述一遍给创作模型**，于是同一份内容付两遍钱，而且转述必然有损。

该读它的是真正在写的那个模型。

## 受众写在 frontmatter，不是配置

`audience: agent | generate`，缺省 `agent`。

它与档位（`skillModes`）是两件独立的事：

- **档位是作者按成本做的选择**——这一份占不占我每一轮的预算。所以它在配置里。
- **受众是技能本身的属性**——「去 AI 味」在任何工程里都是给创作模型的写法。所以它跟着 `SKILL.md` 走。

前一版写着「不解析 frontmatter，因为索引只列名字」，后来「完整」那一档给了 `description` 一个消费者，于是开始解析它。`audience` 是同一条路径的延伸，而且它**必须解析**：索引要按受众分两段，不知道受众就分不出这一刀。

### 代价：工程技能每一份都要读一次文件头

`description` 从前只在「完整」那一档读盘，缺省全是「仅用户」时一次盘都不读——「索引零文件读取」成立。受众打破了它。

代价压在两处：**只读前 4 KiB**（frontmatter 在最开头），**只有工程技能要读**（内置那一半在构建时就读好了，而绝大多数工程一份自己的技能都没有，那时这一趟根本不跑）。

## 索引分两段

```
# 可用技能                        ← agent 类，按档位
- builtin:foreshadowing-audit

# 可交给创作模型的写作方法          ← generate 类，名字 + 描述
- project:去AI味 —— 写正文时避开 AI 腔……
```

合成一段的话，agent 会拿 `skill` 去读第二类——那正是这一刀要避免的事。所以两段分开，各自把用法写在段首；`skill` 工具遇到第二类的名字时**拒绝并指路**（「调 generate，把它填进 `skills` 参数」），而不是回一句「没有叫 X 的技能」——后者会让它照着索引里明明列着的名字反复再试。

### 两段进索引的判据不同

`agent` 类沿用 `isAgentVisible`（只有「仅标题」/「完整」在）。`generate` 类**只认「禁用」**：它的正文本来就不进 agent 的上下文，索引里那一行是名字加一句描述；而**少了那一行 agent 永远不会把它带给 `generate`**——「仅用户」在那一类上等于装了却关掉。

所以 `generate` 类只有两种状态，设置页在那几行只给「启用 / 禁用」两项。

**这一类必须写 `description`**：正文 agent 读不到，名字只有几个字，那一行是它判断「什么时候该带上」的唯一依据。

## 正文怎么进创作上下文

`generate` 工具加一个 `skills` 参数（字符串数组），走的是既有的分层装配：

```
generate(job, target, skills: ["project:去AI味"])
  → 工具层读正文、校验名字        ← 名字错了在这里整次拒绝
  → BuildRequest.skills
  → context/layers/skills.ts     ← 新的一层
  → 「# 写作方法」段，挨着文风指南
```

**正文在工具层读，不在装配层读**，两条理由：名字错了要在**花钱之前**就回给 agent 一句话（到了装配器这一次生成已经开始了）；`context/` 不该 import 一个会拖进 `node:fs` 与烘出来的常量的模块。

四张配方都带这一层，位置在每张的 **P0 force 那一批之后**——那几层是这一次真正要动的产物（本层产物、文风指南、上一章结尾）。方法缺席只是写得平庸，产物缺席这一次生成直接是错的。

**装不下就整份丢，不截断**（cap 0.35，与附件同一个数）。照着半套流程写完比没有更糟；附件那一层超了就截，因为半份材料仍然是材料，方法论不是。丢掉这件事留在上下文明细里，作者看得见。

## 作者那一侧

`generate` 类一样能用 `/` 呼出。区别在折进那句话的是什么：

| 受众 | 折进去的 |
|---|---|
| `agent` | 整份正文（那一档 agent 连名字都没见过，递个名字过去是一次白花的往返） |
| `generate` | **一句指令**——「这一轮每次 generate 都把这几个名字填进 `skills`」 |

折正文进来的话，agent 能做的也只是转述一遍，两头都付钱。

## 明确不做

- **`generate` 类不支持 `references/`。** 创作模型没有工具，`generate` 只注入 `SKILL.md` 正文。所以这一类**必须自足**，而且要控制在几千字——它是整份注入每一次生成的。
- **不做模糊匹配**（沿用上一版）。猜错时创作模型会拿到一份没人想要的写法，而且谁都不会知道。
- **名字对不上不静默丢弃**，整次拒绝。agent 是刻意点名的，默默不带等于让作者付了钱却没用上他要的写法。
- **不给 `generate` 类做「按层自动带」。** 哪一层该带哪一份由 agent 按这一次产出什么判断（描述里写着「写正文时带上」）。做成配置表等于让作者替模型预判每一种组合。
