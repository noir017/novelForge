# core/context — 上下文装配

插件的核心。在有限 token 预算内，把「文风指南 + 全书摘要 + 相关角色卡 + 本层产物 + 近章原文 + 会话历史 + 用户引用」按优先级装配成一次请求的消息序列，并如实记录装了什么、丢了什么。

## 文件

| 文件 | 职责 |
|---|---|
| [tokenCounter.ts](tokenCounter.ts) | ★ `TokenCounter` 接口 + 注册表 + 默认的字符加权实现（中文 ≈ 1.5 token/字，拉丁 ≈ 1/4）。另含真实用量的校准统计。 |
| [tokenizer.ts](tokenizer.ts) | 门面：`estimateTokens`（= `countTokens`）与按预算截取的 `takeHead` / `takeTail`。全仓库几十处调用点都走这里。 |
| [types.ts](types.ts) | `BuildRequest` / `BuiltContext` / `ContextItem` / `LayerId` / `LayerSpec`。单独成文件是为了打断 recipes 与 layers 的循环引用。 |
| [recipes.ts](recipes.ts) | ★ 四个阶段（架构 / 大纲 / 细纲 / 正文）各带哪些层、优先级多少。**改装配策略只改这一张表。** |
| [layers/](layers/index.ts) | ★ 每一层的取数与注入，外加 `resolveFocus`（按配方只读用得上的文件）。`LAYERS` 注册表在 index，实现按 dialog / artifacts / background 拆开。 |
| [prompts.ts](prompts.ts) | ★ 身份（Stage）× 任务（Capability）× 输出契约。架构、大纲、细纲批次与正文的契约移植自 AI-Novel-Writer（GPL-3.0，源自 AI_NovelGenerator），逐段注明出处：正文分第 1 章「黄金第一章」与后续章「连载更新法则」两套，系统提示里有 D8 去 AI 味四条禁令，契约末尾是篇幅合同（±20%）与执行卡（必需事件 / 章节钩子 / 作者本章指导）。另有生成链要用的语法修复、「全局要求」字段重写两条消息。 |
| [replay.ts](replay.ts) | 重演检测（纯函数）：上一章结尾约 1000 字与新稿前 1200 字各自归一，按 8 字 n-gram 比对，**连续覆盖 ≥ 80 字**算重演，报出新稿里那一段原文。移植自上游 `hasSubstantialPreviousChapterReuse`；拒不拒收不在这里决定（卡片标红、写入点两下）。 |
| [builder.ts](builder.ts) | ★ `buildContext()`：算预算 → 按配方跑一遍层 → 拼 messages。 |

## Token 计数是可替换的

改造前 `estimateTokens` 是一个写死的函数，想换更准的算法得改遍全仓库。现在分三层：

1. **`TokenCounter` 接口**——`count(text)` 数 token、`charsFor(tokens)` 反推字符数（截断要用），可选 `prepare()` 供需要加载 wasm/词表的实现。
2. **注册表**——`registerTokenCounter()` 注册、`useTokenCounter(id)` 切换。切换失败（未注册、`prepare()` 抛错）时**保持原计数器并返回 false**，绝不让「数不了 token」把写作流程带停。
3. **`HeuristicTokenCounter`**——默认实现，就是原来那套系数，零依赖、同步、永不失败。它是所有降级路径的终点。

要接 tiktoken 或服务商的 count_tokens 接口，写一个实现注册进去即可，`builder.ts` 一行都不用改。

**校准回路**：服务商返回真实用量时（`usage` 事件 → `collect` 的 `onUsage` → `recordUsage`）记下「估算/实测」比值，`usageStats()` 可查。它**只用于日志与展示，不自动修正估算值**——估算必须是纯函数，否则同一份上下文两次装配会得出不同的预算判断，「不静默截断」的明细也就不可复现了。没给 usage 的服务商什么都不记，不拿估算冒充实测。

## 分阶段装配

一次装配由 `BuildRequest.action.stage` 决定带什么。四张配方在 [recipes.ts](recipes.ts) 里，**顺序即填充顺序**：

| 阶段 | 身份 | 带什么 | 明确不带 |
|---|---|---|---|
| **架构** | 网文策划编辑 | **架构三件（配置 / 前提 / 世界观，P0 force）**、角色图谱一览（P0）、已有角色卡（P1） | 正文原文、大纲 |
| **大纲** | 策划编辑 | **架构三件 + 角色图谱一览 + 故事结构指导 + 大纲全文（都是 P0 force）**、角色卡、全书摘要、各章摘要 | 正文原文 |
| **细纲** | 剧情编剧 | 本章细纲（单章时，P0 force）、**架构三件 + 角色图谱一览 + 大纲里覆盖这几章的那几节（P0 force）**、前 3 章与后 1 章的细纲、前序细纲一览（最近 100 章）、结构指导、更早章的正文摘要 | 正文原文 |
| **正文** | 作者 | **文风指南、全局要求、本章细纲、上一章结尾（不许重演）、后 5 章细纲（边界）、本章已写末尾（接着写时）、上一版（重写时），都是 P0 force**；出场角色卡、架构三件（除全局要求）、大纲里本章那一节（P1）；全书摘要、设定（P2）；近 2 章正文（P3）；更早章的摘要（P4） | —— |

四张都按 [总计划](../../../docs/design/plans/2026-09-30-blueprint-pipeline-roadmap.md) §2.3 排：前三张二期，正文那一张三期（移植自 AI-Novel-Writer 的 `next_chapter_draft` 材料包）。**执行卡与篇幅合同不是层**，由输出契约拼在消息最末（上游 GD:657 的顺序）。

**正文续写那几轮**（`step.kind === 'continuation'`，generation/continuation.ts）换一张精简配方：系统提示、这一轮的话、文风、全局要求、本章细纲、后 5 章边界、本章已写末尾、出场角色。前情摘要与前几章全文第一次调用已经用过，每一轮都付一次全价不值。

三期加的四层：

| 层 | 注入什么 |
|---|---|
| `guidance` | 小说配置的「全局要求」一节，单独成段（`# 全局要求（每一章都要遵守）`） |
| `premiseWorld` | 小说配置（**除全局要求**，不重复带）、故事前提、世界观，一件一条 |
| `plotAhead` | 后 5 章的细纲一章一行（标题 + 关键事件前 300 字），标「绝对不要在本章提前写出」。**按章号窗口取**（N+1..N+5，上游 GD:464-466），只带排过的 |
| `chapterSoFar` | 本章已写正文的最后 1600 字：「接着写」读磁盘，续写那几轮由生成链给（含这一次刚写、还没落盘的） |

「接着写」时不带上一章结尾：这一章的开头早就从那里接过了，两个「从这里接下去」摆在一起，模型会跳回上一章去。

**细纲批次**（请求带 `range`）与单章共用细纲那张配方：批次没有「本章」，`plotSelf` / `plotPrev` 不出场，由前序细纲一览全包（最后三章带章末钩子）；前文的边界是区间第一章，后文从区间最后一章之后算起。生成链拆半重试时，前一半刚排好、还没落盘的那几章经 `draftPlots` 接在一览最后。

二期加的四层：

| 层 | 注入什么 |
|---|---|
| `structure` | 按总章数算好章号区间的故事结构指导（六种结构都有区间，见 `model/structureGuide.ts`），并点明本批落在哪几段。没写总章数时不带，明细里说原因 |
| `rosterDoc` | 角色图谱一览：全部角色卡压成一人一段（身份、人物关系、当前状态的开头） |
| `outlineSlice` | 大纲里覆盖本章 / 本批的那几节；大纲没有区间标题时退回全文并说明 |
| `plotList` | 前序细纲一览，一章一行 |

几处刻意的抬高（表里加粗的几条）：

- **正文阶段文风指南升到 P0 force**。它是「读者感觉不到换人执笔」的唯一保障，不该跟一段长对话抢预算——改之前它在 P1，一段长对话（封顶 30%）加几张角色卡就能把它挤掉。
- **正文阶段本章细纲也升到 P0 force**。细纲**就是**写正文的依据：少了它，模型手上只有文风与前文尾巴，会自己编一章出来。
- **正文阶段后 5 章细纲也是 P0 force**。那是边界：没有它，模型写到钩子时最顺手的就是把下一章的事提前演掉，下一章于是无事可写。
- **架构与大纲两层的架构三件是 P0 force**。四件一件吃一件：前提照着配置写、世界观照着前提与角色写，少了上一件，这一件就是凭空编的。
- **`settle`（落定细纲）时历史 cap 从 30% 抬到 60%、优先级提到 P0**（`recipeFor(stage, capability)` 唯一一处按能力改配方的地方）。这条命令要沉淀的就是那段讨论，按常规由远及近截掉等于把结论截没了。

**细纲阶段带前后文而不是只带上一章**：前 3 章的细纲（关键事件 + 章末钩子）让这一章接得上，后 1 章（本章目的 + 关键事件）让它不至于把下一章要用的东西提前用掉，更早的章以正文摘要形式带。**还没写正文的早期章带不出摘要，退化成只带「本章目的」一行**并 `accept(..., 'degraded', '这一章还没写正文，只带本章目的')`——不是悄悄少带（AGENTS.md 第 2 条）。

**挑角色卡**：`selectCharacters` 第一优先是本章细纲的 `characters[]`（计划出场，D13——只在这里用，不进出场统计），其后是这一轮输入里提到的、前两章摘要里出场的与主角。

**前三个阶段都不带正文原文**：讨论故事结构或剧情走向时读三段正文既没用又昂贵，一段三千字 × 近三段，够装下整本书的摘要还有富余。

## 预算与降级

| 优先级 | 预算不足时 |
|---|---|
| P0 · force | 永远保留（系统提示、用户这一句、本层产物） |
| 用户 @ 的引用 | 单条封顶预算 35%，超出从头部截断而非丢弃 |
| 会话历史 | 整体封顶 30%（`settle` 时 60%）、单轮 12%，由近及远保留，更早的整轮丢弃 |
| 角色卡 | 降级为「身份 + 当前状态 + 未收伏笔」三节 |
| 某章正文 | 降级为该章摘要 → 丢弃 |
| 更早章的摘要 | 由近及远填充，填满即止 |

预算 = `contextWindow - maxOutputTokens - 512`，并与 provider 的 `maxInputTokens` 取小。

## 关键设计

- **不静默截断**：每条 `ContextItem` 带 `status`（included / degraded / dropped / excluded）与人类可读的 `note`，前端折叠展示。作者随时知道这次没带上什么。
- **层与配方分离**：「带什么」在 recipes、「怎么取」在 layers。让剧情阶段不带正文原文是配方里少写一行，不是装配器里多一个 if。
- **只读用得上的文件**：`resolveFocus` 按配方决定读不读前后章的细纲。正文阶段每次生成都多读三章用不上的细纲，那是落在关键路径上的浪费。
- **引用在 P0**：用户特意 @ 的内容不该被自动装配挤掉。
- **历史是多轮消息**：会话历史按 role 交替作为真正消息发出，不是塞一段「以下是之前的对话」；单轮过长取结尾（越靠后越接近当前进度）。
- **去重**：上一章正文能完整放下时，P0 的结尾片段自动撤掉，同一段文字不在 prompt 里出现两次。`manuscriptFull` **只认领它确实注入了的章**——认领了却没注入的话，摘要那一层会跳过它，于是它从上下文里凭空消失，而明细上还看不出少了什么。
- **正文只读 `chapters/`**：一章一纲之后正文只在一处，从前还要回落到中转站 `manuscripts/`。只有 `chapters/` 的老工程一样带得出前文。
- **讨论型能力禁止改写产物**：`outputKindOf(action) === 'text'` 时系统提示里明写「只回答，不要输出改写后的完整产物」。少了这一条，模型会一边回答一边把整份剧情细纲重写一遍，而界面上那一版是不能采纳的。
- **细纲可以写具体场面，但不是正文**：从前细纲被禁止写画面与动作、只许写抽象的因果链，模型拿它去「扩写」出来的是流水账。现在「关键事件」100–300 字、可以写到具体场面，「章末钩子」必填；不写成段的描写与对白。单章与批次用同一份蓝图合同（`{"blueprints":[…]}`，单章就是只有一项），外加上游的章节容量合同（目标字数 ±20%）。
- **`settle` 与 `generate` 的差别只在系统提示**（`CAPABILITY_TASK`），**输出契约必须一字不差**：同一份细纲不该因为入口不同长得不一样。

## 依赖关系

依赖 `model/`（读架构、大纲、细纲、正文、摘要、角色卡、设定；`model/pipeline.ts` 提供 Stage × Capability × Target，`model/structureGuide.ts` 算结构区间，合同的字数上限也在 model 里）与 `llm/`（`ChatMessage` 类型）。**不依赖 `features/`**。被 `generation/`（对话页单次生成与生成链）与 `features/pipelineBatch.ts`（工程页批量）调用——两者走同一个 `buildContext`，因此批量与单次产出的是同一个质量。
