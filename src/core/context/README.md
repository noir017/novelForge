# core/context — 上下文装配

插件的核心。在有限 token 预算内，把「文风指南 + 全书摘要 + 相关角色卡 + 本层产物 + 近章原文 + 会话历史 + 用户引用」按优先级装配成一次请求的消息序列，并如实记录装了什么、丢了什么。

## Token 计数是可替换的

改造前 `estimateTokens` 是一个写死的函数，想换更准的算法得改遍全仓库。现在分三层：

1. **`TokenCounter` 接口**——`count(text)` 数 token、`charsFor(tokens)` 反推字符数（截断要用），可选 `prepare()` 供需要加载 wasm/词表的实现。
2. **注册表**——`registerTokenCounter()` 注册、`useTokenCounter(id)` 切换。切换失败（未注册、`prepare()` 抛错）时**保持原计数器并返回 false**，绝不让「数不了 token」把写作流程带停。
3. **`HeuristicTokenCounter`**——默认实现，就是原来那套系数，零依赖、同步、永不失败。它是所有降级路径的终点。

要接 tiktoken 或服务商的 count_tokens 接口，写一个实现注册进去即可，`builder.ts` 一行都不用改。

**校准回路**：服务商返回真实用量时（`usage` 事件 → `collect` 的 `onUsage` → `recordUsage`）记下「估算/实测」比值，`usageStats()` 可查。它**只用于日志与展示，不自动修正估算值**——估算必须是纯函数，否则同一份上下文两次装配会得出不同的预算判断，「不静默截断」的明细也就不可复现了。没给 usage 的服务商什么都不记，不拿估算冒充实测。

## 分阶段装配

一次装配由 `BuildRequest.action.stage` 决定带什么。四张配方在 [recipes.ts](recipes.ts) 里，**顺序即填充顺序**：

| 阶段 | 身份 | 带什么 | 明确不带 |
|---|---|---|---|
| **架构** | 网文策划编辑 | **架构三件（配置 / 前提 / 世界观，P0 force）**、角色图谱一览（P0）、已有角色卡（P1）；排设定清单时另带设定（P2：分类表与已有条目一览，与规划阶段同一种带法），排世界观时带命中与近几章出现过的设定，其余几件不带；**展开一条设定**（单条设定目标）另带这一条（P0 force，含暗设）、已排细纲里用到它的地方与定稿过的记录（P1，合计封顶）、相关条目（P2） | 正文原文、大纲 |
| **大纲** | 策划编辑 | **架构三件 + 角色图谱一览 + 故事结构指导 + 大纲全文（都是 P0 force）**、角色卡（P1）、全书摘要与设定（P2）、各章细纲（P3） | 正文原文 |
| **细纲** | 剧情编剧 | 本章细纲（单章时，P0 force）、**架构三件 + 角色图谱一览 + 大纲里覆盖这几章的那几节（P0 force）**、前 3 章与后 1 章的细纲、前序细纲一览（最近 100 章）、近几章的连续性事实、结构指导；设定（P2：分类表、已有条目一览，排新章时照抄已有的名字） | 正文原文 |
| **正文** | 作者 | **文风指南、全局要求、本章细纲（含第九节「设定」）、上一章结尾（不许重演）、后 5 章细纲（边界）、本章已写末尾（接着写时）、上一版（重写时），都是 P0 force**；出场角色卡、架构三件（除全局要求）、大纲里本章那一节（P1）；全书摘要、设定（P2）；近 2 章正文（P3）；更早各章的细纲（P4） | —— |

**设定（`lore` 层，设定名录）**：几百条设定的书不能命中就整条塞，先排序、再分两种形态装、按详细度封顶。顺位：R0 本章细纲第九节点名的、R1 关键词命中（作者这次说的 → 本章细纲 → 本章已写的末尾）——**整条**（一句话 + 正文 + 尾巴：水位之后、本章之前定稿章里关于它的新事实，条目落后于正文时模型照样拿得到）；R2 前几章定稿出现过的、R3 大纲 / 细纲阶段其余条目按出现章数——**一句话**。整条超了上限降成一句话、一句话超了上限丢，都写原因；R3 超了只并成一条报（`lore:catalog`），不逐条刷明细。条目整合到本章或更晚时明细里提醒可能含之后的事。续写那几轮也带（只 R0、R1）。消息里整条的空行隔开，一句话的并成一张清单。

**展开一条设定（完善设定，2026-10-19，目标 `{ kind: 'lore', relPath }`，阶段是架构）**：设定那张配方多挂两层，目标不是单条设定时它们什么都不带（[layers/loreFocus.ts](layers/loreFocus.ts)）——`loreSelf`（P0 force）是焦点，这一条的一句话、关键词与全部正文，暗设照规划时的样子标明（`loreBodyFor`），还只有一句话的在明细里注一句；`loreMaterial`（P1）是两样原料（`views/loreMaterial.ts` 的 `expansionMaterial`）：**已排细纲里用到它的地方**（没定稿的细纲第九节点名它的那一行、梗概与关键事件里提到它的句子，带章号）与**定稿过的记录**（与建条目、整合同一份 `recordsAbout`），两样合计照整合的 `MATERIAL_TOKENS` 封顶——都放不下各占一半、一边用不完让给另一边，没带上的写明带到第几章（第 2 条）。`lore` 层在这个目标上不提前返回：去掉目标条目本身，关键词命中的来源在作者的话之外再加这一条的标题、关键词、一句话、正文与上面那几句（整条），同一个分类目录里的一行带，给分类表（建议拆出的子条目要归类），不给 R2、R3。消息里的顺序是「定稿过的记录 → 已排细纲里用到它的地方 → 当前这一条设定」，紧挨着指令。焦点不按 `targetNo` 定位（`focus.no` 是 +∞），已写正文的书也不按正文「整理」（`settingFromText` 跳过它）。系统提示的那一句与输出合同在 [loreExpandPrompt.ts](loreExpandPrompt.ts)，不借 `LORE_ENTRY_SYSTEM`（那一份第 1 条是「不补完、不推测」）；放在 context/ 而不是 features/，因为本层不依赖 features/。

**设定条目的「暗设」（完善设定，2026-10-19）**：条目可选的第四节，读者还不知道的真相（`model/loreFile.ts` 的 `splitLoreHidden` 认）。**正文阶段（写、接着写、重写、讨论正文）与续写**：整条只带明面，这一条真有暗设被去掉的在明细 note 里注一句「暗设没带：……」（第 2 条）；作者 @ 引用的设定条目（`attachments` 层，`lore` 种类）同样去掉、同样注一句。**规划时（设定 / 大纲 / 细纲）**：整条带全部，暗设挪到最后、标题统一换成「## 暗设（读者还不知道）」（`LORE_HIDDEN_MARK`）。怎么拆、怎么标在 `layers/render.ts` 的 `loreBodyFor`，lore 层与 @ 引用共用。一句话（`loreBrief`）本来就跳过暗设。

表里与下文的章数、字数都是**上下文详细度**缺省那一级（「详细」）的值，各级见下面[「上下文详细度」](#上下文详细度)一节。

四张都按 [总计划](../../../docs/design/plans/2026-09-30-blueprint-pipeline-roadmap.md) §2.3 排：前三张二期，正文那一张三期（移植自 AI-Novel-Writer 的 `next_chapter_draft` 材料包），四期在它的 P2 加了 `evidence`。**执行卡与篇幅合同不是层**，由输出契约拼在消息最末（上游 GD:657 的顺序）。

**正文续写那几轮**（`step.kind === 'continuation'`，generation/continuation.ts）换一张精简配方：系统提示、这一轮的话、文风、全局要求、本章细纲、后 5 章边界、本章已写末尾、出场角色，外加近几章定稿的连续性事实（`recentFacts`，≤3000 字）。前几章细纲与前几章全文第一次调用已经用过，每一轮都付一次全价不值；但一条前情都不带也不行——百章实验里首轮常只写到一半，续写写了一章的大半，死了的人在续写里又活过来。细纲配方同样带 `recentFacts`（P1）：全书摘要在 P2，预算紧时先被挤掉，细纲就会排出与正文矛盾的事。收尾过早被回退的那一轮（`step.rewound`，五期补遗 §1.1）契约开头多两句：「收尾那一段已经拿掉了，写足之后按本章细纲约定的结束状态重新收尾」。

**执行卡后面跟一块【本章边界】**（五期补遗 §1.2、§1.3；禁用词是百章实验复盘加的：生成层 `planWriting` 算好经 `BuildRequest.banned` 交过来，第一次调用点名不许用的词，续写那几轮换成「已写部分用了哪几个、几次」）：后 5 章细纲里才排到、本章与前面各章都没排过的人逐个点名「本章不出场：沈秋（第 4 章才登场）」（生成层 `planWriting` 按磁盘算好经 `BuildRequest.notYet` 交过来：带角色卡上的称呼、本章细纲自己提到的人不算，与写完查的那一份同源；没给时 `promptFactsOf` 从 focus 现算一份）；再重列比喻词上限，续写那几轮换成「已写部分用了 k 次，续写部分最多再用 n 次」（`step.similes`）。三期首跑时边界只有一句原则，第 3 章的结尾照样把第 4 章的人写了出来。

**系统提示加一条「用词贴合年代」**（§1.5）：架构、大纲、细纲的「通用要求」第 4 条与正文的硬性要求第 7 条，古代、民国、架空世界不用 PTSD、抑郁症、多巴胺、CPU 这类现代术语。越早的阶段写进去，后面每一层都照着抄。

三期加的四层：

| 层 | 注入什么 |
|---|---|
| `guidance` | 小说配置的「全局要求」一节，单独成段（`# 全局要求（每一章都要遵守）`） |
| `premiseWorld` | 小说配置（**除全局要求**，不重复带）、故事前提、世界观，一件一条 |
| `plotAhead` | 后 5 章的细纲一章一行（标题 + 关键事件前 300 字），标「绝对不要在本章提前写出」。**按章号窗口取**（N+1..N+5，上游 GD:464-466），只带排过的 |
| `chapterSoFar` | 本章已写正文的最后 1600 字：「接着写」读磁盘，续写那几轮由生成链给（含这一次刚写、还没落盘的） |

「接着写」时不带上一章结尾：这一章的开头早就从那里接过了，两个「从这里接下去」摆在一起，模型会跳回上一章去。

**`revision`（上一版正文 + 修改意见）带整章**（五期修）：从前是 `takeTail(…, 3000)`——3000 token 的尾巴，长一点的章前半截直接没了，「重写」时模型只能凭空重写开头，明细上还看不出少了什么（第 2 条）。

四期加的一层（D18）：

| 层 | 注入什么 |
|---|---|
| `evidence` | 前面各章的**定稿原文片段**：拿定稿过的细纲里连续性事实的证据原句回到那一章的正文里逐字定位，带所在段落与前后各一段（移植 `chapter-materials.ts` 的 `assembleChapterMaterials`）。只认定稿之后正文没再改过的章（细纲的 `sourceHash` 对得上正文）。前 5 章的事实全取，更早的只取提到本章角色（细纲 `characters[]` 与别名）的，最多 12 章、一共 6000 字，由近及远填、按章号正序拼成一节「# 定稿原文片段（前情以这些原文为准……）」。正文层 P2 的第一层，续写配方不带 |

- **定位不到**（作者手改过细纲里的事实或证据句）的那几条换成事实原句，条目标 degraded 并写明几条；放不下的章 dropped 写明是封顶了（第 2 条）。
- **与近章全文去重**：某一章整章正文进来了（`manuscriptFull`），它的片段改成 dropped、预算退回去——与上一章结尾片段同一个做法（`scratch.evidence`）。
- **D23**：上一章有正文却还没定稿，明细里多一条 dropped 的「第 N 章 · 定稿原文」，写明「没有连续性事实，角色状态截至第 K 章」；上一章定稿之后正文又改过，写明「连续性事实不作数」；更早的章遇到这两种静默跳过。`characters` 层每张卡的说明带「状态截至第 K 章」。不挡路，但不静默。
- **近章全文 0 章就是一章全文都不带**（四期顺手修掉：从前 `slice(-0)` 把前面每一章都整章塞了进来；现在各层取「最后 n 个」一律走 `takeLast`）。
- 上下文详细度「精简」整层不带，出一条 `evidence:off` 的 dropped 说明。

七期加的一层：

| 层 | 注入什么 |
|---|---|
| `threads` | `threads.md` 里**还没收、和本章有关**的叙事线，一条一个条目（`thread:<序号>`），一条一行拼成一节「# 进行中的叙事线（只作提醒：以本章细纲为准……没到回收章的线不许提前揭开）」，排在定稿原文片段后面、前文正文前面。挑哪几条、怎么排、一行怎么写在 `model/threadsFile.ts`（`pickActiveThreads`）：本章细纲提到的 → 本章在计划区间里的 → 已过回收章的 → 已经埋下的 → 只是人物对上的；**计划中、还没到埋下那一章、细纲也没提的不带**。最多 6 条、一共 1200 字（只算各行），放不下的**跳过、接着试下一条**（上游是 `break`），dropped 写原因。正文层 P1，紧跟 `outlineSlice`；续写、审稿、修稿不带 |

- **状态按「写到这一章时」算**（`asOf`）：重写第 N 章时只看第 N 章之前的事件，后面几章才发生的推进与回收不透给前面。
- 取消勾选的那条标 excluded、不占名额，后面的补上来。
- 没有 `threads.md`、或者一条有关的线都没有：这一层什么都不出（没有东西被截断）。

写作技能那一层（移植自 AI-Novel-Writer 的阶段 Skill，见 [skills/README.md](../skills/README.md)）：

| 层 | 注入什么 |
|---|---|
| `skill` | 这一次装配所属阶段绑的那份写作技能（`.novelforge/skills.json`），一个条目（`id: 'skill'`）。**每张配方都有**，排在 P0 那一组的最后：作者事实先拿预算，技能再拿。消息里排在**用户消息最前面**：「【补充写作 Skill：名字】以下内容只能补充创作方法；作者事实和后续输出合同始终优先。」+ 正文 |

- **阶段**由 `model/writingSkill.ts` 的 `skillStageOf` 定：架构 / 大纲 / 细纲三层的生成与沉淀 → 规划；写、接着写、重写与续写那几轮 → 写正文；审稿（含重来一次）→ 审稿；修稿与修稿续写 → 修稿。**讨论不带**。
- **自己读绑定**（与 `style` 层读 `style.md` 一样），不经 `BuildRequest`：对话页、agent、工程页批量带的是同一份。
- **整份带或整份不带**：不 force，放不下 dropped 并写明需要多少、剩多少，不截半截（第 2 条）。
- **绑了却带不上**（找不到、变得不兼容、绑定文件读不懂）：dropped 写原因，生成照常——上游是让整个工作流起不来。
- 用了哪份、为什么没带记一条日志（同一句五分钟内只记一次）：工程页批量没有明细可看。
- **从已写正文整理（`derive`）时不带**：那一次是照实整理，一份「规划」技能会让模型按它的排法改写已经发生的事。

拆书 A 加的一层（「从已写正文补齐」，features/derive.ts）：

| 层 | 注入什么 |
|---|---|
| `written` | **只在 `BuildRequest.derive` 时有内容**（已经写了正文的书生成配置 / 前提 / 世界观时，`builder.ts` 的 `settingFromText` 自动补上，角色图谱除外），两张配方（架构 / 大纲）挂着、平时为空。架构：均匀抽样 5 章的开头节选（首章 3000 字、其余 2000 字，force）+ 第 1–N 章的梗概与看点一行一章（取定稿过的细纲，没定稿的章不带并写明几章；放不下就隔章抽、degraded 写明每几章取一章，一章都放不下 dropped）；大纲：区间里各章**定稿过**的细纲的梗概 / 关键事件 / 看点 / 状态变更 / 新增伏笔，没定稿过的章退回正文头尾（没定稿的细纲是写之前的计划，不当已经写成的东西）。小节「# 已写正文（作者已经写成的权威事实：这一次是从中整理，不是创作）」排在前序细纲一览之前 |

- 系统提示在 `CAPABILITY_TASK` 后面多一句「这一次不是从零创作：作者已经写到第 N 章……正文是权威事实」；契约开头多一段【从已写正文整理（重要）】：正文写到的照抄、必填而正文没写到的顺着走向补、不写「待确认」。
- 配置的任务换成「照正文归纳、不按市场重新包装」，JSON 合同不变；大纲换成 `deriveOutlineContract`（只写已经发生的，分节格式与续写大纲同一份）。细纲不在这里整理：拆书第一步就是定稿的第一步，照正文写出来的细纲直接算定稿过（见 [features/README.md](../features/README.md) 的 `derive.ts`）。

五期加的三张配方（`recipeFor(stage, capability, step, writeMode)`）与两层：

| 配方 | 带什么 | 明确不带 |
|---|---|---|
| **审稿**（`capability: 'review'`） | 系统提示（审查原则、检查维度、事实的优先级）、作者要求重点检查的方面、**这一章正文全文与本章细纲（P0 force）**、后 5 章细纲（P0，小节标题换成「后续章节计划（非既定历史……）」）；出场角色卡、架构三件、全局要求、上一章结尾（P1）；前几章的连续性事实（P2） | 历史对话、文风（文笔不在审查范围里） |
| **修稿**（`writeMode: 'revise'`） | 系统提示（只依据人工确认的审稿意见改）、**整章原文 + 勾选的审稿清单、文风、全局要求（P0 force）**；本章细纲、出场角色卡、上一章结尾、后 5 章边界（P1）；定稿原文片段（P2） | 写正文那一套法则、篇幅合同、执行卡，大纲、前几章细纲、近章全文 |
| **修稿续写**（被截断之后） | 系统提示、文风、全局要求、原文与清单、已修订正文的最后 1600 字 | 其余一律不带 |

| 层 | 注入什么 |
|---|---|
| `chapterFull` | 目标章自己的正文全文（审稿审的就是它），小节「# 待审正文」紧挨着契约 |
| `recentFacts` | 前几章定稿留下的连续性事实（定稿过的细纲最后一节），只带事实文字（最近 12 章、3000 字封顶）。没定稿、或定稿之后正文又改过的章 dropped 并写原因——拿一份过期的事实判「与前文矛盾」，判出来的可能正是作者改过的地方 |

审稿的输出契约是 JSON 合同 + 目标逐项核对（冻结清单由审稿链在装配之前冻结好、经 `BuildRequest.reviewGoals` 交过来，契约里给模型的与链上校验用的是同一份）；重来那一次（`step.kind === 'reviewRetry'`）前面说清上一次为什么被丢弃。

**细纲批次**（请求带 `range`）与单章共用细纲那张配方：批次没有「本章」，`plotSelf` / `plotPrev` 不出场，由前序细纲一览全包（最后三章带看点，看点空着就不带）；前文的边界是区间第一章，后文从区间最后一章之后算起。生成链拆半重试时，前一半刚排好、还没落盘的那几章经 `draftPlots` 接在一览最后。

二期加的四层：

| 层 | 注入什么 |
|---|---|
| `structure` | 按总章数算好章号区间的故事结构指导（六种结构都有区间，见 `model/structureGuide.ts`），并点明本批落在哪几段。没写总章数时不带，明细里说原因 |
| `rosterDoc` | 角色图谱一览：全部角色卡压成一人一段（名字后面是性别与别名，下面是身份、人物关系、当前状态的开头） |
| `outlineSlice` | 大纲里覆盖本章 / 本批的那几节；大纲没有区间标题时退回全文并说明 |
| `plotList` | 前序细纲一览，一章一行 |

几处刻意的抬高（表里加粗的几条）：

- **正文阶段文风指南升到 P0 force**。它是「读者感觉不到换人执笔」的唯一保障，不该跟一段长对话抢预算——改之前它在 P1，一段长对话（封顶 30%）加几张角色卡就能把它挤掉。
- **正文阶段本章细纲也升到 P0 force**。细纲**就是**写正文的依据：少了它，模型手上只有文风与前文尾巴，会自己编一章出来。
- **正文阶段后 5 章细纲也是 P0 force**。那是边界：没有它，模型写到章末时最顺手的就是把下一章的事提前演掉，下一章于是无事可写。
- **架构与大纲两层的架构三件是 P0 force**。四件一件吃一件：前提照着配置写、世界观照着前提与角色写，少了上一件，这一件就是凭空编的。
- **`settle`（落定细纲）时历史 cap 从 30% 抬到 60%、优先级提到 P0**（`recipeFor(stage, capability)` 唯一一处按能力改配方的地方）。这条命令要沉淀的就是那段讨论，按常规由远及近截掉等于把结论截没了。

**细纲阶段带前后文而不是只带上一章**：前 3 章的细纲（梗概 + 关键事件 + 状态变更）让这一章接得上——发生了什么、人物落在什么处境；后 1 章（梗概 + 关键事件）让它不至于把下一章要用的东西提前用掉。更早的章由前序细纲一览一章一行带，不再另带一份：细纲与定稿是同一份文件，同一份不带两遍。

**挑角色卡**：`selectCharacters` 第一优先是本章细纲的 `characters[]`（没定稿时是计划出场，D13——只在这里用，不进出场统计），其后是这一轮输入里提到的、前两章定稿过的细纲里出场的与主角。

**前三个阶段都不带正文原文**：定架构、排大纲、拆细纲时读三章正文既没用又昂贵，一章三千字 × 近三章，够装下全书摘要还有富余。

## 预算与降级

| 优先级 | 预算不足时 |
|---|---|
| P0 · force | 永远保留（系统提示、用户这一句、本层产物） |
| 用户 @ 的引用 | 单条封顶预算 35%，超出从头部截断而非丢弃 |
| 会话历史 | 整体封顶按上下文详细度（缺省 30%，`settle` 时固定 60%）、单轮 12%，由近及远保留，更早的整轮丢弃。**已经写入的那一轮（`acceptedTo`）与发起它的命令轮不带**（五期补遗 §1.4）：它们落了盘，有专门的层按磁盘带，落盘后手改过的话历史里还是旧版；明细里记「已写入 xxx，以磁盘上那一份为准」。讨论与没采纳的那一版照旧带。**已经移除的内置 agent 跑的那几轮（`isBuiltinAgentTurn`）与交给它的那句指令也不带**：那是调度过程，不是讨论 |
| 角色卡 | 降级为「身份 + 当前状态 + 未收伏笔」三节 |
| 某章正文 | 降级为该章细纲（没定稿的标「计划，没定稿」）→ 丢弃 |
| 更早各章的细纲 | 由近及远填充，最多最近 N 章（上下文详细度，缺省 60），填满即止；没定稿的标「计划」，定稿之后正文又改过的标 ⚠；封顶之外的合成一条 dropped |

预算 = `contextWindow - maxOutputTokens - 512`，并与 provider 的 `maxInputTokens` 取小。

## 上下文详细度

全局设置（设置 → 上下文管理），四级：**每一次调用带多少前文与设定**。级别与每一级的上限定义在 [model/contextDetail.ts](../model/contextDetail.ts)（纯数据、零 import，设置页的下拉框与说明行用同一份）；各层只经 `contextLimitsOf(config)` 取上限，`Assembly.limits` 上一份，不再各自写死常量。对话页、工程页批量、外部 agent 三条路都经 `readConfig()` 拿到同一级。

| 项 | 1 精简 | 2 标准 | **3 详细（缺省）** | 4 完整 |
|---|---|---|---|---|
| 近章全文（`manuscriptFull`） | 0 | 1 | 2 | 3 |
| 上一章结尾（`prevTail`） | 1000 字 | 1500 字 | 1500 字 | 2000 字 |
| 更早章细纲（`plotSummary`，正文 / 大纲） | 最近 5 章 | 20 | 60 | 不限 |
| 定稿原文片段：前几章全取 / 最多几章 / 字数 | 不带 | 3 / 6 / 3000 | 5 / 12 / 6000 | 8 / 20 / 10000 |
| 近章连续性事实（细纲、续写、审稿、写前冲突检查） | 6 章 / 1500 字 | 8 / 2000 | 12 / 3000 | 20 / 5000 |
| 叙事线 | 3 条 / 600 字 | 4 / 900 | 6 / 1200 | 8 / 1800 |
| 前序细纲一览 | 30 章 | 50 | 100 | 不限 |
| 细纲单章：前几章 / 后几章细纲 | 1 / 1 | 2 / 1 | 3 / 1 | 5 / 2 |
| 对话历史封顶 | 15% | 20% | 30% | 40% |
| 角色卡 | 只带身份 / 当前状态 / 未收伏笔 | 整张 | 整张 | 整张 |
| 挑出场角色看前几章定稿过的细纲 | 1 | 2 | 2 | 3 |
| 拆书补齐抽样（`written`） | 3 章 | 4 | 5 | 8 |
| 后台：提取文风缺省勾前几章 / 提取角色缺省勾最近几章 / 参考书文风抽几章 | 1 / 1 / 3 | 2 / 2 / 4 | 2 / 3 / 5 | 3 / 5 / 8 |
| 后台：排叙事线带大纲几字 / 细纲每行事件几字；定稿判线最多几条 | 4000 / 60；6 | 6000 / 90；9 | 8000 / 120；12 | 12000 / 200；16 |
| 设定：整条带几条 / 一句话带几条 / 合计字数 / 每条尾巴几行 | 2 / 10 / 1500 / 1 | 4 / 20 / 3000 / 2 | 6 / 40 / 5000 / 3 | 10 / 80 / 8000 / 5 |

- **第 3 级就是从前的行为**，只多两条：更早章细纲最多带最近 60 章；设定封顶（从前命中就整条塞、不排序不封顶，几百条的书会把窗口填满）。从前细纲那一层没有上限，长篇写到七八十章会把整个窗口填满（128k 窗口约第 80 章）。
- **封顶之外的细纲合成一条 dropped**（`plotSummary:beyond`，「第 1–N 章 · 细纲」），不是一章一条：一百多章的书封在 5 章时，明细里摆九十几行「不带」只会把真正带了什么淹掉。更早的前情由全书摘要接着。名额按「最近几章」数，手动取消勾选的那一章照样占一个名额。
- **因级别少带的都留说明**（第 2 条）：细纲封顶、`evidence:off`、角色卡「只带身份/当前状态/未收伏笔」、前序细纲一览「只带最近 N 章」都写出是哪一级。原有的上限说明（「叙事线一次只带 6 条」「定稿原文片段一共只带 6000 字」）措辞不变，数字跟着级别走。
- **不分级的**：后 5 章边界（`AHEAD_PLOTS`——生成层算「本章不出场」用同一个窗口，两边必须一致）、本章已写末尾 1600 字、@ 引用 35%、`settle` 的历史 60%、整份带的文档层；定稿、全书摘要、角色状态、建卡、记设定、建条目与整合（输入就是那一章本身或按窗口分批，调低只会截掉要整理的东西、或多拆几次调用）。
- **任何一级都不改调用次数**（第 4 条），只改每次带多少。
- 装配结果带 `detail`：装配清单的摘要行写「详细度：详细」，「上下文已装配」那条日志也写；批量写章的确认框写当前级别。
- 设置页原来的「注入完整原文章数」「上一章结尾字数」两个输入框并进了级别。config.json 里的旧键不再读（设置页保存过一次的人这两个数都在文件里，分不清是不是手改的），下一次保存时清掉。
- 测试要单独改某一项（例如「近章全文 0 章、其余照缺省」）用 `NovelConfig.contextOverrides`；走 `readConfig()` 的链路用 `config.ts` 的 `setContextLimitsOverride`。两样都不从 config.json 读：作者能动的只有级别。

## 关键设计

- **不静默截断**：每条 `ContextItem` 带 `status`（included / degraded / dropped / excluded）与人类可读的 `note`，前端折叠展示。作者随时知道这次没带上什么。
- **发出去的那份原样留着**：对话页那一轮的 `built.messages` 记在回复上（`ChatTurn.contextMessages`，随会话落盘，只记第一次调用——续写、修复那几轮另行装配），装配清单摘要行上「复制完整上下文」一下复制整份。日志照旧只记条目名与 token 数（第 11 条）；工程页批量与 MCP 的 `generate` 不留。
- **层与配方分离**：「带什么」在 recipes、「怎么取」在 layers。让细纲阶段不带正文原文是配方里少写一行，不是装配器里多一个 if。
- **只读用得上的文件**：`resolveFocus` 按配方决定读不读前后章的细纲。正文阶段每次生成都多读三章用不上的细纲，那是落在关键路径上的浪费。
- **引用在 P0**：用户特意 @ 的内容不该被自动装配挤掉。
- **历史是多轮消息**：会话历史按 role 交替作为真正消息发出，不是塞一段「以下是之前的对话」；单轮过长取结尾（越靠后越接近当前进度）。
- **去重**：上一章正文能完整放下时，P0 的结尾片段自动撤掉，同一段文字不在 prompt 里出现两次。`manuscriptFull` **只认领它确实注入了的章**——认领了却没注入的话，更早各章细纲那一层（`plotSummary`）会跳过它，于是它从上下文里凭空消失，而明细上还看不出少了什么。
- **正文只读 `chapters/`**：一章一纲之后正文只在一处，从前还要回落到中转站 `manuscripts/`。只有 `chapters/` 的老工程一样带得出前文。
- **讨论型能力禁止改写产物**：`outputKindOf(action) === 'text'` 时系统提示里明写「只回答，不要输出改写后的完整产物」。少了这一条，模型会一边回答一边把整份剧情细纲重写一遍，而界面上那一版是不能采纳的。
- **细纲可以写具体场面，但不是正文**：从前细纲被禁止写画面与动作、只许写抽象的因果链，模型拿它去「扩写」出来的是流水账。现在细纲就是定稿那八节（连续性事实计划时空着，定稿时才生成）：「关键事件」一条一件事、按发生顺序（3–6 条、合计 100–300 字，与定稿写出来的列表同一个样子，定稿才能逐条改而不是重写），可以写到具体场面，梗概与关键事件必填、出场人物至少一人；「看点」写爽点，也写章末吊着读者的那一下，过渡章没有爽点就只写钩子，时间地点、看点、新增伏笔、状态变更都可以空着；不写成段的描写与对白。单章与批次用同一份蓝图合同（`{"blueprints":[…]}`，单章就是只有一项），外加上游的章节容量合同（目标字数 ±20%）。
- **`settle` 与 `generate` 的差别只在系统提示**（`CAPABILITY_TASK`），**输出契约必须一字不差**：同一份细纲不该因为入口不同长得不一样。
- **暗设不进正文，揭开靠细纲**（完善设定，2026-10-19）：写正文时看不见暗设，揭开那一章的正文模型只能从细纲知道。细纲合同（写细纲、落定细纲、批量拆细纲同一份）多一块【暗设】：标着「暗设（读者还不知道）」的，这一章不打算揭开就别写进梗概、关键事件、看点与第九节的 note，要铺垫写进新增伏笔、只写读者看得到的那一面；打算揭开就在关键事件里单列「揭开：……」。大纲合同同一个口径（第 11 条要求）——大纲覆盖这一章的那几节也进写正文的上下文（正文配方的 `outlineSlice`）。

## 依赖关系

依赖 `model/`（读架构、大纲、细纲、正文、全书摘要、角色卡、设定；`model/pipeline.ts` 提供 Stage × Capability × Target，`model/structureGuide.ts` 算结构区间，合同的字数上限也在 model 里）与 `llm/`（`ChatMessage` 类型）。**不依赖 `features/`**。被 `generation/`（对话页单次生成与生成链）与 `features/pipelineBatch.ts`（工程页批量）调用——两者走同一个 `buildContext`，因此批量与单次产出的是同一个质量。
